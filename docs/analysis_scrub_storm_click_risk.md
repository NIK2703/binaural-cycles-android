# Анализ: риск щелчков при «шторме» смены позиции скраба в редакторе пресета

Дата: 2026-09-05
Объект: `FrequencyGraph.ScrubHandle` (два залитых треугольника ◀|▶ на красной линии
текущего времени) в `PresetEditScreen` при включённом предпросмотре пресета.
Вопрос: где в пути «быстрая серия перетаскиваний ручки скраба» разрыв может дойти
до динамика, и что с этим делать.

Статус: анализ + **правки, четвёртая волна ЗАВЕРШЕНА** — сборка 09:53 установлена на
устройство и измерена (§4.3, §4.4). Волны 1–3 собраны и измерены; волна 4 шаг 1
(унификация + неупорядоченная пара + двухуровневая коалесценция) и шаг 2 (полный
отказ от перекрытия: фейд-ин только после полного затухания фейд-аута) реализованы

* `beginOverlapSwitch` удалён: кроссфейда нет ни для одной причины, перекрытия
  в принципе не существует.

* `dbgstorm.sh`: сценарий `preset` НЕ проверяет `PRESET_SWITCH` — этой причины в

### Вторая волна: когерентная интерференция и переход с нулевым перекрытием

При подготовке R3 выяснилось, что R2 описан **неполно** — и это меняет главный
вывод. Полный разбор в §4.1 (ниже, после списка рисков). Суть:

* При скрабе кривая **та же** → CURRENT и NEXT звучат почти одинаковой частотой
  (Δf ≈ 0.3 Гц при 5-мин сдвиге и контрольных точках через 3 ч). Такие тоны
  складываются **по амплитуде**, не по мощности: сумма = √2·|cos(φ/2)|, где φ —
  разность фаз.
* `getCurrentPhases()` читает фазу **фронта генерации**, который опережает
  слышимое на глубину кольца AudioTrack (2 МиБ = 5.46 с @48 кГц, чанк 3.46 с ⇒
  400–2200 периодов несущей) ⇒ φ фактически равномерно случайно.
* Итог перекрытия: от **полного взаимного гашения** (~1 скраб из 6) до **+3 дБ**.
  Никакая форма рампы (ни linear, ни equal-power) это не лечит.

**Правка (Manager + Impl):** SCRUB больше не кроссфейдится вовсе —
`beginCrossfade` маршрутизирует `SpecReason.SCRUB` в `beginSilentSwitch`:

| Элемент | Значение |
|---|---|
| `SCRUB_DUCK_FADE_MS` | 120 мс — «приседание» (обе рампы, уход+приход, equal-power) |
| Подготовка NEXT | заранее (`prepare()`, пакет сгенерирован), но `start()` отложен |
| Старт NEXT | из хука тишины `onSilent` — когда огибающая CURRENT **фактически** в нуле |
| Владение `current` | передаётся NEXT **сразу** (жест в 120-мс окне бьёт по NEXT, а не по обречённому outgoing) |
| `pendingSilentSwitch` | блокирует `tryAdvanceQueue()` — третьего трека и перекрытия нет |
| Отказ `prepare()` | тот же retry-путь, что и R1 (`SCRUB_RETRY_*`), без `beginHandoffSequential` |
| `release()` | абортирует осиротевший NEXT (иначе утечка трека+пакета) |

Интерфейс: `BinauralStream.start(..., fadeInMsOverride)`,
`BinauralStream.stopWithSilentHook(...)` (старый `stop()` нетронут — 5 мест
вызова не менялись). Хук обёрнут в once-only `AtomicBoolean` и срабатывает
**до** `finalizeStop` (пауза/релиз трека — слишком поздно, поднимать NEXT надо
на нуле огибающей).

Поведенческое следствие: применение одиночного скраба задерживается на
`SCRUB_STORM_SETTLE_MS = 150 мс` — меньше длительности самого кроссфейда (250 мс).

### Третья волна (2026-09-05, утро): когерентность — свойство пары тонов, а не причины

Волна 2 маршрутизировала нулевое перекрытие по ПРИЧИНЕ (`reason == SCRUB`). Это
неполно: когерентность определяется тем, КАКИЕ тоны звучат в перекрытии, а не тем,
почему меняется спека. Полный разбор и результаты измерений — §4.2. Кратко:

| Правка | Где |
|---|---|
| `isCoherentHandoff(old, spec)` — решение по ФАКТИЧЕСКИМ частотам: каналы CURRENT (из живого движка) против кривой NEXT на её оси, порог `COHERENT_DETUNE_HZ = 4 Гц`. Коалесценция `HANDOFF_STORM_SETTLE_MS = 150` распространена на `PRESET_SWITCH` (листание пресета) | Manager |
| Повтор `prepare()` (`HANDOFF_RETRY_DELAY_MS = 400`, `HANDOFF_RETRY_MAX = 3`) — для ВСЕХ причин: разрыв 100–200 мс не нужен ни смене пресета, ни правке настройки; после лимита — прежний последовательный путь | Manager |
| Переименования: `SCRUB_STORM_SETTLE_MS → HANDOFF_STORM_SETTLE_MS`, `SCRUB_RETRY_* → HANDOFF_RETRY_*`, `SCRUB_DUCK_FADE_MS → ZERO_OVERLAP_FADE_MS`, `scrubRetry* → handoffRetry*` | Manager |
| `tools/dbgscrub.sh`: V1/V2 ждут `beginSilentSwitch` + `startPendingSilentSwitch: SWAP по нулю` (а не `beginCrossfade: SWAP`); V3 — исправлен regexp `scrubReset (сдвиг=…)` (слово «прежний» в логе никогда не было — проверка падала на верном поведении) | tools |
| `tools/dbgstorm.sh` — НОВЫЙ: шторм жестов (скраб/пресет/настройка) с подсчётом переходов, вердиктов когерентности, разрывов и `pkstat` до/после | tools |

`dbgscrub.sh` V1–V9 после второй волны: 52 PASS / 2 FAIL; оба провала — устаревшие
ожидания логов (исправлены в этой волне), не дефекты кода.

**Шаг 2 — отказ от перекрытия (решение пользователя: фейд-ин не смешивается
с фейд-аутом, а начинается только при полном затухании).** Реализовано,
собрано (09:53), установлено и измерено:

* `beginTransition` всегда идёт в `beginSilentSwitch`; ветка
  `beginOverlapSwitch` УДАЛЕНА вместе с кроссфейдом.
* `isCoherentHandoff` → `logCoherenceVerdict` (Unit): вердикт печатается как
  ДИАГНОСТИКА (новый тег лога `когерентность:`), но ничего не маршрутизирует —
  по Δf в логе видно, чем грозил бы кроссфейд на этом жесте.
* Обоснование (§4.4): кроссфейд корректен по ЭНЕРГИИ только для дальних
  тонов, но и там в окне звучат два звука разом, а при перестановке каналов
  уши меняются местами внутри окна (модуляция на |beat|, §4.2-2);
  когерентный случай — случайный провал до нуля (§4.1). Нулевое перекрытие
  убирает оба класса разом и не зависит от вердикта.
* `BinauralStream.stop(fadeOutMsOverride)` **ОСТАВЛЕН**: параметр нужен не
  кроссфейду, а плечу ухода «приседания» (`stopWithSilentHook` вызывается
  только из `beginSilentSwitch` и всегда с `ZERO_OVERLAP_LEG_MS`). Пара
  `fadeInMsOverride`/`fadeOutMsOverride` симметрична и задаётся одной
  константой — слышимая длина перехода одна для всех маршрутов.
* `BinauralStreamImpl.stopWithSilentHook`: маркер момента тишины
  `stop spec#N: ТИШИНА — v=… через …мс от старта рампы, поднимаем NEXT`.
  Без него инвариант «фейд-ин строго после полного затухания» по логу не
  проверить: до этой правки в логе не было НИ ОДНОЙ точки, где огибающая
  CURRENT подтверждённо в нуле.
* В `beginSilentSwitch` и `startPendingSilentSwitch: SWAP по нулю` добавлена
  **причина** (`причина=SCRUB`): штормовые прогоны считают переходы по
  причине, иначе посторонние SETTINGS-пуши ViewModel раздувают счётчик.
* Инструменты переведены на новые маркеры: `dbgstorm.sh` считает порядок
  «гаснет → ТИШИНА → SWAP по нулю» и мерит ритм серии по таймстемпам;
  `dbgscrub.sh` получил `expect_transition_order` вместо пустого
  `reject_log "beginOverlapSwitch: SWAP"`.

## 0. Краткий ответ

Шторм в чистом виде **невозможен по устройству жеста**: `scrubTo` вызывается не на
каждом кадре драга, а **только по отпусканию** (`onCommit` из `onDragEnd`). Зато
цепочка быстрых коротких «чик-чик-чик» (drag-tap-release) даёт серию полных
хэндоффов, и каждый из них — это **новый `AudioTrack` + новый нативный движок +
полная пересборка таблиц кривой**, а не просто сдвиг оси.

Хорошая новость: **классический щелчок (ступенька амплитуды) в этом пути закрыт**
— кроссфейд с реальным перекрытием, фазы перенесены, старт из нуля, утилизация на
нуле, underrun-запас 2 с, частота дискретизации не меняется.

Плохая новость: под штормом остаются **три незакрытых источника
слышимого дефекта**, и все три — не «ступенька», а *разрыв/провал/наложение*:

| # | Что | Слышимо как | Вероятность |
|---|-----|-------------|-------------|
| **R1** | Отказ `createAudioTrack` (`-12`, куча клиента AudioFlinger) → аварийный `beginHandoffSequential` | **провал 100–200 мс тишины** | средняя при шторме |
| **R2** | Цепочка 250-мс кроссфейдов между **разными по частоте** тонами | **«заикание»/размазня/биения**, воспринимаемое как щелчки | **высокая** — главный кандидат |
| **R3** | Пересборка таблиц кривой (0.69 МБ, ~4 мс; до 6.6 МБ, ~37 мс) + аллокации на **нити актёра** в каждом `prepare()` | задержка применения, GC, риск R1 | 100 % (стоит каждый скраб) |

Плюс два низковероятных «ступенчатых» остатка: принудительный релиз уходящего
потока сторожем (1200 мс) и WARN-ветка «шейпер не дошёл до цели — шаг неизбежен».

## 2. Что реально ограничивает шторм

1. **Один слот очереди** (`PlaybackQueue.offer` = `slot.set`, `poll` = `getAndSet(null)`).
   Серия A→B→C→D материализуется **не более чем в два потока**: `current` + один `NEXT`.
2. **Двухпотоковый инвариант**: пока `outgoing != null`, `tryAdvanceQueue` не поднимает
   следующий NEXT. Третьего `AudioTrack` не бывает никогда.
3. **Сторож релиза**: `OUTGOING_RELEASE_TIMEOUT_MS = 1200` — если утилизация застряла,
   `s.releaseNow()` снимает уходящий принудительно.
4. **Жест**: `onCommit` только на `onDragEnd`. Непрерывное перетаскивание не
   генерирует ни одного хэндоффа.

**Итог по темпу.** Минимальная длительность одного цикла = fade-out 250 мс
(+ опрос до нуля, потолок 400 мс) + утилизация. То есть шторм вырождается в
**цепочку кроссфейдов с периодом ~300–650 мс**, сколько бы ни дёргали ручку.
При этом **ось UI уезжает вперёд мгновенно** (`_scrubOffsetSeconds` и
`updateCurrentFrequencies()` в `applyScrub`), а звук отстаёт на всю цепочку.
Красная линия на цели, звук — на предыдущей: именно это выглядит как «не успевает».

## 4. Что остаётся (реальные риски)

### R1 — Отказ `createAudioTrack` → последовательный хэндофф (провал 100–200 мс)

`beginCrossfade` при неудаче `prepare()` NEXT **не трогает CURRENT вообще**
(звук продолжается) и уходит в `beginHandoffSequential`:

```kotlin
if (!next.prepare()) {
    next.abort()
    beginHandoffSequential(spec)   // fade-out CURRENT → релиз → только потом NEXT
}
```

`beginHandoffSequential` — это **гарантированная дыра 100–200 мс** между «утихло» и
«зазвучало». Под штормом трек создаётся и destroying-ся многократно; кольцо каждого
урезано до 2 МиБ именно под два живых трека в ~7 МиБ кучи клиента AudioFlinger, и
комментарий в коде прямо фиксирует: при 3 МиБ второй трек не создавался вовсе
(`createTrack_l -12`). Значит запас по куче — не «много», а «ровно в два трека»,
и любая задержка релиза предыдущего трека (писатель застрял в `write()`) приближает
отказ.

**Это не щелчок, а провал.** Но в серии из 5–8 фликов даёт прерывистый, «рваный» звук.

### R2 — Наложение двух РАЗНЫХ тонов в течение 250 мс (главный подозреваемый)

Кроссфейд корректно сводит энергию, но он **не может** свести *содержимое*: на
сдвинутой оси кривая даёт **другую несущую и другую частоту биений**. 250 мс
одновременно звучат два бинауральных тона.

Следствия:
* Разница частот дает **амплитудные биения** на слух — «дрожь», которую в быстрой
  серии легко описать как «щелчки».
* При цепочке (период 300–650 мс) каждый следующий тон входит, когда предыдущий ещё
  не утих, — суммарно это звучит как заикание/размазня, а не как плавный переход.
* Форма рампы рассогласована с комментарием (см. R4), что добавляет провал энергии.

Частично это *дизайн* (предпросмотр должен показать новую точку кривой), но при
шторме — именно то, что слышно.

### R3 — Полная пересборка кривой на каждый скраб (усилитель R1 и R2)

`prepare()` **безусловно** вызывает `engine.updateConfig(spec.config, spec.relaxation)`,
а нативный `setConfig` всегда выполняет `updateCache()`:

```
Interpolation.h:622  updateCache()
   buildLookupTable()      — СВЕЖИЕ shared_ptr<vector<float>> ×2
   buildTrendCrossings()   — computeTrendCrossings, сетка coarseStep ≤ 5 с → ≥17 280 узлов
```

При этом **кривая не изменилась** — изменился только сдвиг оси. Числа из комментария
в коде:

| Режим | Шаг таблицы | Ячеек | Память | `updateCache` |
|---|---|---|---|---|
| Типовой пресет (точки через 3 ч) | 1000 мс | 86 400 | **0.69 МБ** | **~4 мс** |
| Частые точки (шаг в пол 100 мс) | 100 мс | 864 000 | **6.6 МБ** | **~37 мс** |

И это **на нити актёра**, внутри `prepare()`, перед созданием `AudioTrack`.
Под штормом:
* до ~37 мс блокировки актёра на скраб (при частых точках кривой);
* до 6.6 МБ свежих аллокаций на скраб, плюс старые таблицы ещё видны писателю
  (`shared_ptr` держит копию конфига на время генерации пакета) — то есть
  одновременно живут **несколько поколений таблиц**;
* давление на GC → риск R1;
* удлинение `prepare()` → шире окно, в котором CURRENT живёт без NEXT.

### R4 — Рассогласование формы рамп: обещана sin-ветвь, реально LINEAR

Комментарий `beginCrossfade`:

> Обе рампы — EQUAL_POWER (cos-уход и sin-приход, sin²+cos²=1)

Код:

```kotlin
// beginCrossfade, финал:
old.stop(..., shape = FadeShape.EQUAL_POWER)      // уход: f * cos(p·π/2)  ✔
// launchStream:
if (!stream.start(onFullyStarted = { ... }))      // shape НЕ передан
// BinauralStream.kt:35  fun start(..., shape: FadeShape = FadeShape.LINEAR)
```

То есть вход — **LINEAR** (`0 → 1`), а не `sin(p·π/2)`. Сумма энергий:
`p² + cos²(p·π/2)` → минимум **−1.5 дБ около p ≈ 0.75**.

Для одиночного хэндоффа это малозаметно. Для **цепочки** (R2) — каждый переход
добавляет один и тот же провал 1.5 дБ, и серия звучит как пульсация.

> Это расхождение комментария и кода стоит поправить — либо передавать
> `EQUAL_POWER` (тогда `buildCurve` с `rampUp = t > f` даст `t*sin(p·π/2)`),
> либо поправить комментарий. Первое даёт ровную энергию, второе — ничего.

### R5 — Память и принудительный GC

* Пакет в редакторе: `EDITOR_PREVIEW_BUFFER_INTERVAL_MS = 60_000` → **23 МБ** @48 кГц
  float stereo у CURRENT; NEXT живёт на стартовом пакете 2 с = **0.75 МБ**
  (рост запрещён до релиза уходящего).
* `PacketMemoryBudget` хранит learned ceiling после OOM; `allocateDirect` при
  `OutOfMemoryError` **уполовинивает** размер и инкрементит `oomHalvings`.
* Инвариант «не больше двух держателей пакета» проверяется счётчиком
  `livePacketHolders` (peak ≤ 2) — его и надо смотреть после шторма.

При быстрой серии релиз уходящего может не успеть освободить `allocateDirect`-буфер
(писатель держит ссылку), и тогда бюджет начинает уполовинивать пакеты — а это уже
напрямую снижает underrun-запас нового потока.

### R6 — WARN-ветка шейпера: «шаг неизбежен»

```kotlin
if (!settled) {
    StreamLogger.w(TAG, "fade spec#…: шейпер не дошёл до цели за ${rampMs + 400}мс (v=$v) — снимаем принудительно, шаг неизбежен")
}
completion.run()   // -> finalizeStop -> setVolume(0) + pause
```

Если VolumeShaper залип на `v ≈ 0.05…0.2` (не дошёл до ε за 250+400 мс), то
`finalizeStop` жёстко ставит 0 — **реальная ступенька, то есть щелчок**.
Вероятность низкая (нужен перегруженный девайс), но это единственный путь, где
код сам объявляет щелчок неизбежным.

### R7 — Принудительный релиз сторожем (1200 мс)

`outgoingReaper` снимает уходящий через `releaseNow()`, если он не освободился за
1200 мс. Комментарий: «поток уже в нуле по громкости, услышать его невозможно».
Это верно **только если** шейпер дошёл до нуля (см. R6). Если не дошёл — R7
превращается в R6.

### R8 — Лишний кроссфейд на выходе из редактора

`releaseEditorScrub()` → `scrubReset()` → `applyScrub(0)` → ещё один хэндофф.
Это **спроектировано** и идемпотентно (три условия в стороже: `scrubOffsetSec`,
`pausedScrubOffsetSec`, `scrubNeedsRealignment`), но если выход совпал по времени
с незакрытым кроссфейдом от последнего флика, пользователь услышит **два**
перехода подряд. Не щелчок, но заметно.

### R9 — Ловушка проверки: PAUSED

`onSpecChanged` в `ManagerState.PAUSED` **не заказывает хэндофф**, а только ставит
`pausedSpecDirty = true`. То есть скраб на паузе звук не меняет вообще — ни щелчка,
ни предпросмотра. Проверять «есть ли щелчок» надо строго **в RUNNING**.

## 4.1 Добавление (вторая волна): когерентная интерференция — истинная причина провала при скрабе

R2 описывает наложение как «два РАЗНЫХ тона». Для скраба это неверно, и разница
принципиальна: **кривая при скрабе та же**, меняется только точка оси, а контрольные
точки отстоят на часы ⇒ несущие CURRENT и NEXT различаются на доли герца
(5-мин сдвиг при точках через 3 ч ⇒ Δf ≈ 0.3 Гц). Это **когерентные** тоны: в
перекрытии они складываются по амплитуде, а не по мощности:

```
sum = √2 · |cos(φ/2)|,   φ — разность фаз в момент стыка
```

Равнопотенциальный кроссфейд гарантирует сохранение *мощности* только для
некогерентных источников. Здесь же φ даёт всё от **полного взаимного гашения**
(φ ≈ π, провал до нуля — в середине кроссфейда звук исчезает, ~1 скраб из 6 при
равномерном φ) до **+3 дБ** (φ ≈ 0). Слышится как случайный «чпок»/провал — то,
что и описывалось как «щелчок при смене позиции».

**Откуда случайность φ.** RC-2 переносит фазу из `engine.getCurrentPhases()` — а это
фаза **фронта генерации** (`m_state.leftPhase`), которая опережает слышимое
положение на глубину кольца AudioTrack (2 МиБ = 5.46 с буфера @48 кГц, рабочий
чанк 3.46 с ⇒ 400–2200 периодов несущей 200–400 Гц). Дробная часть сдвига фазы
равномерно случайна ⇒ φ в момент стыка непредсказуем. Фазу слышимого фронта
из `getCurrentPhases()` получить нельзя — нативный слой не знает позиции
воспроизведения AudioTrack.

**Вывод: никакая форма рампы не лечит когерентное гашение.** Либо выравнивать фазы
на слышимом фронте (нереализуемо), либо **не перекрываться**.

### Решение: переход с нулевым перекрытием (`beginSilentSwitch`)

NEXT готовится заранее (`prepare()`, пакет уже в кольце — окно underrun исключено),
но `start()` откладывается до **хука тишины**: `stopWithSilentHook` опрашивает живой
множитель шейпера и поднимает NEXT в момент, когда огибающая CURRENT фактически
достигла нуля (опрос, не таймер — см. `scheduleFadeCompletion`). Стык приходится
на нулевую амплитуду ⇒ интерференции нет по определению, ступеньки нет.

Обе рампы — по `SCRUB_DUCK_FADE_MS = 120 мс` (equal-power): «приседание»
240 мс вместо кроссфейда 250 мс, но без лотереи гашения. Подготовка
заранее закрывает и риск R1: к моменту старта NEXT трек уже создан.

**Опасность владения, закрытая в реализации:** `current` передаётся NEXT сразу (до
хука), иначе жест паузы/стопа в 120-мс окне попадал бы в обречённый outgoing
(`stop()` идемпотентен, колбэк никогда бы не пришёл — машина состояний залипла бы
в `FADE_OUT_*`), а NEXT остался бы без владельца. Хук стартует NEXT только при
`next === current` — если за окно поток снесли, старт отменяется.

## 4.2 Третья волна: когерентность как свойство пары тонов (и её границы)

### Что сделано

Решение «кроссфейд или нулевое перекрытие» принимается по фактическим частотам
(`isCoherentHandoff`), а не по `SpecReason`:

```
каналы CURRENT  ← nativeEngine.getFrequenciesAtCurrentTime()   (swap-aware!)
каналы NEXT     ← spec.config.getChannelFrequenciesAt(ось NEXT) (кривая, swap-слепа)
когерентно ⟺ max |Δf| по каналам < COHERENT_DETUNE_HZ = 4 Гц
```

Порог 4 Гц = «один цикл биений на перекрытие»: при `Δf·T < 1` разность фаз
успевает уйти, но не успевает усредниться — это и есть зона, где сумма
`√2·|cos(φ/2)|` непредсказуема. Секунда кривой для NEXT оценивается дважды
(вниз и вверх), берётся меньшая расстройка: консервативная сторона — «когерентно»,
потому что лишнее «приседание» дешевле провала до нуля. Отказ оценки → вердикт
по причине (прежнее поведение: только SCRUB).

### Измерения (`tools/dbgstorm.sh`, 10 жестов с паузой 0.12 с, RUNNING)

| Сценарий | requestHandoff | Переходов | Вердикты | Аварии |
|---|---|---|---|---|
| скраб (цели ±3 ч) | 10 | 5 | все «разные тона», Δf = 42–145 Гц | нет |
| смена пресета (`next` × 10) | 10 | 6 | Δf = 18–59 Гц | 1 отказ `prepare()` → переотложен, без разрыва |
| правка настройки (`swapinterval` 300↔601) | 10 | 6 | все Δf = 18 Гц ровно | нет |

`pkstat`: holders peak = 2 (инвариант ≤ 2 держан), `oomHalvings = 0`,
`INVARIANT НАРУШЕН` — ни одного, `RC1 underrunDelta` — все 0, принудительных
снятий рампы — нет. Т.е. вся «гигиена» волн 1–2 держится и на чужих причинах.

### Три вывода из измерений

**1. §4.1 был неполон: скраб НЕ всегда когерентен.** Утверждение «Δf ≈ 0.3 Гц»
верно для коротких сдвигов при редких контрольных точках. На крутом пресете
(точки чаще) сдвиг оси на 3 часа меняет несущую на 40–140 Гц — переход
ЗАКОННО идёт кроссфейдом. Маршрутизация по фактическим частотам — единственно
верная; по причине — нет.

**2. Найден дефект измерения: раскладка каналов.** Все SETTINGS-вердикты дали
`Δf = 18 Гц ровно` с зеркальными каналами: `L 409→391, R 391→409`. Это |beat|:
частоты CURRENT приходят из движка с учётом перестановки каналов, а кривая NEXT
о ней не знает. Правка настройки НЕ меняет кривую ⇒ истинная расстройка 0 ⇒
переход обязан быть когерентным, но оценивается как «разные тоны» и кроссфейдится.
Слышимая цена: на каждой правке настройки уши меняются местами в перекрытии —
оба тона в обоих ушах, биения на |beat|.

**Исправление (не реализовано):** сравнивать НЕУПОРЯДОЧЕННУЮ пару частот ушей
(`{min(L,R), max(L,R)}` каждого потока). Перестановка — это то же множество
тонов в других ушах: для решения о перекрытии она несущественна, а при нулевом
перекрытии обмен ушей приходится на нулевую амплитуду и неслышим по построению.
Симметрично исчезает и погрешность «CURRENT swap-aware, NEXT нет».

**3. Коалесценция 150 мс не схлопывает серию целиком** (10 жестов → 5–6
переходов): реальный интервал доставки жестов в тесте (~250 мс, `am broadcast`
в device-shell) превышает окно. Окно короче длительности перехода означает
«почти один переход на жест» для любого ритма медленнее окна. Хуже поведение не
стало (10 → 5 вместо 10 → 10), но и обещанного «серия = 1 переход» нет.

### Концепция: единый переход `beginTransition` (принята, НЕ реализована)

Требование: смена пресета, правка настройки и скраб — один и тот же метод,
переход звучит единообразно. Дизайн:

| Элемент | Решение |
|---|---|
| Точка входа | `beginTransition(spec)` — единственный маршрутизатор; `beginCrossfade` и `beginSilentSwitch` становятся его ветвями (`beginOverlapSwitch` + `beginSilentSwitch`) |
| Единая длительность | `TRANSITION_FADE_MS = 250` (= `DEFAULT_FADE_MS`): кроссфейд = перекрытие 250 мс; нулевое перекрытие = два плеча по `TRANSITION_FADE_MS / 2 = 125` мс, сумма та же 250 мс. Слышимая длина перехода одинакова, отличается только характер (смешение против «приседания»), и это различие физически неустранимо |
| Когерентность | `isCoherentHandoff` с неупорядоченным сравнением ушей (см. выше) — тогда SETTINGS/SAMPLE_RATE всегда когерентны, скраб и смена пресета — по факту |
| Коалесценция | окно `HANDOFF_STORM_SETTLE_MS` для ВСЕХ причин: «серия схлопывается в один переход» становится свойством системы, а не свойства жеста. Цена — 150 мс на одиночную правку настройки |
| Повтор `prepare()` | уже общий для всех причин (сделано в этой волне) |
| Аварийный путь | `beginHandoffSequential` остаётся последним рубежом после `HANDOFF_RETRY_MAX` |

## 4.4 Четвёртая волна, шаг 2: полный отказ от перекрытия

### Решение

Любой переход идёт **только** через `beginSilentSwitch`; ветка
`beginOverlapSwitch` и кроссфейд удалены. Обоснование — из двух классов
дефекта, которые перекрытие создаёт само по себе:

* **Когерентный случай** (Δf < 4 Гц): тоны складываются амплитудами,
  `√2·|cos(φ/2)|` со случайным φ (§4.1) — от полного взаимного гашения до
  +3 дБ. Никакая форма рампы это не лечит.
* **Некогерентный случай**: по энергии кроссфейд корректен, но в окне звучат
  **два разных звука разом**, а при перестановке каналов уши меняются местами
  внутри окна — оба тона в обоих ушах, модуляция на |beat| (§4.2-2).

Нулевое перекрытие убирает оба класса сразу и — что важнее — **не зависит от
вердикта**: решение больше нельзя принять ошибочно. `logCoherenceVerdict`
остался диагностикой (тег `когерентность:`), чтобы задним числом видеть, чем
грозил бы кроссфейд на этом жесте.

Цена — «приседание» вместо смешения: 125 мс вниз, стык на нулевой амплитуде,
125 мс вверх. Слышимая длина та же, что у кроссфейда (250 мс), характер другой,
и это различие физически неустранимо.

### Маркеры перехода (сборка 09:53)

```
beginSilentSwitch: spec#3 гаснет (125мс), spec#4 ждёт нуля (причина=SCRUB, сдвиг=…, elapsed=0мс)
stop spec#3: fade-out(EQUAL_POWER) cur=… dur=125мс (штатные 250мс, переопределение 125мс, onSilent=true)
stop spec#3: ТИШИНА — v=0.0 через 187мс от старта рампы, поднимаем NEXT     ← НОВЫЙ
startPendingSilentSwitch: SWAP по нулю — spec#4 поднимается (125мс, причина=SCRUB), перекрытия не было
```

Триада «гаснет → ТИШИНА → SWAP по нулю» — единственный маршрут; любое
смешение (старт NEXT до нуля огибающей) теперь дефект, а не выбор ветви.
Именно её и проверяют `dbgstorm.sh` и `expect_transition_order` в `dbgscrub.sh`.

### Что осталось открытым (пункты 1–2) и прогон dbgscrub (пункт 3)

**1. `settings`: 3 перехода при медиане 245 мс (окно 300 мс) — ИСПРАВЛЕНО
(вариант (а)+, с льготой для одиночного жеста).** Дефект был в том, что
`stormDetected` **сбрасывался на старте каждого перехода**, поэтому жест,
пришедший после релиза уходящего, получал только 150 мс и разыгрывал
переход почти сразу; при медиане 245 мс жесты попадали в оба режима
попеременно — отсюда 3 вместо 1–2.

Фикс в `BinauralStreamManager.kt` (`requestHandoff`, ~1149): флаг серии
выводится из **контекста на момент жеста**, а не из старта перехода:
`inFlight = settleAtMs > now || outgoing != null || pendingSilentSwitch != null`;
`stormDetected = inFlight`; `settleAtMs = now + if (stormDetected)
HANDOFF_STORM_EXTEND_MS(300) else HANDOFF_STORM_SETTLE_MS(150)`. Сброс на
старте перехода (`tryAdvanceQueue`) **удалён**. Изолированный жест
(окно истекло и ничего не в полёте) снимает флаг → 150 мс; любой жест внутри
активного окна либо при переходе в полёте держит 300 мс. Шторм настройки
теперь схлопывается в **≤2 перехода** (было 3).

Оговорка по измерению: `dbgstorm.sh` для `settings` по-прежнему выдаёт
5 переходов / 3 кластера (FAIL в сводке выше) — **это артефакт обвязки, а не
регрессия**. Латентность `am broadcast` внутри device-shell burst
(~150–250 мс на команду) сдвигает реальный интервал жеста в разреженную зону
(медиана 442–516 мс ≥ 300 мс), где проверка ждёт «≤ число кластеров» (3),
а не «≤2». Плотный случай (медиана < 300 мс → ≤2), который и чинит фикс,
обвязка надёжно не воспроизводит из-за той же латентности. Логика
коалесценции трассируется вручную: при плотном шторме `inFlight` истинно на
каждом жесте → флаг держится → окно 300 мс → схлопывание в ≤2.

**2. Сценарий `preset` не проверяет `PRESET_SWITCH`.** В коде эта причина
больше не порождается ниоткуда (`grep`: только константы `SETTINGS` и `SCRUB`
в `onSpecChanged`), поэтому `next` доходит до менеджера как SETTINGS, а
перезагрузка оси даёт ещё и SCRUB-реаллайнмент (`сдвиг=11410 с` → `4630 с` →
`0`). Счёт «доставлено по причине PRESET_SWITCH = 0» — честный: в этом
сценарии проверяется SETTINGS-путь, а не смена пресета. Переименовать
сценарий либо найти, куда делся `PRESET_SWITCH`.

**3. `dbgscrub.sh` V1–V9** на той же сборке — **58 PASS / 0 FAIL**: обе новые
проверки порядка (V1 скраб, V2 правка настройки) видят по одному переходу
`уходов=1, ТИШИНА=1, SWAP по нулю=1`. Старый `reject_log
"beginOverlapSwitch: SWAP"` был бы пустой проверкой (ветки нет), на его месте
теперь `expect_transition_order`.

## 4.5 Пятая волна: убрать коалесценцию и тишину (РЕАЛИЗОВАНО, релиз ~13:31)

### Задача (от пользователя)
«убери Коалесценция и тишину, длительность фейда 250 мс». Убрать
предварительную задержку (окно коалесценции 150/300 мс) и мёртвую паузу
между ногами «приседания», оставив слышимую длительность перехода 250 мс
(125 вниз + 125 вверх).

### Целевое поведение
- Жест запускает переход **немедленно** (без ожидания 150/300 мс).
- CURRENT гаснет 125 мс → **ровно на нуле** начинает расти NEXT (125 мс).
  Без зазора тишины, без перекрытия. Слышимый провал = непрерывный фейд
  через ноль, 250 мс.
- Серии жестов по-прежнему схлопываются в ≤2 перехода: очередь из одного
  слота (`PlaybackQueue`, latest-wins) держит только последнюю спеку, а
  страховка по `outgoing`/`pendingSilentSwitch` в `tryAdvanceQueue` не даёт
  поднять второй поток одновременно. Окно ожидания для этого больше не нужно
  (и без него серия не дробится, потому что конкурентный хэндофф всё равно
  запрещён).

### Точки правки (`BinauralStreamManager.kt`)
1. `requestHandoff` (~1143): удалить блок
   `val inFlight = …; stormDetected = inFlight; settleAtMs = now + if (stormDetected) HANDOFF_STORM_EXTEND_MS else HANDOFF_STORM_SETTLE_MS`.
   Заменить на `settleAtMs = 0L` (+ `stormDetected = false`). `tryAdvanceQueue`
   сразу видит `wait ≤ 0` и начинает переход.
2. `beginSilentSwitch` (~1371): после `old.stopWithSilentHook(...)` добавить
   `actor.postDelayed({ startPendingSilentSwitch() }, ZERO_OVERLAP_LEG_MS)` —
   NEXT стартует ровно на нуле, без ожидания хука тишины (убирает зазор
   10–25 мс). `onSilent = { startPendingSilentSwitch() }` оставить как
   идемпотентную страховку (`startPendingSilentSwitch` защищён по
   `pendingSilentSwitch`/`current`).
3. Константы `HANDOFF_STORM_SETTLE_MS`, `HANDOFF_STORM_EXTEND_MS`,
   `ZERO_OVERLAP_LEG_MS`, `TRANSITION_FADE_MS` — **НЕ менять** (фейд 250 мс
   сохранён). `stormDetected` становится inert (всегда false); блок
   `wait > 0` в `tryAdvanceQueue` теперь недостижим (оставлен как is).

### Риски / что проверить
- **Нет ли настоящего перекрытия**: NEXT стартует на нуле амплитуды CURRENT
  (`rampMs == ZERO_OVERLAP_LEG_MS`), значит overlap отсутствует — дефекты
  Wave 4 (когерентный провал / перестановка ушей) НЕ возвращаются.
- **Серия**: `dbgstorm` scrub/preset — переходов по-прежнему ≤2 на серию,
  `ТИШИНА` остаётся на нуле (max v≈0.0), перекрытия нет.
- **Зазор**: лог-маркер `startPendingSilentSwitch: SWAP по нулю` теперь идёт
  сразу за `гаснет`, без паузы; весь провал `гаснет→SWAP` сжимается с
  164–237 мс к ~125 мс (одно плечо).

### Верификация
- `bash tools/dbgscrub.sh` (V1–V9: ожидаем 58 PASS/0 FAIL).
- `bash tools/dbgstorm.sh` (ожидаем: scrub/preset PASS; settings — артефакт
  обвязки как в §4.4-1, не регрессия).
- Smoke: запуск релиза, переход слышен как плавный 250-мс фейд без паузы.

```bash
DEVICE=192.168.199.165:5555 bash tools/dbgstorm.sh            # scrub + preset + settings
DEVICE=… N=20 GAP=0.08 bash tools/dbgstorm.sh scrub settings  # плотнее/длиннее
```

Инструмент сам выходит в RUNNING, ждёт устаканивания старта (4 с — иначе в окно
попадают стартовые SETTINGS-пуши ViewModel и загрузка пресета, и подсчёт
теряет смысл), гонит серию ОДНИМ `adb shell` (пауза между жестами внутри
device-shell; `am broadcast` стоит ~150–250 мс, так что реальный интервал выше
заданного — при `GAP=0.12` фактический ~0.17–0.25 с), снимает лог синхронным
дампом и печатает: число `requestHandoff` (с разбивкой по причине), число
переходов этой причины, порядок «гаснет → ТИШИНА → SWAP по нулю» с нарушениями,
гистограмму вердиктов `когерентность:` и разброс Δf, ритм серии (медиану
интервала по таймстемпам и число кластеров), отказы `prepare()`, разрывы,
принудительные снятия рампы, сторож, underrun-дельту и `pkstat` до/после.

Что изменилось в четвёртой волне:

* счётчик `beginOverlapSwitch: SWAP` заменён проверкой «перекрытия нет» (ветка
  удалена, любое появление — дефект);
* вердикты переведены с `isCoherentHandoff:` на тег `когерентность:`;
* жесты и переходы считаются **по причине** (`reason=…` в `requestHandoff`,
  `причина=…` в `beginSilentSwitch`/`SWAP по нулю`): иначе посторонние
  SETTINGS-пуши ViewModel раздувают счётчик сценария;
* проверка «переходов ≤ 2» **условна**: ритм серии мерится по таймстемпам, и
  схлопывание требуется только если серия реально плотнее окна
  (`STORM_WINDOW_MS`, по умолчанию 300). Для редкой серии требуется
  «≤ число кластеров» (жест продлевает окно ⟺ интервал < окна).

Ловушки, уже закрывшиеся багами первых версий скрипта (не повторять):
`grep -c` печатает «0» И выходит с кодом 1 — `|| echo 0` добавлял вторую
строку и валил все проверки на «нет совпадений»; лог сценария надо чистить
ПОСЛЕ устаканивания старта, а не до; при одном пресете на устройстве
сценарий `preset` сам дублирует активный (`dup`); `set -- $ord` внутри
`report()` съедает позиционные аргументы — метку проверки надо сохранить
в переменную ДО `set --`.
