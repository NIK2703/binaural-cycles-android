# Второй проход: энергопотребление UI и фоновой работы

Дата: 2026-08-30. Анализ + внедрены правки U1 (все три подхода) и U2 (см. §6).

## 0. Отправная точка

Первый проход (`battery_hotpath_audit_2026-08-30.md`) замером показал, что
нативный путь генерации звука стоит **1.03 с CPU/час** — 0.1–0.2 % энергии
сессии. Оптимизировать DSP дальше некуда. Поэтому этот проход искал в других
местах: **UI при включённом экране** и **любая периодическая работа при
выключенном**.

И главное нашлось именно там: **перерисовка списка пресетов стоит в 25–50 раз
больше CPU, чем весь аудиодвижок.**

## 1. 🔴 U1. Список пресетов перерисовывает ~7 мини-графиков каждую секунду — в том числе когда ничего не играет

### Цепочка

1. `BinauralPlaybackService.kt:757` — джоб 1 Гц. Обновление времени **НЕ
   защищено флагом воспроизведения**:
   ```kotlin
   delay(1000)
   if (!isScreenInteractive()) continue
   audioEngine?.updateCurrentFrequencies()
   audioEngine?.currentTimeOfDaySeconds?.value?.let { _currentTimeOfDaySeconds.value = it }
   if (_isPlaying.value || _debugTimeEnabled.value) {   // ← только частоты
   ```
   То есть время тикает каждую секунду **даже на паузе**.

2. `BinauralViewModel.kt:435-453` — `combine(5).distinctUntilChanged()`;
   `currentTimeOfDaySeconds` (строка 440) входит в combine и честно меняется
   каждую секунду, поэтому `distinctUntilChanged()` не помогает.

3. `PresetListScreen.kt:132` — чтение `telemetry.currentTime` **внутри лямбды
   `items`**:
   ```kotlin
   items(uiState.presets, key = { it.id }) { preset ->
       val (lowerFreq, upperFreq) = preset.getChannelFrequenciesAt(telemetry.currentTime)
   ```
   Это прямо противоречит комментарию на строках 49–50 того же файла:
   > «Отдельный поток телеметрии: текущее время и флаг воспроизведения меняются
   > каждую секунду и **не должны перекомпоновывать весь список пресетов**».

   Намерение заявлено верно, реализация его нарушает.

4. `PresetListScreen.kt:234` — каждая видимая карточка содержит
   `MiniFrequencyGraph`. Карточка 140 dp + отступ 8 dp ⇒ **~7 одновременно
   скомпонованных** на типичном экране.

5. `MiniFrequencyGraph.kt:152` — **один-единственный** `drawBehind`, который
   рисует сетку + 5 путей + N кружков + N+2 подписи **и** указатель. Проверка
   `isPlaying` стоит **внутри** (строка 423), поэтому чтение `currentTime` на
   строке 164 инвалидирует весь лямбда-блок ⇒ **полная перерисовка**.

### Что именно перерисовывается (на карточку, в секунду)

| Операция | Строка | Аллокации |
|---|---|---|
| 5 × `drawPath` | 340, 349 | `PathEffect.dashPathEffect(floatArrayOf(6f,6f))` — `FloatArray` + объект эффекта **на каждый вызов** |
| ~10 × `drawCircle` | 368 | `primaryColor.copy(alpha = 0.5f)` на каждую точку |
| ~12 × `nativeCanvas.drawText` | 386, 408, 415 | `"%.0f".format(...)` |
| сетка | — | — |

Геометрия при этом закэширована корректно (`MiniGraphCache` за `remember`,
строки 115–143) — `Path` не пересчитывается. Проблема не в расчётах, а в
**растеризации, которая повторяется целиком**.

### Два отягчающих обстоятельства

**А. Шесть карточек из семи рисуют пиксель-в-пиксель ту же картинку.**
`PresetListScreen.kt:142`: `isPlaying = isActivePreset && telemetry.isPlaying`.
У неактивных карточек `isPlaying == false`, указатель не рисуется (строка 423),
и результат каждой перерисовки **идентичен предыдущему**. Чистые потери.

**Б. Даже у активной карточки движение невидимо.** Указатель сдвигается на
1/86400 ширины графика в секунду ≈ **0.0125 px/с** на карточке 1080 px, то есть
**80 секунд на один пиксель**. Ежесекундная перерисовка даёт ноль видимых
изменений.

### Оценка стоимости

`drawText` ≈ 20–50 мкс, `drawPath` по полилинии ≈ 50–200 мкс, плюс запись и
воспроизведение DisplayList. Оценочно **1–2 мс на карточку на перерисовку**,
× 7 карточек = **7–14 мс/с**, то есть **25–50 с CPU/час** при открытом списке.

| | CPU/час |
|---|---|
| Список пресетов (оценка) | **25–50 с** |
| Весь аудиодвижок (замер) | 1.03 с |

**Перерисовка списка дороже генерации звука в 25–50 раз.** Оценка, не замер
(рендер Compose на хосте не измерить), но порядок величины надёжен: он задан
десятками вызовов растеризации в секунду, а не их ценой.

### Решения (по убыванию цена/риск)

1. **Квантовать время.** Округлять `currentTime` до 30–60 с. Проверено: ни один
   экран **не показывает секунды** — `currentTime` используется только в
   `timeToX()` (позиция указателя) и в `getChannelFrequenciesAt()` (строки
   132, 435). При 60 с указатель сдвигается на 0.07 % ширины — неразличимо.
   Срезает выбросы телеметрии в 30–60 раз и попутно лечит U3. **Нулевое
   изменение функциональности.**
2. **Не передавать время неактивным карточкам.** Передавать `currentTime`
   только для `isActivePreset`, для остальных — константу. Тогда 6 из 7
   карточек вообще не инвалидируются. Никакого визуального эффекта: указатель у
   них и так не рисуется.
3. **Разделить `MiniFrequencyGraph` на статичный и динамичный `drawBehind`** —
   по образцу `FrequencyGraph.kt:365-381`, где это уже сделано правильно.
   Убирает сетку, пути, кружки и подписи из ежесекундного пути.

Рекомендую (1) + (2): вместе дают ~порядок, без риска для внешнего вида.
(3) — отдельно, как выравнивание с уже правильным `FrequencyGraph`.

## 2. 🟡 U2. `isScreenInteractive()` — binder-IPC каждую секунду

Добавленный в первом проходе guard (см. §7.3 первого отчёта) предотвращает
*работу* джоба, но не *пробуждение*: `pm.isInteractive` — это вызов в
`system_server`.

```kotlin
private fun isScreenInteractive(): Boolean {
    val pm = getSystemService(Context.POWER_SERVICE) as? PowerManager
    return pm?.isInteractive ?: true      // ← IPC при каждом вызове
}
```

**Важно о масштабе:** в нормальном потоке джоб останавливается
`onAppBackground()` из `MainActivity.onPause()`, так что это **не** 3600
IPC/час постоянно. Счёт идёт только в сценарии, который guard и закрывает —
sticky-сервис пересоздан в фоне, `onAppBackground()` не приходит. Там цикл
крутится 1 Гц, и каждая итерация — это IPC, после которого не делается ничего.

**Решение:** зарегистрировать `ACTION_SCREEN_ON/OFF` и останавливать джоб
полностью, а не опрашивать состояние. Минимум — закэшировать экземпляр
`PowerManager` (убрать повторный `getSystemService`).

## 3. 🟡 U3. `PresetEditScreen` читает телеметрию в non-lazy `Column`

`PresetEditScreen.kt:225-235` читает `currentCarrierFrequency`,
`currentBeatFrequency`, `isPlaying`, `currentTime` в теле экрана, который
является `Column` с `verticalScroll` (строка 201) — не `LazyColumn`.

**Серьёзность ниже, чем у U1**: Compose пропускает дочерние элементы с
неизменившимися входами, а тяжёлая работа `FrequencyGraph` спрятана в
`remember` и `drawBehind`. Платится повторное исполнение тела экрана 1 Гц.

Лечится бесплатно квантованием времени из U1.

## 5. Честное резюме

Энергия сессии, которой можно управлять, после первого прохода практически
исчерпана. Остальное делится на:

- **Неизменяемое:** аудиотракт (кодек, DMA, микшер) — плата за непрерывное
  воспроизведение; экран, когда он включён.
- **Изменяемое:** U1. Это крупнейший управляемый расход CPU в приложении, и он
  больше всего, что было сэкономлено в DSP. Но по отношению к экрану
  (200–500 мВт при включённом) это всё равно ~1–2 %.

То есть **U1 — это в первую очередь выигрыш в плавности (7–14 мс/с на UI-потоке
⇒ дропаные кадры при прокрутке списка) и только во вторую — в батарее.** Это
стоит исправить, но важно не продавать это как экономию заряда.

## 6. ✅ Что внедрено (U1 + U2)

### U1 — квантование времени + разделение слоёв (все три подхода из §1)

**Корень проблемы устранён в источнике.** В
`BinauralViewModel.observePlaybackState()` время суток квантуется до 60 с
**до** попадания в `combine(5).distinctUntilChanged()`:

```kotlin
) { playing, beat, carrier, swapped, timeSeconds ->
    val quantizedSeconds = (timeSeconds / 60) * 60
    PlaybackTelemetry(
        ...,
        currentTime = LocalTime.fromSecondOfDay(quantizedSeconds.coerceIn(0, 86399))
    )
}
```

Следствие: `telemetry` теперь эмитит **~1 раз в минуту вместо ~1 раза в секунду**
(снижение частоты перекомпоновки примерно в 60 раз). Ни один экран не
показывает секунды, так что функциональность не меняется.

**Подход (2) — неактивные карточки получают константу.** В `PresetListScreen`
`items`-лямбда теперь передаёт «живые» время/частоты только активной карточке,
остальным — `INACTIVE_CARD_TIME = LocalTime(12, 0)` и нулевые частоты. Compose
**пропускает перекомпоновку 6 из 7 карточек** целиком (у них входы не меняются).

**Подход (3) — разделение `MiniFrequencyGraph` на статичный и динамичный слой.**
Вместо одного `drawBehind`, рисующего сетку + 5 путей + кружки + подписи + указатель
целиком каждый тик, теперь:
- `drawWithCache { onDrawBehind { drawCachedGeometry(..., drawIndicatorOnly = false) } }`
  — статичная часть (сетка, пути, точки, подписи) кэшируется по `size`;
- второй `drawBehind { if (isPlaying) drawCachedGeometry(..., drawIndicatorOnly = true) }`
  — перерисовывается только указатель.

`drawIndicatorOnly` добавлен в сигнатуру `drawCachedGeometry` со значением по
умолчанию `false`, поэтому все существующие вызовы остаются валидными.

**Отладочный слайдер не пострадал.** Квантуется `telemetry.currentTime` (используется
списком/редактором), но отладочная панель времени получает **отдельный сырой поток**
`BinauralViewModel.debugCurrentTime` (от `BinauralPlaybackService.currentTimeOfDaySeconds`,
посекундно). `DebugTimeControlPanel` перенаправлен на него. Квантование не загачено
на `BuildConfig.DEBUG` — оно применяется во всех сборках, отладочный слайдер
выделен именно ради сохранения своей посекундной точности.

### U2 — кэширование состояния экрана через `ACTION_SCREEN_ON/OFF`

`isScreenInteractive()` больше не делает binder-IPC `pm.isInteractive` каждую
секунду. В `BinauralPlaybackService` добавлены:
- поля `screenStateReceiver: BroadcastReceiver?` и `isScreenOn: Boolean = true`;
- `registerScreenStateReceiver()` — инициализирует `isScreenOn` из
  `PowerManager.isInteractive` и регистрирует `ACTION_SCREEN_ON`/`ACTION_SCREEN_OFF`
  (с `Context.RECEIVER_NOT_EXPORTED` на TIRAMISU+ через `VERSION.SDK_INT`);
- `unregisterScreenStateReceiver()` — `try/catch`, зеркалит `unregisterNoisyAudioReceiver`;
- `isScreenInteractive(): Boolean = isScreenOn` (чистое чтение поля).

Регистрация в `onCreate` после `registerNoisyAudioReceiver()`, отмена в `onDestroy`
после `unregisterNoisyAudioReceiver()`. В нормальном потоке джоб и так
останавливается `onAppBackground()`, так что реальный выигрыш — только в сценарии
sticky-сервиса, пересозданного в фоне (устраняет ~1 IPC/с впустую).

### U3

Закрыт бесплатно квантованием времени (§1.1): `PresetEditScreen` читает телеметрию в
теле non-lazy `Column`, но теперь входы меняются ~1/мин вместо ~1/с.

### Проверка

- `:app:compileDebugKotlin` + `:core:audio:compileDebugKotlin` + `:core:audio:externalNativeBuildDebug`
  — **BUILD SUCCESSFUL** (Kotlin + NDK, офлайн-сборка, без изменений C++).
- Предупреждения только pre-existing (deprecation `Icons.Filled.*`, opt-in
  аннотаций) — к правкам не относятся.

| Эмитов телеметрии | ~1/с | ~1/мин (–~60×) |
