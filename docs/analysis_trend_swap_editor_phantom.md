# Фантомные смены каналов в TREND-режиме на кривой с постоянными биениями

**Статус:** РАССЛЕДОВАНИЕ ЗАВЕРШЕНО, ПРИЧИНА НАЙДЕНА И ИСПРАВЛЕНА.
**Дата:** 2026-09-06
**Сборка:** debug (`com.binauralcycles.debug`), устройство POCO 23049PCD8G `192.168.199.165:5555`.

---

## 1. Симптом (со слов пользователя)

При включённой тенденциальной смене каналов (`ChannelSwapMode.TREND`):

1. Открыть редактор предустановок на **новой** (несохранённой) предустановке.
2. Запустить её воспроизведение (кнопка Play в редакторе → черновик, `draftSounding`).
3. **Добавить вторую точку** графика — после этого каналы начинают меняться местами
   «каждые несколько секунд», **вне зависимости от нарисованного графика**.
4. Если эту же предустановку **сохранить** и слушать сохранённую — смена каналов
   идёт **правильно**, по расписанию экстремумов кривой.

## 2. КОРЕНЬ ПРИЧИНЫ: шум float32 в Δbeat, а не путь редактора

Причина **не в редакторе и не в черновике** — путь редактора лишь делает баг
заметным, потому что каждое движение точки пересобирает поток.

### 2.1 Механизм

Тренд считается по частоте биений:

```
Δbeat(t) = beat(t + 60с) − beat(t − 60с),   beat = upper − lower
```

Каналы (`upper`/`lower`) интерполируются **порознь**, и `beat` получается
вычитанием двух близких величин. При **постоянной** частоте биений (обе точки
имеют одинаковый `beat`) теоретически Δbeat ≡ 0, но на float32 остаётся
«дребезг» порядка **1e-4 Гц**: каналы несут 200…600 Гц, относительная точность
float32 ~1e-7.

`computeTrendCrossings()` (`Interpolation.h`) искала нули грубой сеткой и
отбрасывала только **точные** нули:

```cpp
const float d = sampleAt(i);
if (d == 0.0f) continue;           // ← дребезг 1e-4 через эту проверку проходил
if (lastSignedIdx >= 0 && ((d > 0.0f) != (lastSign > 0.0f))) pushCrossing(...);
```

Дребезг знакопеременный ⇒ детектор видел смену знака почти на каждом узле
сетки (шаг 5 с) ⇒ **5112 «экстремумов» за сутки** там, где биения вообще
не меняются. Проходя мимо каждого, планировщик исполняет ритуал смены
раскладки — отсюда «каналы меняются каждые несколько секунд».

Второй, сопутствующий источник: поправка фазы в начале суток
(`midnightPhase`, `ChannelLayout.h:148`) читала знак `trendBeatDeltaAt(curve, 0)`.
На плато это тоже шум ⇒ раскладка после КАЖДОЙ пересборки потока (а в
редакторе — после каждого движения точки) была случайной.

### 2.2 Почему «вторая точка» — именно порог

- 1 точка → `computeTrendCrossings` выходит сразу (`points.size() < 2`) → свапов нет.
- 2 точки с одинаковым beat → плато Δbeat → thousands of phantom crossings.

### 2.3 Почему в редакторе это гарантировано

`FrequencyGraph.kt` (double-tap) берёт частоту биений новой точки
**интерполяцией существующей кривой**:

```kotlin
val interpolatedBeat = if (displayPoints.size >= 2) {
    val (leftFreq, rightFreq) = Interpolation.interpolateChannels(...)
    kotlin.math.round(rightFreq - leftFreq)
} else {
    displayPoints.firstOrNull()?.beatFrequency ?: 0.0f   // ← у нового пресета 16 Гц
}
```

У нового пресета одна точка: добавленная второй точкой наследует тот же
`beat`, что и звучит ⇒ плато ⇒ фантом. Пользователь потом правит несущую
(график «нарисован»), а `beat` остаётся константой — отсюда «вне зависимости
от графика».

### 2.4 Почему «после сохранения — правильно» — наблюдение обманчиво

`dsave` пушит конфиг с **тем же объектом кривой**, менеджер его
дедуплицирует (`BinauralStreamManager.updateConfig`), хэндоффа нет, и движок
продолжает работать со **старым** списком пересечений. Замер это подтвердил:
переключение на другой пресет и возврат на сохранённый «Фантом» даёт тот же
`nCross=5112`. То есть сохранённый пресет **тоже** был сломан; разница в том,
что вне редактора нет пересборок потока, и пользователь не слышит
мгновенных случайных переворотов раскладки.

## 3. Замеры (до исправления)

Диагностика `SWAPCFG` (`BinauralEngine::setConfig`, тег logcat, только debug):

```

  pts=1 valid=1 nCross=0 beat0=0.0000 d=[0 … 0] cross=[]

2 точки, ОДИНАКОВЫЙ beat (12:00 c200/b16 + 14:00 c300/b16, MONOTONE):
  pts=2 valid=1 nCross=5112 beat0=0.0000
  d(0,2h..22h)=[0.0000 -0.0000 0.0000 0.0000 0.0000 0.0000 0.0000 0.0000 0.0000 0.0001 -0.0000 -0.0000]
  cross=[12.70P 44.79T 58.75P 69.48T 70.21P 94.17T …]      ← каждые 5–30 с
```

Опрос знака биений (`swapwatch 100`, тег `SWAPWATCH`) на той же кривой:

```

СМЕНА #1: знак=-1 beat=-16.000 (t=5025 мс)
```

## 4. Исправление

### 4.1 Мёртвая зона трендовой дельты

`Config.h`:

```cpp
constexpr float TREND_DELTA_EPSILON_HZ = 1e-3f;        // абсолютный пол
constexpr float TREND_DELTA_RELATIVE_EPSILON = 1e-6f;  // доля от частоты канала
```

`Interpolation.h` — масштабируемый порог (шум растёт вместе с несущей):

```cpp
inline float trendDeltaEpsilonHz(const FrequencyCurve& curve) {
    float maxChannelHz = 0.0f;
    for (const FrequencyPoint& p : curve.points)
        maxChannelHz = std::max(maxChannelHz, std::fabs(p.carrierFrequency)
                                            + 0.5f * std::fabs(p.beatFrequency));
    return std::max(TREND_DELTA_EPSILON_HZ, TREND_DELTA_RELATIVE_EPSILON * maxChannelHz);
}
```

`computeTrendCrossings()`: узел внутри мёртвой зоны знак не обновляет —
ровно как прежний точный ноль, только теперь в зону попадает и дребезг:

```cpp
if (std::fabs(d) <= deltaEps) continue;
```

`refineZero(..., eps)`: бисекция останавливается, когда середина попадает
в мёртвую зону (уточнять шум бессмысленно).

`ChannelLayout.h` (`midnightPhase`): та же зона, чтобы знак шума не решал,
перевёрнута ли раскладка в начале суток:

```cpp
if (delta0 < -trendDeltaEpsilonHz(cfg.curve)) swapped = !swapped;
```

### 4.2 Обоснование порога

| Величина | Значение |
|---|---|
| Шум Δbeat на плато (замер) | ≤ 1e-4 Гц |
| Порог (`eps`) | 1e-3 Гц (для несущей ≤ 1000 Гц) |
| Реальный суточный ход Δbeat | 0.01…0.16 Гц |

Запас: ×10 сверху от шума и ×10 снизу от сигнала.

### 4.3 Регрессионный тест

`BufferPackageTest.cpp::TrendSwapPureTest.ConstantBeatHasNoTrendCrossings` —
две точки с одинаковым `beat` ⇒ `trendCrossings` пуст, раскладка одинакова
в любой момент суток. Тесты собираются отдельным CMake (`AUDIO_TEST_BUILD`,
нужен хост-GTest), в Android-сборку не входят.

## 6. Инструментарий (оставлен в debug-сборке)

Команды приёмника `DebugCommandExecutor` — headless-зеркало пути редактора,
чтобы не тыкать вслепую в Compose-график:

| Команда | Что делает (зеркало `BinauralViewModel`) |
|---|---|
| `dn` | `FrequencyCurve.newPresetCurve()` — черновик нового пресета |
| `dstart` | `startDraft()`: id `__draft__`, `updateConfig(buildPlaybackConfig(…))`, `play()` |
| `dadd <сек\|HH:MM> <н> <б>` | `addEditingPoint` + `updateEditingCurve`: кламп, сортировка, буфер 60 с, `updateFrequencyCurve` |
| `drelax <on\|off>` | режим расслабления черновика (виртуальные точки) |
| `dsave <имя>` | `createPreset(activate = true)` |
| `dshow` | черновик + настройки свапа/расслабления |
| `dstop` | остановка |
| `swapwatch <сек>` | опрос знака `currentBeatFrequency` каждые 200 мс, лог `SWAPWATCH` |

Диагностика `SWAPCFG` в `BinauralEngine::setConfig()` оставлена, но **за
`AUDIO_DEBUG`** (раньше была за `ANDROID` и лилась бы в release).

Грабли CLI (recurring): `--es cmd` без вложенных кавычек; логи только в
`.debug`; `adb` надо переподключать в каждом вызове; `logcat -G 16M` → `-c`
→ сценарий → `-d`.

## 7. Хронология

1. **Статика путей** `startDraft` / `updateAudioConfig` / `createPreset` —
   гипотеза «черновик и сохранённый пушат разные конфиги» **опровергнута**
   (единый `buildPlaybackConfig`, один и тот же объект кривой).
2. **Нативный детектор на чистых пресетах** (импорт T1/T2) — корректен:
   1 точка → 0 пересечений, 2 точки с разными биениями → 2.
3. **Headless-команды редактора** (`dn/dstart/dadd/…` + `swapwatch`) — чтобы
   не тыкать в график.
4. **Воспроизведение**: `dadd` с тем же `beat`, что и у первой точки (ровно
   то, что делает double-tap) → `nCross=5112`, 6 переворотов за 65 с.
5. **Сравнение draft vs saved** — сохранённый пресет даёт тот же
   `nCross=5112`: виноват не путь редактора, а кривая.
6. **Исправление** — мёртвая зона Δbeat + поправка фазы; проверка
   (фантом = 0, реальные тренды = без изменений, положительный контроль
   проходит).
7. Регрессионный тест в `BufferPackageTest.cpp`; диагностика `SWAPCFG`
   переведена под `AUDIO_DEBUG`.
