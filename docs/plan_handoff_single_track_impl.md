# Детализация реализации: `retune()` на одном треке

Дополнение к `docs/plan_handoff_single_track.md`. Статус: **ждёт утверждения**,
код не тронут. Все номера строк — на состояние репозитория от 2026-09-06.

---

## 0. Что выяснилось при детализации (и что меняет план)

| Было в плане (§11) | Стало |
|---|---|
| Риск 1: `setConfig` на живой движок запрещён инвариантом потоков | **Снят.** Писатель — это и есть аудио-поток, то есть ровно та нить, которой инвариант разрешает трогать `m_generator` и `m_config`. Конфиг подаётся через атомарный слот, писатель применяет его в своей точке цикла. Новой синхронизации не нужно. |
| Риск 2: перемотка фазы на слышимую позицию | **Снят, и не решением, а отсутствием необходимости.** Переход идёт через ноль: уходящий погашен доказуемо, приходящий рендерится с подъёмом из нуля. Фаза в точке стыка безразлична — щелчка нет при ЛЮБОЙ фазе. `getCurrentPhases`/`setPhases`/`captureContinuity`/`enrichForContinuity` удаляются без замены. |
| Риск 4: `flush()` + `play()` — надёжность | **Снят частично.** Механизм уже существует и обкатан: `applyResumeSeek()` (`BinauralStreamImpl.kt:1546`) делает ровно это при возобновлении после паузы. Остаётся только случай отказа `flush()`. |
| — | **НОВЫЙ РИСК (§6): стоимость регенерации пакета.** Пакет — десятки минут; полная регенерация ≈1 с CPU и растянула бы провал до секунды. Решение: регенерировать ограниченный пакет. |

**Главное следствие:** реализация не строит новый механизм, а переиспользует
уже существующий путь «пауза → перемотка → flush → наполнение → play». Нового
кода — один флаг, один слот конфига и одна ветка в цикле писателя.

## 1. Инвариант владения (не нарушать)

```
нить актора   : AudioTrack (pause/flush/play), VolumeShaper, флаги состояния,
                расписание таймеров
нить писателя : directBuffer, курсор пакета, generatedFrames, frameBias,
                ВСЕ вызовы движка (generateBufferDirect / setConfig /
                setCurveTimeSeconds / setPhases)
```

Правило: **движок трогает только писатель.** Актор передаёт намерение через
атомарный слот, писатель исполняет. Это не новое ограничение, а ровно то, что
уже написано в `BinauralEngine.h:264-279`.

## 2. Новое состояние в `BinauralStreamImpl`

```kotlin
// Задание на перенастройку. Пишет актор, читает и обнуляет писатель.
private val pendingRetune = AtomicReference<PlaybackSpec?>(null)
// Провал в полёте: между «наложили спад» и «play() после перезаполнения».
@Volatile private var retuning = false
// Цель перехода на оси времени суток (сек), для варианта с перемоткой.
private val pendingSeekTime = AtomicLong(NO_SEEK)
// Спек больше не неизменен: он меняется при retune.
@Volatile var spec: PlaybackSpec   // было val
```

`spec` становится мутабельным — это механическая правка, но она затрагивает
логи (`spec.serial`) и `BinauralStreamManager` (сравнения, `sessionSpec`).
Отдельно оговаривается: **частота дискретизации и формат каналов меняться не
могут** — иначе трек надо пересоздавать (§7).

## 3. `retune(spec)`: два сценария

### 3.1. Стоим на паузе — провал не нужен вообще

Пауза уже означает тишину и припаркованного писателя. Значит:

```
pendingRetune.set(spec); wakeWriter()      // всё
```

Писатель применит конфиг и снова припаркуется. Ни таймеров, ни шейпера, ни
`flush`. **Это бесплатный и самый частый случай** (пользователь листает
пресеты на паузе), и он полностью убирает провал из UX.

### 3.2. Играем — провал по построению

```
t0
  актор: shaper.replace(рампа: cur → 0 за F)          // F = 125 мс
         retuning = true
         pendingRetune.set(spec)  (или pendingSeekTime, см. §5)
         track.pause()            // ЕДИНСТВЕННЫЙ способ прервать write(WRITE_BLOCKING)
         actor.postDelayed(::finishRetune, F + M)     // M = 60 мс, статическая граница

t0 + F + M
  актор: wakeWriter()             // писатель исполнит retune и встанет в лачок

писатель (в своей точке цикла):
  1. spec = pendingRetune.getAndSet(null)
  2. engine.setConfig(spec.config)                    // легально: писатель = аудио-нить
  3. engine.setCurveTimeSeconds(target)               // сбрасывает total, пересаживает UI-якорь
  4. kotlin: generatedFrames = 0; frameBias.set(-head) // перезапуск оси кадра
  5. track.flush()
       неудача → прекратить, откатиться на recreateTrack() (§7)
  6. buf.clear(); generated = engine.generateBufferDirect(buf, retuneSamples)
     packetBytes = generated*8; offset = 0            // регенерация ОГРАНИЧЕННОЙ длины (§6)
  7. записать чанк в кольцо
  8. сигнал «готово» (лачок); retuning = false

актор (по лачку):
  shaper.replace(рампа: 0 → spec.volume за F)
  track.play()
```

**Почему `F + M` — это гарантия, а не измерение.** Рампа шейпера идёт в
масштабе реального времени микшера. К моменту `t0 + F + M` она либо дошла до
нуля и удерживает его, либо микшер подставлял тишину (underrun) — что тоже ноль.
`M` покрывает только задержку старта рампы (квант микшера). Ошибка в большую
сторону стоит нескольких десятков мс лишней тишины; в меньшую — невозможна при
`M` ≥ кванта. **Обратной связи нет.**

**Почему `track.pause()` в t0, а не в `t0+F+M`.** Писатель может быть
заблокирован в `write()` на несколько секунд; прервать его можно только паузой.
К моменту паузы выход уже на нуле, поэтому пауза неслышна.

## 4. Изменения в `writerLoop` (точечно)

Текущий цикл: `while (lifecycleRef.get() == StreamLifecycle.PLAYING)` —
`BinauralStreamImpl.kt:2150`. Добавляется **одна ветка в самое начало**, до
`if (paused)` (строка 2160):

```kotlin
if (retuning) { doRetuneOnWriter(); continue }
```

`doRetuneOnWriter()` — новый приватный метод рядом с `applyResumeSeek()`;
содержит шаги 1–8 из §3.2. Он **не** паркует писателя и **не** снимает
`lifecycle`: трек остаётся `PLAYING`, просто стоит на паузе.

Вторая правка — ветка ошибки записи (строка 2230): после проверки `paused`
добавить

```kotlin
if (retuning) continue     // пауза поставлена нами ради перехода, не ошибка
```

Третья правка — готовность к `play()`. Существующий `prefillUntilPlay`
(строка 2261) ждёт `inRing >= prefillFrames`, где `prefillFrames` считается от
полного кольца. После `retune` в наличии только ограниченный пакет (§6), поэтому
цель надо ограничить доступным:

```kotlin
val prefillGoal = minOf(prefillFrames, availableFrames)
```

Всё. Остальной цикл не меняется.

## 5. Скраб отдельно: перемотка вместо регенерации

Скраб в пределах того же пресета меняет **только позицию на кривой**, а не
конфиг. Такой пакет уже посчитан: достаточно переставить курсор — ровно то, что
делает `applyResumeSeek()` при возобновлении.

Нужен обобщённый вариант планировщика: сегодня `planResumeSeek(deltaSeconds)`
(строка 1499) переводит Δ секунд в кадры через окно между слышимой позицией и
фронтиром:

```kotlin
val skipFrames = (deltaSeconds / window * unplayed.toFloat()).toLong()
```

Для скраба цель задаётся абсолютным временем суток `T`, поэтому та же формула с
`(T − a0)` вместо `Δ`. То есть `planResumeSeek` обобщается до
`planSeekToTime(targetTimeOfDay)` без новой математики.

**Правило маршрутизации:**

| Запрос | Действие |
|---|---|
| тот же пресет, цель внутри окна `[a0, фронтир]` | перемотка курсора, конфиг не трогаем |
| другой пресет | `setConfig` + регенерация |
| тот же пресет, цель ВНЕ окна | регенерация |
| изменилась частота дискретизации / формат | `recreateTrack()` (§7) |

## 6. НОВЫЙ РИСК: стоимость регенерации пакета

Замер из комментариев в коде: **1.02 с CPU на час звука**, то есть полная
регенерация пакета в десятки минут занимает порядка секунды. Если регенерировать
весь интервал внутри провала, провал растянется до секунды — недопустимо.

**Решение — ограниченный пакет перехода:**

```kotlin
private const val RETUNE_PACKET_SECONDS = 30
```

30 с при 48 кГц стерео float — 11.5 МБ и ≈8.5 мс CPU. Этого хватает, чтобы
наполнить кольцо (5.5–10 с) и сыграть сразу, а полный интервал писатель
дорастит на следующем витке существующим `maybeGrowPacketBuffer()`.

Разбор подряд: писатель пишет 30-секундный пакет в кольцо быстрее реального
времени, сразу же видит `offset >= packetBytes` и на следующем витке
регенерирует полный интервал. Регенерация начинается **сразу после записи**, а
не через 30 с, поэтому кольцо не успевает опустеть — underrun не возникает. Это
тот же порядок, что сегодня обеспечивает `STARTUP_PACKET_SECONDS = 2` при
старте нового потока.

Побочный эффект: сразу после `retune` эффективный запас до underrun равен
глубине кольца, а не длине пакета — как и при старте сегодня. Временное участие
писателя до доращивания пакета — приемлемо и само рассосётся.

## 7. Что остаётся от старого пути: `recreateTrack()`

Создание нового AudioTrack остаётся законным **только** в трёх случаях:

1. смена устройства вывода / потеря фокуса с переходом на другое устройство;
2. изменилась частота дискретизации или формат каналов;
3. **`flush()` вернул ошибку** — деградация, при которой старое содержимое
   осталось в кольце и прозвучало бы после снятия провала.

В случаях 2 и 3 допустимо то же поведение, что и сегодня (последовательный
хэндофф с разрывом ~100–200 мс): это редкий путь, а не основной. Он сохраняется
как `recreateTrack()` — по сути нынешний `beginHandoffSequential`, но без
обвязки «тишина/когерентность».

## 8. Краевые случаи

| Сценарий | Поведение | За счёт чего |
|---|---|---|
| Пользователь нажал паузу во время провала | провал отменяется, трек остаётся на паузе, конфиг применится при возобновлении | `retuning` снимается в `pause()`, задание остаётся в слоте |
| Пользователь нажал стоп во время провала | задание снимается, обычная утилизация | `pendingRetune.set(null)` в `stop()` |
| Новый `retune` во время провала | **только** перезапись `pendingRetune`; таймер не перезапускается, шейпер не трогается | шторм |
| Скраб непрерывно (drag) | один провал в момент его начала; пока он идёт, цель перезаписывается; по завершении — следующий провал | то же правило |
| `retune` на паузе | без провала, мгновенно (§3.1) | тишина уже есть |
| Потеря фокуса во время провала | как пауза, затем `recreateTrack()` при смене устройства | |
| Смерть сервиса во время провала | трек уничтожается обычным путём, задание теряется — состояние согласовано | задание в памяти, а не в БД |
| Пакет ещё не дорос, а пришёл `retune` | регенерируется ограниченный пакет, доращивание отменяется | `offset = 0`, `packetBytes` пересчитывается |

Отдельно: **`ManagerState.HANDOFF`, `pendingHandoff`, `handoffStartWallMs`,
`switchElapsedMs` исчезают** — поток остаётся `PLAYING` на всём протяжении
перехода. Если UI опирается на `HANDOFF` (блокировка кнопок, индикация), ему
нужен отдельный сигнал; это надо проверить по `BinauralStreamManager` и
ViewModel **до** реализации.

## 10. Этапы и критерии

| # | Этап | Критерий готовности |
|---|---|---|
| 1 | Долгоживущий шейпер, база 1.0, без `closeShaper` | старт/пауза/резюм без ступенек; опроса на fade-in нет |
| 2 | Удалить `scheduleFadeCompletion` со всеми зависимостями | компилируется, поведение прежнее; прогон `tools/dbgscrub.sh` V1–V9 |
| 3 | `retune()` **на паузе** (§3.1) — самый простой путь | смена пресета на паузе: звук меняется, щелчка нет, провала нет |
| 4 | `retune()` **в игре** (§3.2) без смены конфига = скраб через перемотку | скраб звучит с правильной позиции, щелчка нет |
| 5 | `retune()` со сменой конфига (+ ограниченный пакет, §6) | смена пресета в игре: провал ≈310 мс, щелчка нет |
| 6 | Удаление второго трека, `outgoing`, reaper, `HANDOFF` | шторм 200 жестов за 4 с → корректный итог |
| 7 | Снять `MAX_TRACK_BUFFER_BYTES`, вернуть кольцо 10 с | пробуждений/час не больше нынешних |

Каждый этап — отдельный коммит, прогон V1–V9 + `tools/dbgstorm.sh`, установка на
устройство и субъективный прослух. Этапы 3–5 можно выкатывать и проверять по
отдельности: каждый сам по себе уже убирает часть ритуала.

## 11. Что надо проверить в коде до начала

1. Держит ли `AudioGenerator` ссылки/указатели на векторы `m_config` между
   вызовами `generateBufferDirect`? Если держит — `setConfig` из писателя
   потребует не атомарного слота, а барьера после конца пакета.
2. Зависит ли UI (ViewModel) от `ManagerState.HANDOFF`?
3. Используются ли `getCurrentPhases`/`setPhases` где-то кроме хэндоффа?
4. Может ли `PlaybackSpec.sampleRate` меняться между пресетами на практике?
5. Что реально возвращает `track.flush()` на целевом устройстве (POCO,
   Android 13) — нужен замер до этапа 4.
