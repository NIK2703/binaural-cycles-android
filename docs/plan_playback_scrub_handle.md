# План: ручка предпросмотра (scrub) на указателе текущего момента

**Задача.** При редактировании пресета, который сейчас воспроизводится, дать
возможность «перетащить» позицию прослушивания по графику и послушать, как
пресет звучит в другом месте суток. На верхнем конце красной полосы
появляется ручка из двух залитых стрелок, смотрящих в разные стороны от
линии. Пока тянем — на месте текущего момента остаётся серая вертикальная
линия (текущий момент всё это время идёт вперёд). Рядом с линией в
изменённом положении появляется кнопка сброса: по нажатию прослушивание
возвращается к текущему моменту.

**Статус:** реализовано полностью (шаги 1–10). Стенд `tools/dbgscrub.sh` написан
и прогнан на устройстве: **V1–V9 = 54 PASS / 0 FAIL** (протокол — §14.3). Осталось:
ручная проба жеста на устройстве (кламп ручки у краёв — открытый вопрос §13.4),
прослушивание (нет ли щелчка на скрабе и сбросе) и коммит.

## 2. Модель времени: сдвиг оси, а не «позиция трека»

Приложение живёт инвариантом *«звук == текущий момент суток»*. Поэтому скраб —
это не «позиция в треке», а **сдвиг всей оси времени суток**:

```
ось( t ) = normalize( t + Δ ),      Δ ∈ [0, 86400)
```

- **Δ = 0** — обычный режим;
- **Δ ≠ 0** — предпросмотр: движок считает, что сейчас `реальное_сейчас + Δ`.

Следствия, ради которых выбран именно сдвиг, а не «заморозить позицию»:

1. **Инвариант preserved.** Кривая продолжает эволюционировать под
   прослушиванием: красная линия едет вперёд со скоростью 1×, серая — тоже.
   Слышно не «застывшую точку», а то, как звучал бы этот участок суток.
   Для пресета с часовыми переходами это единственно осмысленный предпросмотр.
2. **Ничего не надо ломать в движке.** Ось sample-driven: `m_curveTimeSeconds`
   продвигается генерацией. «Заморозка» потребовала бы нового режима движка
   (остановить продвижение, но продолжать писать PCM) — это правка C++ и
   новый класс багов. Сдвиг не требует ничего.
3. **Всё производное остаётся консистентным.** Знаковая раскладка каналов
   (`beat(t)`), scatter биений, режим расслабления, кроссфейд перестановки
   каналов — всё это функции времени суток и продолжают работать на единой
   сдвинутой оси. Половинчатые решения здесь дают именно те баги, которые
   проект уже ловил (см. `docs/analysis_swap_crossfade_missing.md`).
4. **Красная и серая линии едут параллельно** — расстояние между ними
   визуально и есть Δ. Пользователь видит «мы слушаем на 6 часов вперёд».

Альтернатива (зафиксировать красную линию там, где отпустили) отвергнута:
она требует режима заморозки в движке и превращает прослушивание в статичный
тон без развития.

## 3. Где живёт сдвиг

### 3.1 `PlaybackSpec`

```kotlin
enum class SpecReason { PLAY, SETTINGS, PRESET_SWITCH, SAMPLE_RATE, RESUME, DEBUG, SCRUB }

data class PlaybackSpec(
    ...
    /** Сдвиг оси времени суток для предпросмотра, секунды [0, 86400). 0 = обычный режим. */
    val scrubOffsetSec: Int = 0,
    ...
)
```

Сдвиг входит в спеку, а не в «глобальную переменную движка», потому что
потоков бывает два (CURRENT и NEXT во время кроссфейда), и у каждого своя
ось. Спека — единственное место, где зафиксировано, **на какой оси построен
именно этот поток**.

### 3.2 Менеджер потоков

```kotlin
// нить актёра
private var scrubOffsetSec: Int = 0
private var pausedScrubOffsetSec: Int = 0     // сдвиг на момент ухода в паузу
val scrubOffsetSeconds: StateFlow<Int>        // наружу, для UI

fun scrubTo(timeOfDaySec: Int) = actor.post { ... }
fun scrubReset()               = actor.post { scrubToInternal(0) }
```

`setScrub` считает сдвиг **в последний ответственный момент, на нити актёра**:

```kotlin
val offset = normalizeTimeOfDay(timeOfDaySec - targetTimeOfDaySecondsUnshifted()).toInt()
```

`buildSpec()` всегда подставляет `scrubOffsetSec = scrubOffsetSec`, поэтому
любой новый поток (хэндофф, смена SR, возобновление из паузы) наследует ось
автоматически.

### 3.3 `prepare()` — первая ветка

`BinauralStreamImpl.prepare()`, сразу после выбора якоря:

```kotlin
val anchorSec = if (spec.scrubOffsetSec != 0)
    normalizeTimeOfDay(resolved.valueSec + spec.scrubOffsetSec.toFloat()).toInt()
else
    resolved.valueSec
engine.setCurveTime(anchorSec)

if (spec.scrubOffsetSec != 0) {
    // Ось сдвинута: play() БЕЗ preserveTimeline переякорил бы кривую
    // на реальные настенные часы и сбросил setCurveTime().
    engine.setPlaybackStartTime(System.currentTimeMillis() - spec.resumeElapsedMs)
    engine.play(preserveTimeline = true)
} else if (spec.resumeAnchorMs > 0) { ... }
```

Ветка намеренно **первая**: сдвиг явным образом запрещает «свежий старт».

### 3.4 Обход быстрого пути `audioEquals`

Этого не сделать — и скраб молча не применится. `requestHandoff` и
`tryAdvanceQueue` считают спек «той же самой» по `audioEquals`
(config + relaxation + sampleRate), а при скрабе меняется только ось.

```kotlin
// requestHandoff
if (cur != null && cur.spec.audioEquals(spec) &&
    cur.spec.scrubOffsetSec == spec.scrubOffsetSec && (...)) { cur.setVolume(...); return }

// tryAdvanceQueue — та же проверка перед «Nothing to do»
if (cur.spec.audioEquals(queued) && cur.spec.scrubOffsetSec == queued.scrubOffsetSec) { ... }
```

### 3.5 Пять мест, обязанных знать про сдвиг

| Место | Было | Стало |
|---|---|---|
| `targetTimeOfDaySeconds()` :1416 | `realTimeOfDaySeconds()` / virtual | `normalizeTimeOfDay(base + scrubOffsetSec)` |
| `captureContinuity` :1646-1648 | `isPlausible(tod, realTimeOfDaySeconds())` | `isPlausible(tod, targetTimeOfDaySeconds())` |
| `checkInvariant` :1884 | `realTimeOfDaySeconds()` | `targetTimeOfDaySeconds()` |
| `checkInvariantNow` :1923 | `realTimeOfDaySeconds()` | `targetTimeOfDaySeconds()` |
| `updateCurrentFrequencies` :505 | `_currentTimeOfDaySeconds.value = s.getCurrentTimeOfDay()` | см. §3.6 |

`targetTimeOfDaySeconds()` закрывает три места сразу (1343, 1384, 1458) —
включая решатель возобновления из паузы: A0/F0 сняты на сдвинутой оси, `now`
тоже сдвинут, Δ = now − A0 корректен.

**Сторож инварианта** обязан стать сдвиг-чувствительным, иначе в debug-сборке
на каждый скраб будет валиться `INVARIANT НАРУШЕН` — то есть сторож, поставленный
ловить «звук уехал от часов», будет ложно срабатывать на легальный режим.

### 3.6 Ось, которую видит UI, пока идёт кроссфейд

Ловушка: сразу после `scrubTo` CURRENT — ещё старый поток с `scrubOffsetSec = 0`,
и следующий тик опроса (через ~1 с) показал бы реальное «сейчас» — красная
линия дёрнулась бы назад и только через секунду вперёд.

Решение — одна строка, показывающая **целевую** ось независимо от того, какой
поток сейчас в слоте:

```kotlin
// updateCurrentFrequencies(), есть живой поток
val correction = scrubOffsetSec - s.spec.scrubOffsetSec
_currentTimeOfDaySeconds.value =
    normalizeTimeOfDay(s.getCurrentTimeOfDay() + correction).toInt()
```

Проверка всех случаев:

| Ситуация | `scrubOffsetSec` | `s.spec.scrubOffsetSec` | Показано |
|---|---|---|---|
| до скраба | 0 | 0 | реальное сейчас |
| сразу после `scrubTo(X)` | X | 0 (старый поток) | `сейчас + X` = цель |
| после SWAP | X | X | ось нового потока = цель |
| второй скраб поверх кроссфейда | Y | X | `(сейчас + X) + (Y − X)` = `сейчас + Y` |

Нет живого потока (пауза/простой):
`normalizeTimeOfDay(pausedTimeOfDay + (scrubOffsetSec - pausedScrubOffsetSec))`,
а если паузы не было — `normalizeTimeOfDay(realTimeOfDaySeconds() + scrubOffsetSec)`.

Частоты в течение ~1 с кроссфейда остаются от старого потока (реальное сейчас),
пока красная линия уже на цели — расхождение только в «толщине» полосы биений
на линии. Принимается: это честное отображение того, что реально звучит в
динамике в этот момент.

## 4. Публичное API по слоям

```
BinauralStreamManager   scrubTo(timeOfDaySec: Int) / scrubReset()
                        val scrubOffsetSeconds: StateFlow<Int>
        ↓
BinauralPlaybackService scrubTo(sec) / scrubReset()      — тонкая проброска
        ↓
BinauralViewModel       fun scrubTo(time: LocalTime)
                        fun resetScrub()
                        PlaybackTelemetry += scrubOffsetSeconds: Int
        ↓
FrequencyGraph          scrubOffsetSeconds: Int
                        onScrubTo: (LocalTime) -> Unit
                        onScrubReset: () -> Unit
```

Почему в API передаётся **абсолютное время суток**, а не сдвиг: сдвиг обязан
считаться на нити актёра в момент применения (`now` успевает уехать между
касанием и постом). UI знает только «куда поставили линию».

`resetScrub()` — то же самое, что `scrubTo(текущее_сейчас)`, но без вычислений:
`scrubOffsetSec = 0` и хэндофф.

## 5. Указатель на графике: три элемента

Все три живут в `FrequencyGraph` и появляются только при
`isPlaying && isEditingActivePreset`.

### 5.1 Серая линия — «реальное сейчас»

Рисуется **в динамичном слое `drawBehind`, до красной** (под ней):

```kotlin
if (scrubOffsetSeconds != 0 || scrubDragTime != null) {
    val realX = graphParams.timeToX(realTime)
    drawLine(
        color = onSurfaceVariant.copy(alpha = 0.35f),
        start = Offset(realX, 0f), end = Offset(realX, height),
        strokeWidth = 2f
    )
}
```

- Полосы биений и маркера на ней нет — это только «призрак» положения.
- Тоньше и бледнее красной, поэтому при совпадении (Δ ≈ 0) она просто
  прячется под красной, а не спорит с ней.
- `realTime` приходит **готовым из менеджера** (`PlaybackTelemetry.realTime`)
  и в UI не считается. Исторически здесь было
  `realTime = axisTime − axisMatchedOffset`; от этого отказались — см. §14.7:
  ось и сдвиг доезжают до UI разными StateFlow в непредсказуемом порядке, и
  вычитание залипало на величине Δ.
  ```
  axisTime = currentLocalTime                     // ось движка, уже со сдвигом
  realTime = <готовое из менеджера>               // реальное сейчас
  preview  = scrubDragTime ?: scrubPendingTarget ?: axisTime
  ```
  Ни одно из трёх не считается из положения пальца: иначе во время
  перетаскивания серая линия поехала бы вместе с пальцем — ровно наоборот
  тому, что нужно.

### 5.2 Ручка ◀|▶ — два залитых треугольника

Расположение: верхний конец красной полосы, визуал — 3 dp ниже верхней грани
области графика, по центру линии.

```
        ┌──────────────┐        ← «чип» 28×18 dp, surface α0.9,
        │ ◀        ▶   │           скругление 8 dp, обводка outline α0.5 (1 dp)
        └───┬──────┬───┘
            │      │            ← треугольники 7×9 dp в цвете indicator
        ════╪══════╪═══════     ← красная линия проходит между ними
```

- **Тактильная зона** 48×40 dp, визуал 28×18 dp: зона выступает на 10 dp выше
  области графика (внутрь 8 dp полей карточки — не обрезается, `Box` без клипа).
- **Кламп по краям:** `x.coerceIn(halfW, widthPx − halfW)`. У самого края чип
  перестаёт сидеть ровно на линии — это стандартная плата за то, чтобы он не
  уехал за границу графика. Альтернатива (выпустить за область графика в поля
  карточки) даёт 8 dp запаса — можно включить, если кламп будет раздражать.
- **Жест:** `detectHorizontalDragGestures` — а не `detectDragGestures`, чтобы
  вертикальный скролл экрана, начатый на ручке, не отбирался.
- **Снап:** 5 минут (`TIME_STEP_MINUTES`), как у перетаскивания точек.
  Накопление идёт без снапа, снапится отображаемое и фиксируемое значение —
  иначе на 1 px (~80 с) шаг был бы рваным.
- **Масштаб при захвате:** `graphicsLayer { scaleX/Y = 1.15f }` + тень 2 dp.
- **contentDescription:** «Прослушать другое время суток».

### 5.3 Кнопка сброса

- **Где:** сразу справа от ручки, зазор 4 dp. Если
  `x + halfHandle + 4 + btnW > widthPx` — переезжает влево от ручки.
- **Вид:** круг 30 dp, `surfaceContainerHighest`, иконка `RestartAlt` 18 dp в
  `onSurfaceVariant`, elevation 2 dp. Тактильная зона 44 dp.
- **Появляется** только при `scrubOffsetSeconds != 0` — с альфой/масштабом
  через `AnimatedVisibility`, чтобы не прыгать.
- **contentDescription:** «Вернуть прослушивание к текущему моменту».

### 5.4 Пузырь времени

Пока палец на ручке — над чипом пузырь `HH:MM` тем же стилем, что уже
используется при перетаскивании точки (`inverseSurface`, скругление 8 dp).
В отпущенном состоянии пузыря нет: о сдвинутом положении говорят серая линия
и кнопка сброса.

### 5.5 Жест: только по отпускании

**Звук перестраивается один раз, когда палец отпущен** — не на каждом шаге
перетаскивания. Причины:

- каждый шаг — это полный хэндофф (подготовка NEXT, старт трека, кроссфейд
  ~1 с, релиз уходящего); при обновлении раз в 200 мс кроссфейды накладывались
  бы друг на друга и звук превращался бы в кашу;
- длина кроссфейда (~1 с) больше любого разумного интервала обновления, то есть
  «живой» звук под пальцем всё равно был бы смазан;
- пока палец идёт, звучит старая ось (реальное сейчас) — это не ошибка, а
  норма: решение ещё не принято;
- дешевле и предсказуемее: один скраб = один хэндофф = одна запись в логе.

Отмена жеста (палец ушёл за пределы, системный «назад») — `onDragCancel`:
`scrubDragTime = null`, звук не трогаем.

Отпустили точно на серой линии → `normalize(цель − now) == 0` → это
`scrubReset()`, серая линия и кнопка исчезают. Естественный жест «вернуться»
 перетаскиванием, а не только кнопкой.

## 6. Состояние в `FrequencyGraph`

```kotlin
var scrubDragTime by remember { mutableStateOf<LocalTime?>(null) }
```

- позиция ручки и красной линии читается **на фазе раскладки** через
  `Modifier.offset { IntOffset(...) }` — тиканье телеметрии 1 раз в секунду не
  перекомпонует дерево (тот же приём, что у `DraggablePoint`);
- `onScrubTo` вызывается из `onDragEnd`, `onScrubReset` — из кнопки.

Новые параметры графика — с дефолтами, чтобы не ломать `MiniFrequencyGraph`
и остальные вызовы:

```kotlin
scrubOffsetSeconds: Int = 0,
onScrubTo: (LocalTime) -> Unit = {},
onScrubReset: () -> Unit = {},
```

## 7. Конфликты жестов и z-порядок

| Конфликт | Решение |
|---|---|
| Двойное нажатие по графику добавляет точку (`onDoubleTap`) | На ручке — `.clickable(onClick = {})` с пустым действием: съедает тап, до родителя он не доходит. Проверенный в этом же файле приём: `DraggablePoint` совмещает `.clickable` и `.pointerInput(detectDragGestures)` |
| Ручка перекрывает маркер точки у верхней границы несущей | Ручка объявляется **последним** ребёнком `Box`-а области графика, то есть выше точек. Точка на максимуме диапазона — редкость, и нижняя половина её 24-dp круга остаётся доступна |
| Контекстное окно точки (popup) | Оно ребёнок `BoxWithConstraints`, объявлен после `Box`-а графика → выше ручки. Окно всегда **под** точкой, пересечение только у самых верхних точек |
| Скролл экрана (график внутри `verticalScroll`) | `detectHorizontalDragGestures` забирает только горизонталь; вертикальный свайп, начатый на ручке, уходит скроллу |
| Закрытие popup по касанию мимо (проход Final) | Касание ручкой уже съедено → popup не закроется. Верное поведение |
| `BackHandler` | Не меняется |

## 8. Когда сдвиг сбрасывается

Сдвинутая ось — это ложь о времени, поэтому она обязана жить ровно столько,
сколько пользователь про неё помнит.

| Событие | Действие | Где |
|---|---|---|
| Нажата кнопка сброса | `scrubReset()` | VM |
| Выход из редактора (сохранить / не сохранять / «назад») | `resetScrub()` до восстановления кривой | `cancelEditingInService`, `finishEditing`, `saveAndNavigateBack` |
| Полная остановка воспроизведения | `scrubOffsetSec = 0` | менеджер, в `onStop`/`release` |
| Смена пресета | `resetScrub()` | VM, в `playPreset` |
| Уход в паузу | сдвиг **сохраняется**, но `pausedSpecDirty = true` при его смене на паузе | менеджер |
| Пересоздание сервиса / смерть процесса | сдвиг не переживает (только память) | — |

Смена настроек, частоты дискретизации, правка точек кривой — сдвиг
**сохраняется**: именно ради этого всё и затевается (послушать правку в 3 часа
ночи).

Авто-возврата по таймеру нет: посреди прослушивания внезапный возврат оси
хуже, чем явная кнопка. Признак «мы не сейчас» всегда на экране (серая линия +
кнопка), а за пределы редактора сдвиг не выходит.

## 9. Чего делать НЕ надо

- **Не трогать C++.** `setCurveTimeSeconds` уже есть и не за debug-гардой.
- **Не расширять `debugScrub`.** Он завязан на virtual clock, не работает в
  реальном режиме (`scrubVirtualTime` молча выходит, если
  `!m_virtualClock.isEnabled()`) и всё равно не форсит хэндофф (см. §11.1).
- **Не наследовать позицию кривой через `CurveAnchor`.** `enrichForContinuity`
  осознанно не несёт якорь — вся борьба с защёлкиванием 0 → 0 была именно про
  это (`docs/handoff_anchor_zero_analysis_plan.md`). Сдвиг — скаляр, а не якорь:
  он не устаревает, потому что применяется к «сейчас» в момент `prepare()`.
- **Не трогать `MiniFrequencyGraph`** и экран списка: сдвиг не переживает выход
  из редактора, MiniGraph не должен про него знать.
- **Не добавлять второй источник «реального сейчас» в UI.** Серая линия
  берётся из того же источника, что и ось, — менеджер публикует их **парой,
  из одной базы** (§14.7). Два НЕЗАВИСИМЫХ时钟 (отдельный тикер в композабле
  рядом с осью движка) по-прежнему запрещены: они дали бы дрожание линий друг
  относительно друга.

## 11. Ловушки

### 11.1 `debugScrub` не форсит хэндофф — и это же подстерегает скраб

`debugScrub` вызывает `requestHandoff(buildSpec(SpecReason.DEBUG))`, но спока
полностью `audioEquals` живой → срабатывает быстрый путь
(`cur.setVolume(...); return`), поток не пересоздаётся и
`applyNativeDebug` не вызывается. Скраб с той же схемой **молча не
применился бы**. Отсюда обязательная правка §3.4.

### 11.2 `play()` без `preserveTimeline` сбрасывает ось

В `prepare()` последняя `else`-ветка — `engine.play()`: он переякоривает
`m_curveTimeSeconds` на `realTimeOfDaySeconds()` и стирает только что
поставленный `setCurveTime`. Сдвинутая ось обязана идти через
`play(preserveTimeline = true)` (§3.3). Полагаться на то, что фазы несущих
всегда не-null и третья ветка сработает, — нельзя.

### 11.3 Сторож инварианта

Без правки §3.5 в debug-сборке скраб = гарантированное
`INVARIANT НАРУШЕН` с Δ, равной сдвигу. Сторож перестанет отличать «звук
уехал» от «оператор слушает другое время».

### 11.4 `enrichForContinuity` и `debugScrubPending`

Там стоит ранний `if (debugScrubPending != null) return spec` — непрерывность
не наследуется при debug-скрабе. **Продакшен-сдвиг туда не должен попасть**:
ему наследование фаз нужно (иначе NEXT стартует с фазы 0 и интерферирует с
уходящим). Это две независимые переменные; путать их нельзя.

### 11.5 Квантование телеметрии

`BinauralViewModel` квантует `currentTime` до 60 с. Серая линия наследует ту же
погрешность (≤ 60 с ≈ 0.07 % ширины графика) — неразличимо. Зато линии
гарантированно не дрожат друг относительно друга.

### 11.6 Пакет длиной в минуты

Сдвиг не может быть реализован «перемоткой» уже сгенерированного пакета: при
пользовательском интервале 10 минут и сдвиге в 6 часов перематывать нечего —
пакет надо перегенерировать. Поэтому скраб — всегда хэндофф, а не
`resume(skipSeconds = ...)`. (В редакторе интервал и так снижен до 60 с через
`armEditorPreviewBufferInterval()`, но на скраб вне правок это не распространяется.)

### 11.7 Шторм скрабов

Два скраба подряд во время кроссфейда коалесцируются: очередь latest-wins на
один слот, `tryAdvanceQueue` не поднимает NEXT, пока `outgoing != null`.
Формула коррекции оси (§3.6) при этом остаётся верной. Зависших состояний не
возникает, но это надо проверить сценарием V6.

новой спекой. Смещение держится в `buildSpec()`, а не в точке входа, поэтому
покрытие то же.

**Критерий PASS — всегда из двух частей**, и это принципиально:

1. `audible ≈ now + scrub` (по кругу суток, допуск 5 с) — ось доехала до звука;
2. `scrub ≈ ожидаемому` (допуск 8 с) — доехала именно ТУДА.

не то время. Второе без первого — это просто значение в `StateFlow`, которое не
попало в `prepare()`. Допуск на сдвиг взят с запасом потому, что сдвиг считается
на нити актёра в момент применения и почти всегда на 1–2 с меньше круглого
числа — время между чтением `now` стендом и доставкой команды.

### Тонкие места, обнаруженные при реализации

- `resetSession()` НЕ годится как место сброса сдвига: он вызывается и на живом
  пути `tryAdvanceQueue` (когда `current == null` при `pendingHandoff`) — там

| V8 | 23:35 | 01:35 | 7198 | пауза не сбила ось; `resumesnap` = SOFT |

Отдельно подтвердилось то, что было главным риском плана (§11.1 и §11.3):
быстрый путь `audioEquals` на скрабе **обходится** (`needsHandoff` сравнивает
сдвиги) — иначе ни один сценарий не сдвинул бы ось; и сторож инварианта
**не срабатывает** на легальный предпросмотр, то есть по-прежнему отличает
«звук уехал» от «оператор слушает другое время».

#### Что пришлось поправить по ходу верификации

1. **`vsnap` не нёс сдвиг.** Машинный снимок обязан различать «ось сдвинута»
   и «звук уехал от часов» — обе ситуации выглядят как `audible != now`.
   Добавлено поле `scrub=`.
2. **`DebugCommandExecutor.applyPreset()` не повторял `resetScrub()`** из
   `BinauralViewModel.playPreset()`. UI-путь стирал сдвиг, CLI-путь — нет, и
   V9 был бы невоспроизводим. Это расхождение CLI с реальным UI, а не уступка
   стенду.
3. **`vsnap` печатал числа с запятой.** `String.format` без локали берёт
   системную, и на русской локали снимок отдавал `now=83991,88`; `awk` читает
   такое как `83991`, то есть молча теряет дробь. Машинный формат переведён на
   `Locale.US`.
4. **Ловушка самого стенда (кода не касается): `clockreset` обязан идти ДО
   снятия сдвига.** `clockreset` двигает только настенные часы, ось живого
   потока остаётся где была. Если сначала снять сдвиг, `pscrubreset` получит
   уже нулевой сдвиг → та же спека → быстрый путь `audioEquals` отсечёт её →
   хэндоффа не будет → расхождение в сутки уедет в СЛЕДУЮЩИЙ сценарий, где
   сторож честно заорёт `INVARIANT НАРУШЕН` на чужой ошибке. Ровно это и было
   первым (и единственным) FAIL прогона: V6 получил в наследство вилку от
   уборки V5.

### 14.4 Правка: серая линия не исчезает на отпускании ручки (2026-09-03)

Симптом с устройства. Тянем ручку — серая линия на месте, красная идёт за
пальцем. Отпускаем: красная на мгновение возвращается туда, откуда тянули, на
месте цели мелькает серая, через мгновение она же становится красной, а серой
нет. Ожидание (§5.1): серая всё время стоит на реальном «сейчас» и не
пропадает, пока ось сдвинута.

Причина — рассогласование двух входов, приходящих в UI в РАЗНЫЕ кадры:

| Вход | Источник | Когда обновляется |
|---|---|---|
| `scrubOffsetSeconds` | отдельный StateFlow менеджера | сразу по жесту |
| `axisTime` (ось) | `currentTimeOfDaySeconds` | опрос 1 Гц, квантование до 60 с |

Между ними — окно до секунды, в котором `axisTime` ещё СТАРЫЙ. Формула §5.1
`реальное_сейчас = ось − сдвиг` в этом окне смешивает новое со старым: серая
линия уезжала на величину Δ, а при Δ = 0 просто пропадала (условие её
видимости завязано на сам сдвиг). Красная линия в том же окне уезжала на
`axisTime`, то есть назад к «сейчас» — отсюда «жест отменился».

Три правки, каждая закрывает свою половину окна:

1. **`FrequencyGraph`: сдвиг, согласованный с осью.** ← УСТАРЕЛО, снято §14.7:
   сам подход «вычесть сдвиг из оси в UI» признан негодным.
   `axisMatchedOffset = remember(axisTime) { scrubOffsetSeconds }` — сдвиг,
   зафиксированный в момент прихода оси и не подменяемый новым до прихода
   следующей оси. Формула та же, но перестала смешивать разновозрастные
   данные: в установившемся режиме это ровно «ось − сдвиг», а в окне —
   «старая ось − старый сдвиг», то есть то же самое реальное «сейчас».
   Второго источника времени не появилось (§9).
2. **`FrequencyGraph`: цель перетаскивания живёт до прихода оси.**
   `scrubPendingTarget` — палец уже отпущен, а красная линия остаётся на цели,
   пока ось не доедет (допуск 300 с = квантование 60 с + снап ручки 5 мин;
   это 2–3 px, поэтому «скраб меньше допуска» неотличим от «ось на месте»).
   Снимается в `LaunchedEffect(axisTime, scrubPendingTarget)`; страховка 2.5 с
   на случай, что скраб не состоялся — линия обязана вернуться на ось, а не
   замереть. Условие видимости серой линии учитывает `scrubPendingTarget`:
   иначе она пропадала бы ровно в том окне, где нужнее всего.
3. **`BinauralStreamManager.applyScrub`: ось публикуется сразу, а не на
   следующем тике 1 Гц.** `updateCurrentFrequencies()` считает поправку §3.6
   сам (старый поток ещё в слоте, его `spec.scrubOffsetSec` прежний), поэтому
   ось UI встаёт на цель в том же кадре, что и сдвиг. Сервис копирует ось
   отдельным коллектором — как уже делал для сдвига, — а не только в
   ежесекундном джобе: иначе немедленная публикация никуда бы не доехала.

Без правки 3 красная линия висела бы на цели до секунды (не flicker, но
заметная задержка), и сброс кнопкой возвращался бы с той же задержкой. С
правкой 3 окно сжимается до кадра-двух, а правки 1–2 делают его невидимым в
любом случае: порядок прихода двух StateFlow не гарантирован, и держать
корректность на нём нельзя.

### 14.5 Правка: линия воспроизведения останавливается на границе, а не переходит на противоположную сторону (2026-09-03)

Симптом с устройства. Тянем ручку скраба за правый (или левый) край графика —
красная линия «перескакивает» на противоположный край (через полночь), вместо
того чтобы встать на границе. Ожидание (запрос на граничное поведение): за
пределами графика линия обязана остановиться на границе (00:00 слева, 23:59:59
справа), не переходя на другую сторону.

Причина — две независимые точки, обе давали обход:

1. **Накопление жеста не кламповалось.** `onHorizontalDrag` делал
   `accumulatedPx += dragAmount` без ограничения. Уводя палец далеко за край,
   `accumulatedPx` уходил за `[0; widthPx]`, и обратно линия не двигалась, пока
   пользователь не «вернёт» тысячи px.
2. **`snappedTimeFromDrag` делал круговую нормализацию.**
   `normalized = ((snapped % 86400) + 86400) % 86400` — любое `raw > 86400`
   сворачивалось в левую часть суток. В частности `raw = startSeconds + widthPx
   · 86400 / widthPx = startSeconds + 86400` (ручка у правого края) давал
   `normalized = startSeconds`, то есть линия прыгала на место, откуда её
   потянули, но с противоположной стороны графика. Это и есть «переход на
   противоположную сторону».

Правка — ОДНА, держит обе точки:

1. **`FrequencyGraph.snappedTimeFromDrag`: кламп вместо круга.**
   `clamped = snapped.coerceIn(0.0f, 86399.0f)` — итоговое время упирается в
   границы суток и не сворачивается. Круговая арифметика убрана полностью.
   Именно этот кламп останавливает линию на крае и не даёт ей перескочить на
   противоположную сторону при перетаскивании за границу.

**Накопление жеста (`accumulatedPx`) НЕ клампуется.** `onHorizontalDrag` делает
просто `accumulatedPx += dragAmount`. `dragAmount` при тяге влево отрицательный,
поэтому кламп накопления к `[0; widthPx]` ЗАПРЕЩЁН: он шваркал накопление на 0
при любом движении влево, и линия «не уходила» назад — только вперёд (регресс,
пойманный на устройстве сразу после первой редакции §14.5, см. ниже). Граница
держится клампом ВРЕМЕНИ, а не накопления; оверскролл за край ограничен самим
временем, а не величиной накопления.

Следствие для остального. График — это один день `[00:00; 24:00]`, и ручка
больше НЕ умеет скрабить «через полночь»: цель всегда в `[0; 86399]`. Сама
операция скраба в движке (`PlaybackSpec.scrubOffsetSec`, путь `pscrub`) круговую
арифметику сохраняет — стенд V5 этим путём проверяет обёртку и остаётся
актуальным; поменялось только поведение ПЕРЕТАСКИВАНИЯ ручки в UI. Если позже
понадобится скраб через полночь жестом — это отдельная фича (двухфазный жест /
долгое удержание у края), вне текущего запроса.

Проверка (ручная, стенд жест не ловит):
- Потянуть ручку вправо до упора и дальше за край — красная линия встаёт на
  23:59:59 и не уходит на 00:00; отпустить у края — фиксируется 23:59:59.
- То же влево — линия встаёт на 00:00.
- Вернуть палец внутрь графика из «прилипшего» состояния — линия сразу едет за
  пальцем (накопление не увезено в минус/плюс тысячи px).
- Сброс кнопкой возвращает красную линию на реальную ось (без регресса §14.4).

### 14.7 Правка: серая линия уезжала на цель перетаскивания (2026-09-04)

Симптом с устройства. Тянем ручку на шесть часов вперёд и отпускаем: красная
линия встаёт на цель, а **серая едет вместе с ней** и стоит на цели, а не на
реальном «сейчас». Держится так до следующего изменения оси, то есть до минуты
(квантование телеметрии §11.5). Ожидание (§5.1): серая линия — это текущий
момент времени суток и НИКОГДА не зависит от того, куда перетащили
прослушивание.

Причина не в жесте и не в геометрии, а в самой формуле серой линии: §5.1
в редакции §14.4 считал её вычитанием.

```
realTime = axisTime − axisMatchedOffset
axisMatchedOffset = remember(axisTime) { scrubOffsetSeconds }
```

`axisTime` и `scrubOffsetSeconds` — **два разных StateFlow**: менеджер
публикует ось и сдвиг, сервис копирует их двумя отдельными коллекторами
(`BinauralPlaybackService.onCreate`), ViewModel — тоже двумя, и **порядок их
прихода в композабл не гарантирован**. `remember` же пересчитывается только
когда меняется КЛЮЧ, то есть ось. Разбор двух порядков:

| Что пришло первым | Что посчитал `remember` | Где серая линия |
|---|---|---|
| сдвиг, потом ось | на новой оси — новый сдвиг | на реальном «сейчас» ✔ |
| ось, потом сдвиг | на новой оси — **старый** сдвиг | **на цели, и так до минуты** ✘ |

Второй случай — не редкость, а подбрасывание монеты: два коллектора стартуют
в одном `serviceScope` и диспетчатся независимо. Причём пришедший вторым
сдвиг уже ни на что не влияет: ключ `remember` не изменился, пересчёта не
будет до следующего **изменения оси**. §14.4 это и предсказывал словами
(«порядок прихода не гарантирован, держать корректность на нём нельзя»), но
правка 1 того же параграфа всё равно опиралась на порядок.

Корень глубже: одно и то же число — «реальное сейчас» — вычислялось дважды,
и второй раз, косвенно, на стороне композабла, из двух значений, которые не
обязаны быть одной свежести.

**Правка: реальное время публикуется менеджером отдельным потоком, в паре с
осью.**

```
BinauralStreamManager   unshiftedTimeOfDaySeconds: StateFlow<Int>   // НОВОЕ
                        currentTimeOfDaySeconds: StateFlow<Int>
        ↓
BinauralPlaybackService unshiftedTimeOfDaySeconds (статический, свой коллектор)
        ↓
BinauralViewModel       PlaybackTelemetry.realTime: LocalTime
        ↓
FrequencyGraph          realTimeOfDay: LocalTime?
```

Оба времени считаются в ОДНОМ вызове `updateCurrentFrequencies()` из ОДНОЙ
базы — позиции потока, который реально звучит:

```kotlin
// снимаем сдвиг, реально заложенный в ЭТОТ поток (старый — во время кроссфейда)
val realSec = normalizeTimeOfDay(s.getCurrentTimeOfDay().toFloat() - s.spec.scrubOffsetSec).toInt()
_unshiftedTimeOfDaySeconds.value = realSec
_currentTimeOfDaySeconds.value = normalizeTimeOfDay(realSec.toFloat() + scrubOffsetSec).toInt()
```

- **Ось при этом не изменила значение**: `поток − свой_сдвиг + общий_сдвиг`
  — это прежняя формула `поток + (общий − свой)`, только записанная через
  базу. Проверено на всех состояниях (нет сдвига / сразу после `scrubTo` /
  после SWAP / два скраба в одном кроссфейде) — совпадает.
- Расстояние между красной и серой линиями теперь **в точности** равно сдвигу,
  включая окно кроссфейда: оба числа из одного источника.
- Дрейфа между линиями нет: база — ось звука, а не настенные часы, поэтому
  §9 («не добавлять второй источник времени») не нарушен. Запрет касается
  НЕЗАВИСИМЫХ часов; здесь два показания одних.
- `remember(axisTime)` и `axisMatchedOffset` удалены из `FrequencyGraph`
  совсем: восстанавливать согласованность в UI больше нечего.
- `scrubPendingTarget` (§14.4, правка 2) оставлен: он держит КРАСНУЮ линию на
  цели, если хэндофф по какой-то причине не сдвинул ось. ← его влияние на
  видимость СЕРОЙ линии снято §14.8 — там видимость переведена на геометрию,
  а не на `scrubPendingTarget`.
- Пауза и простой: реальное время публикуется тоже — замороженное
  (`pausedTimeOfDay − pausedScrubOffsetSec`) и от базы (`baseTimeOfDaySeconds()`)
  соответственно. На паузе указатель не рисуется вовсе (`isPlaying == false`),
  но пара обязана быть консистентной: при возобновлении её читают.
- `debugScrub` публикует пару тоже: оператор переставил ось, значит «реальным
  сейчас» становится `ось − активный_сдвиг`.

Отставание нового потока на одну эмиссию (до секунды) безвредно: реальное
время меняется плавно, секунда на графике суток — сотая доля пикселя, и
следующая эмиссия всё поправит. Залипнуть значение больше не может — оно
никуда не вычитается.

**:app:compileDebugKotlin — BUILD SUCCESSFUL.** Прогон `tools/dbgscrub.sh`
(V1–V9) правку не покрывает: стенд работает через CLI и до `FrequencyGraph`
не доходит — проверка по-прежнему ручная, на устройстве (§15.1). Что смотреть:
потянуть ручку и отпустить — серая остаётся на «сейчас» и НЕ едет за красной;
повторить несколько раз подряд (порядок прихода StateFlow — случайный); сброс
кнопкой возвращает красную линию к серой, серая при этом не двигалась.

### 14.8 Правка: серая линия пропадала на отпускании ручки (2026-09-04)

Симптом с устройства (поверх §14.7). После §14.7 серая линия перестала
УЕЗЖАТЬ за красной, но теперь **ПРОПАДАЕТ в момент отпускания** ручки: тянем
— видна, отпускаем — исчезает на какое-то время, потом возвращается. Ожидание
(§5.1): серая линия — призрак реального «сейчас» и обязана быть видна
**постоянно**, пока красная линия не стоит ровно на текущем моменте.

Причина — в условии видимости серой линии в `FrequencyGraph` (второй слой
`drawBehind`):

```kotlin
if (scrubOffsetSeconds != 0 || scrubDragTime != null ||
    scrubPendingTarget != null
) { /* рисуем серую */ }
```

Все три флага — преходящие, и в окне сразу после отпускания ВСЕ три ложны
одновременно:

1. `scrubDragTime` — палец уже отпущен, ручка стёрта → `null`.
2. `scrubPendingTarget` — ось (опрос 1 Гц) за ту же секунду успевает доехать
   до цели, `LaunchedEffect` сверяет `axisTime` с целью в допуске 300 с
   (§14.6) и **снимает цель** → `null`.
3. `scrubOffsetSeconds` — `StateFlow` сдвига всё ещё 0: он публикуется тем же
   менеджером, но в другом потоке, и до композабла не долетел.

Итог: ровно в тот кадр, где серая нужнее всего (показать ТОЛЬКО что
появившийся сдвиг), условие ложно — линия гаснет, потом сдвиг приходит и
включает её снова. Видимость была привязана к *состоянию скраба*, а не к
*положению* линий.

**Правка: видимость серой линии решает геометрия, а не состояние (2026-09-04).**

Серая видна, пока красная линия (`previewTime`) отстоит от реального «сейчас»
(`realTime`) дальше порога:

```kotlin
val ghostGapPx =
    abs(circularDiffSeconds(previewTime, realTime)) / (24f * 3600f) * graphParams.widthPx
if (ghostGapPx > GHOST_LINE_MIN_GAP_PX) { /* рисуем серую */ }
```

- Порог `GHOST_LINE_MIN_GAP_PX = 2f` (пиксели, а не секунды): смысл вопроса —
  «красная на текущем моменте или нет», он визуальный. 2 px — это ширина самой
  линии: при меньшем зазоре два штриха сливаются. Сверху порог перекрыт
  квантованием телеметрии 60 с (§11.5): сутки на ~1000 px — 0.7 px/минута, так
  что «красная на сейчас» (расхождение 0…60 с) устойчиво в мёртвой зоне, а от
  трёх минут зазор уже виден.
- Разность берётся `circularDiffSeconds` (по кругу суток). Прямое сравнение
  `timeToX` сломалось бы у полуночи: пара 23:59 / 00:01 дала бы весь график.
- Флаги состояния (`scrubOffsetSeconds`, `scrubDragTime`, `scrubPendingTarget`)
  из условия **удалены** — они больше не управляют видимостью. `scrubPendingTarget`
  сам по себе остаётся: он держит красную линию на цели (§14.4/§14.8), но на
  серую не влияет.
- Побочный эффект: исчезла и старая зависимость от порядка прихода StateFlow
  сдвига. Раньше при «ось пришла первой» сдвиг ещё 0 и серая гасла; теперь
  расхождение `previewTime` от `realTime` уже ненулевое — линия держится на
  весь кроссфейд, пока красная не приедет на текущий момент.

**Толщина серой линии приведена к красной (2026-09-04).** Было

`strokeWidth = 2f`, только полоса биений — `3f`, см. `drawCurrentTimeIndicator`).

### 14.10 Правка: кнопка сброса у ручки (2026-09-04)

Кнопка сброса оси к реальному «сейчас» живёт рядом с ручкой ◀|▶ и видна
**постоянно**, пока воспроизведение идёт НЕ по текущему моменту (§5.3).

- **Без фона.** Раньше кнопка была кружком `surfaceContainerHighest` с
  `shadowElevation` — он визуально весил больше самой ручки и спорил с графиком
  под ней. Теперь это чистая `Icon` (`Icons.Default.RestartAlt`, 18 dp) без
  `Surface`. Тактильная зона оставлена 44 dp, зазор до ручки 4 dp.
- **Цвет и прозрачность — как у треугольников ручки.** `tint =
  indicatorColor.copy(alpha = SCRUB_ARROW_ALPHA)` (§14.9, `SCRUB_ARROW_ALPHA =
  0.3f`). Кнопка визуально «одной породы» с ручкой, а не отдельным контролом.
- **Положение:** СПРАВА от ручки, пока справа хватает места; если нет —
  ПЕРЕЕЗЖАЕТ ВЛЕВО (явное требование пользователя, 2026-09-04). Запасной
  вариант слева нужен у правого края графика, где справа места уже нет.
  Центр считается по геометрии и клампуется по *визуальному* размеру иконки
  (18 dp), так что 44 dp-зона может чуть вылезти за край, но сама иконка — нет.
- **Порядок в `Box`**: кнопка объявлена ДО ручки, поэтому в зоне пересечения
  их тактильных зон (48 dp ручка и 44 dp кнопка расходятся всего на ~27 dp)
  захват жеста выигрывает ручка, а не кнопка.
- **Видимость — геометрия, а не флаг (§14.8).** `showReset =
  offNowGapPx(previewTime, realTime, widthPx) > GHOST_LINE_MIN_GAP_PX &&
  scrubDragTime == null`. Пока палец на ручке — кнопки нет (захват), как только
  отпустил и линии разошлись — появляется. Та же `offNowGapPx`, что и у серой
  линии, так что кнопка и серая появляются/исчезают синхронно. Параметр
  `scrubOffsetSeconds` из `FrequencyGraph` **удалён** целиком: им управляла бы
  состояние скраба, а не положение (§14.8 — та же ловушка, что гасила серую).

### 14.11 Правка: «магнит» к сейчас при перетаскивании + автосброс при выходе (2026-09-04)

**А) Магнит к текущему моменту (§5.3, запрос пользователя).** Ручку
«прилипает» к реальному «сейчас», если во время перетаскивания под палец
уходит время в пределах **±15 минут** от настоящего текущего момента.

- Порог `SCRUB_SNAP_TO_NOW_SECONDS = 15 * 60` (секунды). Сравнивается
  `circularDiffSeconds(previewTime, realNow)` — по кругу суток, чтобы липло и
  через полночь.
- Сравниваем с **реальным «сейчас»** (`realTimeOfDay`, передаётся в `ScrubHandle`
  отдельным параметром), а НЕ с осью: ось сама сдвинута скрабом, и «липнуть к
  ней» было бы бессмысленно. `realTimeOfDay` читается через
  `rememberUpdatedState`, чтобы магнит ловил живое «сейчас» даже на секунду
  позже начала жеста.
- Внутри `onHorizontalDrag` считаем `snap`: если попали в окно — `finalTarget =
  realNow` (а не квантованная цель), иначе цель как есть. `onDrag(finalTarget)`
  кладёт это в `scrubDragTime`, поэтому КРАСНАЯ линия во время жеста встаёт
  ровно на СЕРУЮ — видимый «щелчок» на текущий момент. Пузырь времени при этом
  показывает само «сейчас».
- По **отпускании** магнита — это **сброс**, а не скраб в замороженную секунду:
  `onDragEnd` при `snappedToNow` вызывает `onReset()`, а не `onCommit(target)`.
  Иначе коммит квантованного `realTimeOfDay` оставил бы offset до 60 с (§11.5) и
  красная медленно уплывала бы от серой. `onReset()` теперь не только дёргает
  `viewModel.scrubReset()` (offset = 0, ось точно на «сейчас»), но и чистит
  локальные цели жеста `scrubDragTime`/`scrubPendingTarget`, чтобы красная сразу
  легла на ось. Вызывается и кнопкой сброса, и магнитом — поведение единое.

**Б) Автосброс при закрытии редактора (§5.3, запрос пользователя).** Уход с
экрана редактирования пресета всегда возвращает прослушивание к реальному
«сейчас».

- В `PresetEditScreen` добавлен `DisposableEffect(Unit) { onDispose {
  viewModel.scrubReset() } }` (СЛЫШИМЫЙ сброс — движок возвращает ВОСПРОИЗВЕДЕНИЕ
  хэндоффом на «сейчас», а не только линию/сдвиг оси). Срабатывает при ЛЮБОМ
  реальном уходе экрана из композиции — системный «назад», стрелка `TopAppBar`,
  свайп, — даже если конкретный путь навигации не прошёл через
  `finishEditing()`/`cancelEditingInService()`.
- Почему именно слышимый `scrubReset()`, а не тихий `resetScrub()`: тихий
  стирает сдвиг, НЕ трогая поток, — на путях, где кривую никто не перестраивал,
  звук остался бы на прослушиваемом (скрабнутом) времени. Слышимый же
  guaranteed возвращает и звук. Двойного щелчка на штатных путях НЕТ:
  `finishEditing()`/`cancelEditingInService()` уже стёрли сдвиг тихим
  `resetScrub()` (их хэндофф перестройки кривой сам возвращает звук), а
  `scrubReset()` движка при нулевом сдвиге делает ранний выход (no-op).
  Слышимая работа остаётся только путям, где сброс больше никто не сделал.
  `DisposableEffect(Unit)` НЕ пересоздаётся на реконфигурациях (поворот экрана),
  `onDispose` здесь — только при реальном закрытии.

**:app:compileDebugKotlin — BUILD SUCCESSFUL; :app:assembleDebug -PabiFilter=arm64-v8a — BUILD SUCCESSFUL; установлено на устройство (§15.1).** Проверка
ручная, на устройстве: потянуть ручку ближе чем на 15 мин к серой — красная
щёлкает на «сейчас» и держится; отпустить — звук сразу на текущем моменте,
кнопка сброса/серая гаснут. Выйти из редактора любым способом — ось
возвращается к «сейчас» (offset → 0).

### 14.12 Правка: чистая иконка сброса + скрытие «выделенной области пересечения» при перетаскивании (2026-09-04)

**А) Иконка сброса — убрать артефакт отрисовки (запрос пользователя).** У
`Icons.Filled.RestartAlt` в текущем окружении отрисовки — разрыв/зазор в
«хвосте» стрелки снизу по центру. Заменена на чистую стандартную

**Б) Снятие «выделенной области пересечения» во время жеста (запрос
пользователя, уточнение 2026-09-04: НЕ дырка, а сплошная полупрозрачная
линия).** Яркий сегмент красной линии внутри полосы биений

телеметрии движка (`currentCarrierFrequency`/`currentBeatFrequency`), то есть
отражает РЕАЛЬНУЮ позицию звука, а не цель пальца.

  `drawCurrentTimeIndicator`. При `showBeatBand == false` сегмент внутри
  полосы биенов НЕ пропускается (первая версия оставляла на его месте дырку —
  пользователь явно попросил без неё), а рисуется той же полупрозрачной
  линией, что и крайние сегменты (`alpha 0.3f`, `width 2f`): во время жеста
  вся красная линия — СПЛОШНАЯ и однородная, без выделений и без разрывов.
- В точке вызова (блок `.drawBehind`, только при `isPlaying`) передаётся
  `showBeatBand = scrubDragTime == null && scrubPendingTarget == null`:
  - при **начале перетаскивания** (`scrubDragTime != null`) яркое выделение
    гаснет мгновенно, линия целиком становится равномерно полупрозрачной и
    продолжает следовать за пальцем;
  - после **отпускания** (`scrubDragTime == null`, но `scrubPendingTarget !=

    пересечение, рассчитанное для СТАРОЙ позиции;

    возвращается, теперь с частотами, соответствующими НОВОЙ красной линии
    («показывается только после обновления пересечения при отпускании»).
