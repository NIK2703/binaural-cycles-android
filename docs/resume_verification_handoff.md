## 1. Задача

Исходная задача: «когда ставишь воспроизведение на паузу, а потом через
некоторое время возобновляешь — оно продолжается с той позиции, на которой
остановилось. ЭТО НЕКОРРЕКТНОЕ ПОВЕДЕНИЕ: воспроизведение всегда должно
соответствовать текущему моменту времени в рамках суток».

Требование к верификации: **добавить в debug-сборку всё необходимое для точной
проверки всех граничных случаев** и **использовать виртуальное время вместо
прямого ожидания**.

## 2. Инвариант (суть приложения)

Звук всегда соответствует **текущему моменту суток** по кривой пресета.
Пауза — это тишина, а не «запомненная позиция»: возобновление играет ритм для
`now`, а не для точки остановки.

Решатель возобновления (в `BinauralStreamManager`):

- `A0` — слышимая позиция на заморозке; `F0` — фронтир генерации
  (`getCurveTimeSeconds()`); `now` — текущее время суток;
- `Δ = normalize(now − A0)`, `window = normalize(F0 − A0)`;
- `Δ ≤ window` → **SOFT**: пакет переиспользуется, курсор ставится на
  АБСОЛЮТНЫЙ кадр `T = A0 + Δ·rate` + `AudioTrack.flush()` (сброс кольца трека,
  где лежат копии PCM, записанные до паузы — без flush первые R секунд звучала
  бы СТАРАЯ позиция, что и выглядело как «продолжение с той же позиции»);
- `Δ > window` → **REBUILD**: пересборка потока с якорем на `now`
  (`resumeCurveTimeSeconds = -1` → `prepare()` → `engine.setCurveTime(now)`).

Нормализация `((x % 86400) + 86400) % 86400` обязательна — ловит переход через
полночь и отрицательные Δ.

## 3. Центральная проблема верификации и её решение

**VirtualClock (`vtime`/`scale`/`scrub`) для проверки паузы НЕ ГОДИТСЯ.**
В виртуальном режиме носитель времени движка — sample-driven ось
(`base + сгенерированные_секунды * scale`): на паузе генерация стоит, значит и
«now» по VirtualClock стоит. Сколько ни жди — Δ паузы останется нулевой, и
решатель вообще не будет испытан.

Решение — **виртуальные настенные часы**: процесс-глобальный сдвиг в
миллисекундах, который видят ОБЕ стороны:

- Kotlin: `DebugClock` (`com.binaural.core.audio.debug`) — через него теперь
  читает «now» и `PlaybackSpec.realTimeOfDaySeconds()`, т.е. решатель;
- C++: `binaural::debug::wallOffsetMs()` (`DebugWallClock.h`) — через него
  читают якорь свежего старта `BinauralEngine::realTimeOfDaySeconds()` /
  `getCurrentTimeSeconds()` и семя `VirtualClock::realTimeOfDaySeconds()`.

Тогда `warp +10000` моделирует «прошло 10 секунд паузы» мгновенно: «сейчас»
уезжает вперёд, а пакет, голова трека и фронтир остаются замороженными —
ровно как при настоящей паузе. В release сдвиг всегда 0 (единственный путь
установить его — debug-команды под `BuildConfig.DEBUG`; JNI-методы под
`ENABLE_DEBUG_TIME_CONTROL` — no-op заглушки).

### Новые debug-команды

```
warp <дельта>            прокрутить часы: 5 | 5s | 250ms | 2m | 1h | -3
totime <сек|HH:MM[:SS]>  поставить часы на момент суток (ближайший переход)
clock                    сдвиг и «сейчас» ОБЕИХ сторон + drift (расхождение)
clockreset               вернуть реальное время
vsnap                    однострочный машинный снимок:
                         state/playing/now/audible/audibleraw/frontier/
                         lag/window/warped
```

`vsnap` — основной инструмент скрипта: одна строка, разбирается
`grep -o 'lag=[0-9.]*'`. `lag = now − audibleraw` по кругу суток — главная
метрика («слышимое == сейчас»).

### Сценарии в `tools/dbgverify_resume.sh` (все без ожидания паузы)

1. Нулевая пауза (Δ≈0) → SOFT
2. Короткая пауза (Δ = 2 с, внутри окна) → SOFT
3. Длинная пауза (Δ = 1 час) → REBUILD
4. Пауза ровно на сутки (Δ ≡ 0 по модулю суток) → проверка круговой нормализации
5. **Пауза через полночь** (`totime 23:59:50` → pause → warp +30 с → audible
   обязан быть за полночью, а не 23:59:xx)
6. Часы НАЗАД (Δ отрицательная → normalize даёт ~86395 с → REBUILD, но звук
   обязан быть точкой на 5 с раньше A0)
7. Смена настроек на паузе (грязная спека → REBUILD)
8. Прерванный stop→play во время фейда
9. Две паузы подряд (накопление виртуального сдвига)

Реального ожидания в скрипте остались только короткие: запуск потока,
генерация пакета, предзаполнение кольца трека (поллинг `vsnap` до сходимости
`lag`, таймауты 15–25 с). Время самой паузы не ждём никогда.

\* Δ паузы в сценариях 1–2 больше команды `warp` (0 и 2 с), потому что к
виртуальному сдвигу добавляются 3–4 с РЕАЛЬНОГО времени на `pause`/`warp`/
`resume` по adb. Это не помеха: критерий — слышимое == сейчас, а не величина Δ.

Ключевые наблюдения:

- **Окно свежести пакета на устройстве ≈ 601 с** (`window = F0 − audible`).
  Поэтому Δ = 2 с идёт по SOFT, а Δ = 1 ч и 2 ч — по пересборке. Порог
  сценариев задан не «жёстко», а относительно этого окна.
- **Переход через полночь отработан**: pause на 23:59:5x → `warp 30s` →
  `audible = 26 s`, то есть слышимое перешагнуло полночь, а не застряло на
  23:59. Круговая нормализация работает.
- **Часы назад** дают Δ = 86398.5 с (нормализация −1.5 с), что заведомо больше
  окна → пересборка, и звук всё равно соответствует «сейчас».
- **`lag` после возобновления = 0**, т.е. `flush()` + абсолютная перемотка
  действительно убирают переходную задержку: слышимое == сейчас СРАЗУ, без
  доигрывания старого PCM из кольца трека. Именно это и было сутью бага.

  с потерей данных. **Следствие:** каждая сборка на другой машине будет
  требовать `adb uninstall com.binauralcycles.debug`. Если надоест — положить
  общий `debug.keystore` в корень и добавить в `app/build.gradle.kts`
  `signingConfigs { create("debug") { ... } }` + `debug.keystore` в .gitignore.
- **Два бага в самом скрипте** (не в приложении!):
  1. `report_resolution` сравнивал путь возобновления точной строкой, а
     решатель отдаёт уточнённые варианты `REBUILD_STALE` / `REBUILD_DIRTY` /
     `REBUILD_NO_STREAM` / `REBUILD_NO_FRONTIER`. Четыре ложных FAIL (3, 6, 7,
     9b) при нулевом Δ. Добавлено префиксное сопоставление
     (`matches_resolution`): `REBUILD` покрывает все `REBUILD_*`.
  2. Условие ожидания `t_lag` сравнивало поле `lag` напрямую, а это
     `circularDelta(now, raw)` ∈ [0, 86400): если слышимое обгоняет now на
     долю секунды, получалось ≈ 86399 и ложное «не сошлось» (плюс 20 с лишнего
     ожидания). Теперь берётся круговое расстояние — та же метрика, по которой
     выносится вердикт.

4. **Разбор результатов.**
   - Все PASS → готово.

     новый вариант `REBUILD_*`: скрипт сопоставляет по префиксу, но точное имя

   скачка на ухо (flush не должен щёлкать), поведение при РЕАЛЬНОЙ (не
   виртуальной) паузе 10–60 с, экран выключен, плюс `tools/dbgxfade.sh`
   (все 10 фаз) после правок.
6. **Закоммитить.** Репозиторий пока БЕЗ единого коммита (ветка

   корневой коммит всего проекта — делается осознанно, одной темой:

## 9. Риски и открытые вопросы

- `getCurrentTimeSeconds()` со сдвигом используется только до первого якоря
  UI-таймлайна (проверено чтением кода: `getCurrentTimeOfDaySeconds()` после
  якоря возвращает `m_uiLastUiTimeSec`), поэтому warp не ломает индикацию —
  но при ручных экспериментах стоит иметь в виду, что `warp` меняет «сейчас»
  и для UI.
- Если во время воспроизведения (не на паузе) сдвинуть часы на большой
  интервал, разрыв между `now` и фронтиром вырастет, и следующий
  pause→resume уйдёт в REBUILD — это корректно, но помнит об этом при
  интерпретации результатов.
- Сценарий 4 (сутки) принимает любой путь (`any`): SOFT там математически
  корректен (Δ ≡ 0), суть проверки — что круговая нормализация не даёт мусор.
- **Подпись debug-сборки нигде не зафиксирована.** Пакет, собранный на другой
  машине (или в Termux на самом устройстве), не обновится поверх — только
  `adb uninstall`. Пока это терпимо, но каждый прогон с новой машины начинается
  с удаления и потери данных приложения.
- Виртуальный сдвиг не переживает перезапуск процесса: `warp` живёт в памяти,
  при старте приложения сдвиг равен 0 (это и нужно — release-поведение
  не меняется).
- Δ паузы в сценариях 1–2 систематически на 3–4 с больше заданного `warp`:
  это реальное время на adb-команды `pause`/`warp`/`resume`, а не ошибка
  решателя. При желании можно вычесть его, измерив `now` до и после паузы
  (снимки уже печатают `now`), но на вердикт это не влияет.
