## 0. Главный вывод

**Приложение уже тратит 0.1–0.2 % энергии воспроизведения, и это не изменится
ни одной оптимизацией внутри приложения.** Бюджет из `battery_hotpath_audit` §4:

| Компонент | Дж/час |
|---|---|
| Приложение целиком (генерация + писатель + уведомление) | ~1.1 |
| Базовый аудиовывод (кодек, DMA, микшер) | **540–1080** |

Практический смысл: **дальнейшая работа над горячим путём — это не батарея.**
Это (а) запас прочности на слабом железе, (б) память, (в) поддержка. Ожидания
по батарее стоит привязывать к аудиовыводу, который приложение не контролирует.

При этом **предыдущий вывод «внутри `generatePackage*` оптимизировать больше
нечего» не подтвердился**: в ядре нашлось −33 % (§1.2).

## 1. Новые измерения

Методика — та же, что в `binaural-host-benchmark`: хостовый бенч, флаги release
(`-O3 -ffast-math -funroll-loops -fomit-frame-pointer -ffp-contract=fast -msse4.2`),
20–40 млн кадров на точку, медиана по 3 прогонам.

### 1.1 SSE против скаляра: ×2.1 (раньше не сравнивалось)

`generateAudioBuffer()` целиком, обе сборки из одних исходников:

| Путь | нс/кадр | запас по realtime @44.1 кГц |
|---|---|---|
| `generatePackageSse` | **5.87** | ~3860× |
| `generatePackage` (скаляр) | **12.44** | ~1820× |

Важная оговорка про NEON: путь ARM **строго слабее** SSE — в `Wavetable::fastSinNeon`
сборка таблицы скалярная (`for (i<4) y0[i] = s_sineTable[idx[i]]`), а в NEON-фейде
скалярный scatter. Поэтому SSE здесь — **консервативная оценка снизу** для arm64:
на NEON разрыв со скаляром не меньше.

См. §4.1 — в продакшене этот разрыв недостижим, но как **датчик регрессии** он полезен.

### 1.2 Ядро: −33 % (опровергает вывод прошлого прохода)

Лестница вариантов, меняется ровно один фактор за шаг:

| Вариант | нс/кадр | абс. ошибка | vs A0 |
|---|---|---|---|
| A0 база | 6.335 | 2.588e-03 | — |
| A1 дешёвая обмотка фазы | 4.834 | 2.588e-03 | −23.7 % |
| A2 + убрать ветку отрицательной дроби | 3.660 | 2.588e-03 | −42.2 % |
| A3 + парная таблица | 3.561 | 1.331e-02 (баг shuffle) | −43.8 % |
| **A4 = A2 + защита `_mm_max_ps`** | **3.931** | **2.588e-03** | **−37.9 %** |
| A5 = A3 + защита | 3.897 | 1.331e-02 (баг shuffle) | −38.5 % |

Две независимые правки:

1. **Дешёвая обмотка фазы.** Вместо `p -= TWO_PI * (int)(p * ONE_OVER_TWO_PI)`
   (mul + cvt f2i + cvt i2f + mul + sub) — два условных вычитания. Прирост фазы
   за 4 сэмпла < 4π на худшем сочетании SR/частоты (SR 8000, тон 2000 Гц ⇒ ровно 2π),
   то есть **запас двукратный**.
2. **`Wavetable::fastSinSseNonNeg`** — SSE-синус без ветки на отрицательную дробь.
   Ветка мертва, потому что `_mm_cvttps_epi32` + `and` с маской даёт `t >= 0`.
   Один `_mm_max_ps` оставлен как страховка: при крутом падении частоты внутри
   сегмента (`3*omegaStep > 3*omega`) младший лан теоретически может уйти в минус.

A3/A5 (парная таблица) отброшены: выигрыш 0.6 % против A4 при ошибке ×5 —
это был мой баг в порядке лан, а gather и так почти бесплатный.

**Итог end-to-end: 5.87 → 3.91 нс/кадр (−33 %), ~5800× realtime.**

### 1.3 Что это даёт в бюджете

При 44.1 кГц: 158.76 млн кадров/час.

| | нс/кадр | CPU/час |
|---|---|---|
| Было (замер прошлого прохода) | 6.4 | **1.02 с** |
| Стало | 3.91 | **0.62 с** |

Доля приложения в энергии воспроизведения: 0.1–0.2 % → 0.06–0.12 %.
Для батареи это незаметно; для запаса прочности на слабом устройстве — вдвое больше места.

> ⚠️ **Статус правки: НЕ ПРОВЕРЕНА.** Побитовое сравнение выхода не доведено
> (сборка прервана по просьбе — параллельно работал другой агент). Стенд готов:
> `/tmp/bench/dump2.cpp` + `/tmp/bench/cmp_dump2.sh`, запуск
> `bash /tmp/bench/build_dump2.sh && bash /tmp/bench/cmp_dump2.sh`.
> Бэкапы: `/tmp/bench/AudioGenerator.cpp.bak`, `/tmp/bench/Wavetable.h.bak`.

## 3. Новые находки

### 🔴 N1. `BinauralAudioEngine` — 1447 строк мёртвого кода

`core/audio/.../engine/BinauralAudioEngine.kt` **никогда не инстанцируется**.
`BinauralPlaybackService.audioEngine` имеет тип `BinauralStreamManager?`
(строка 112), DI-модуль `AudioModule` пуст и explicitly это комментирует.
Единственные упоминания класса — комментарии, `docs/` и устаревшие
`app/build/outputs/mapping/release/{mapping,seeds}.txt` от сборки, где он ещё был достижим.

Внутри — свой `AudioTrack`, свой `VolumeShaper`, свой WakeLock, свой
`generateAudioLoop`, своя логика аллокации direct-буфера и **свои константы,
противоречащие живым** (см. N2).

Эффект: −1447 строк поддержки; убирает главный источник путаницы при правках
политики буферов (две реализации, обе выглядят «рабочими»).
Риск: нулевой для рантайма. Перед удалением стоит проверить, нет ли обращения
через рефлексию — по исходникам его нет.

### 🔴 N2. Конфликтующие константы буфера

Один и тот же предел описан дважды, с разными значениями:

| Где | Константа | Значение |
|---|---|---|
| `BinauralStreamImpl.maxBufferBytes` (живой) | 256 МБ / 96 МБ | по битности |
| `BinauralAudioEngine.MAX_BUFFER_BYTES` (мёртв) | `1024*1024*1024` | **1 ГБ** |

Плюс расхождение комментария с кодом: `setFrequencyUpdateInterval` пишет
«верхний предел 60 с», тогда как `MAX_BUFFER_INTERVAL_MS = 600_000` мс = **600 с**.

Эффект: путаница при настройке; риск принять решение по неверной константе.
Труд: правка комментария + удаление мёртвого (N1).

### 🟠 N3. Скалярный путь генерации недостижим в продакшене

`CMakeLists.txt` даёт SIMD-define **каждому** поставляемому ABI:

| ABI | define |
|---|---|
| `armeabi-v7a` | `USE_NEON` |
| `arm64-v8a` | `USE_NEON` + `USE_NEON_ARMV8` |
| `x86` | `USE_SSE` |
| `x86_64` | `USE_SSE` |

Все четыре собираются (`app/build.gradle.kts:19`). Скалярные `generatePackage` /
`generateSolidBuffer` / `generateFadeBuffer` вызываются только из
`#else`-ветки `generateAudioBuffer` (строка 659) и из `generateBatch`,
который сам мёртв (JNI-биндинг есть, вызывающих в Kotlin нет — Н5 прошлого прохода).

Итого ~380 строк троекратно дублированной логики (scalar / NEON / SSE), из которых
в продакшене живы две. Удаление скаляра — спорное решение (теряется фолбэк для
будущих ABI вроде RISC-V), но **держать три копии fade-логики, одна из которых
никогда не исполняется и не тестируется на устройстве, — это долг**.
Минимум — пометить скалярный путь как host/test-only.

### 🟡 N4. Диагностика стыка считается всегда, даже при выключенном логе

`BinauralEngine.cpp:615–635`: блок считает `prevEndForSeam` и делает 1–2 вызова
`getChannelFrequenciesAt` **вне** макроса `PKG_LOG`. При `PKG_LOG(...) == ((void)0)`
компилятор, скорее всего, выбросит вычисления (функция inline, побочных эффектов нет),
но это не проверено.

Эффект: если не выбросит — 2 лишних lookup + 2 чтения памяти на пакет (6/час, пренебрежимо).
Труд: обернуть блок в `#if defined(ANDROID) && !defined(AUDIO_TEST_BUILD)` либо вынести
в `if (pkgBoundaryLogEnabled())`. Проверить дизассемблером перед тем, как считать находкой.

### 🟡 N5. Мёртвые переменные в горячих функциях

По предупреждениям компилятора (`-Wall -Wextra`):

| Место | Переменная | Примечание |
|---|---|---|
| `generateFadeBufferSse` (~1178) | `vBaseVol` | не используется |
| `generateFadeBufferNeon` (~769) | `vBaseVol` | не используется |
| `generatePackage` / `Neon` / `Sse` | `currentElapsedMs` | пишется, читается только в `LOG_SEG` |
| `generatePackage` (~1366, ~1661) | `lastLeft/RightSample`, `endLeft/RightSample` | **чтения из буфера**, используемые только в `LOG_SEG` |

Последние четыре — реальные загрузки из памяти в конце сегмента. Если компилятор
их не выбросит, это потенциальный промах кэша на каждый 100-мс сегмент
(6000 сегментов на пакет). Стоимость всё равно ничтожная (~3.6 мс/час в худшем случае),
но как гигиена — убрать.

### 🟠 N6. `PCM_16BIT` — переоценка: дело не в CPU, а в памяти

Прошлый проход оценил N2 в «~−30 % CPU приложения» и отложил до слепого
listening-теста. Оценка верная, но **мотивация сместилась**: CPU приложения —
это 0.1 % сессии, за него бороться бессмысленно. Настоящий приз — **память**:

| | PCM_FLOAT (сейчас) | PCM_16BIT |
|---|---|---|
| Direct-буфер, 600 с @44.1 кГц | 211.7 МБ | 105.8 МБ |
| Кроссфейд CURRENT+NEXT | 423 МБ | 212 МБ |
| Трафик `write()` | 1.27 ГБ/час | 0.64 ГБ/час |

Плюс 16-бит разблокирует длинные пакеты на 32-битных устройствах (там предел 96 МБ).

**Оценка риска выросла в моей личной шкале**: квантование тихих тонов и более
грубые фейды — это изменение звука, а не расхода. Нужен дитер (TPDF, ±0.5 LSB)
и слепой A/B. Без него принимать по-прежнему нельзя.

### 🟡 N7. `WRITE_CHUNK_MS` 8 → 30 с

450 → 120 пробуждений/час. Цена: +8 МБ на кольцо трека и худшая реакция на
паузу/смену пресета. Учитывая, что батарейный выигрыш лежит в пределах
погрешности (приложение 0.1 % сессии), **браться стоит только ради подстраховки
underrun на загруженном устройстве**, а не ради энергии.

## 4. Что НЕ является возможностью (проверено, закрыто)

Здесь перечислено то, что выглядело подозрительно и **не подтвердилось** —
чтобы не возвращаться.

### 4.1 Длина пакета не влияет ни на что, кроме памяти

`SOLID` дробится на подсегменты по 100 мс **в обеих ветвях** планировщика
(и со swap, и без) — `BufferPackagePlanner.h:388` и `:521`. Значит кривая
частот следует с шагом 100 мс независимо от длины пакета: ни точность,
ни CPU, ни пробуждения от неё не зависят. Пробуждения задаёт `WRITE_CHUNK_MS`
(это подтверждается и кодом: `chunk = minOf(packetBytes - offset, maxChunkBytes)`,
`maxChunkBytes` считается из `WRITE_CHUNK_MS`).

Дополнительное доказательство: в debug virtual-time приложение уже работает
на пакетах **250 мс** (`BinauralStreamManager.kt:312`) — и это штатный режим.

> Прошлый проход сузил настройку до 16 с, пользователь потребовал отката,
> и дефолт вернули к 600 с. **Повторно предлагать сужение дефолта не надо** —
> это уже решённый вопрос, настройка пользовательская и намеренно честная.

### 4.2 Перетаскивание точки не пересобирает поток на каждом кадре

`FrequencyGraph` коммитит изменение в сервис **только в `onDragEnd`**
(`:539`), а слайдеры в `ChannelSettingsCard` — в `onValueChangeFinished`.
Во время жеста меняется только локальный UI-state. Снаружи жеста
`updateConfig`/`updateFrequencyCurve` дедуплицируют по равенству
(`BinauralStreamManager.kt:173, 192`). Схема корректная.

### 4.3 Писатель паркуется на паузе, а не крутится

`parkWriter()` — `wait(PARK_POLL_MS)` с таймаутом 200 мс, wake по `notifyAll`.
На паузе генерация и запись запрещены, пакет и смещение сохраняются.

### 4.4 UI-опрос привязан к состоянию экрана

`startUiFrequencyUpdateJob` (1/с) и `startNotificationUpdateJob` (30 с) оба
проверяют `isScreenInteractive()`, которое после U2 — кэш по
`ACTION_SCREEN_ON/OFF`, а не binder-IPC.

### 4.5 `updateCache()` больше не узкое место

После N4 таблица адаптивная: 100–1000 мс на ячейку ⇒ 864–8640 записей ×2,
то есть 7–69 КБ вместо 6.59 МБ. Проход 19–39 мс на смену настроек закрыт.

## 6. Воспроизведение замеров

```bash
# SSE против скаляра (§1.1)
bash /tmp/bench/simd_build.sh     # две сборки из одних исходников

# Лестница вариантов ядра (§1.2)
g++ -O3 -ffast-math ... /tmp/bench/kernel2.cpp -o /tmp/bench/kernel2
/tmp/bench/kernel2

# Побитовое сравнение выхода (§1, статус правки)
bash /tmp/bench/build_dump2.sh && bash /tmp/bench/cmp_dump2.sh
```

Стенд для последнего — `/tmp/bench/dump2.cpp`: управляет `AudioGenerator`
напрямую (обход `BinauralEngine`, потому что тот читает wall-clock, а
виртуальные часы заперты за `ENABLE_DEBUG_TIME_CONTROL`, которого в release нет).
Покрытие: сетка SR × несущая × биения, все четыре остатка `samples % 4`
(при 44100: 10/20/30/40 мс → 441/882/1323/1764), крутые рампы 2000↔20 Гц
при `timeScale` 1/10/60, полный swap-цикл, фейд кусками по 1 мс, стартовые
фазы у границы 2π, все типы интерполяции и нормализации.
