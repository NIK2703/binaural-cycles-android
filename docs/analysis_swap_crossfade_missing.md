# Пропавший кроссфейд при смене каналов: разбор, хронология, решение

Дата открытия: 2026-09-03. Статус на 2026-09-03: анализ завершён, **решение
(ред. 5, конструктивная валидность) спроектировано и задокументировано, ждёт
внедрения**. Документ — единый источник истины по этой проблеме; ред. 1–4
описаны как пройденные ловушки, чтобы не наступать на них снова.

---

## 1. Симптом

При смене раскладки каналов (какое ухо слышит более высокий тон) звук ДОЛЖЕН
проходить ритуал «затухание → тишина → нарастание» (FADE_OUT → PAUSE →
FADE_IN, см. `docs/design_signed_beat_channel_layout.md` §3.4). Вместо этого
слышна **резкая смена каналов без затухания**.

Хронология жалобы (все — пользователь):
- «в момент смены каналов происходит быстрая плавная смена каналов» (эпоха
  рампы «beat проходит через ноль»).
- «исправь: при смене каналов нет ни фейд-аута ни фейд-ина».
- «я протестировал последние и релиз и дебаг — там нет затухания при смене
  каналов».
- 2026-09-03, после ред. 4 (float + `std::nextafterf`): «теперь снова резкая
  смена каналов, без затухания»; «после твоих только что сделанных изменений
  кроссфейд при смене каналов снова пропал».

**Ключевая улика — последняя фраза:** кроссфейд БЫЛ (ред. 3, double) и ПРОПАЛ
именно после ред. 4 (float/nextafterf). То есть ред. 4 на устройстве регрессирует
работавшее решение.

## 2. Архитектура (минимум для понимания)

Раскладка — это ЗНАК частоты биений, дошедшей до генератора:

```
left  = c − s(t)·b/2
right = c + s(t)·b/2
```

где `s(t) ∈ {−1, +1}` — множитель раскладки (см. `ChannelLayout.h`,
`layoutSignAt`/`channelsAt`). ТРИ источника знака складываются как числовые
множители: знак beat в точках пресета (`FrequencyPoint::beatFrequency`), релакс
`beatReduction > 100 %`, и расписание TIMER/TREND (`layoutSignAt`).

Смена раскладки по расписанию — это **СТУПЕНЬКА** `s(t)` в момент `T*`;
плавность даёт не частота, а **огибающая громкости** `layoutGainAt(t)`:

```
[затухание F] → [тишина P] → [нарастание F],  центр — в T*,
g(T*) = 0 (приподнятый косинус), окно симметрично 2F+P.
```

`layoutGainAt` возвращает ровно `1.0`, если `nearestSwapProcedure` вернула
`valid=false` ИЛИ `fadeSec=0`. Следовательно:

> **«резкая смена без затухания» ⟺ процедура смены НЕВАЛИДНА** (`valid=false`).

Генератор дополнительно режет подсегмент по `T*` (`collectSegmentCuts`), чтобы
ступенька частот попала на границу сэмпла, где огибающая равна нулю (см.
AudioGenerator.cpp, `(pieceEnd-1)`-фикс глиссандо).

## 3. Эволюция проверки переворота — где живёт баг

`nearestSwapProcedure` обязан отличать «в `T*` знак реально переворачивается» от
«`T*` формальный» (напр. TREND без пересечений даёт `T*=0` — затухать там
незачем). Для этого служит проверка «состояние чуть до `T*` ≠ состоянию чуть
после». Четыре редакции этой проверки — четыре ловушки одного семейства
«выразить окрестность через квантование float»:

### Ред. 1 — абсолютный ε = 1e-3 с
`channelSwapStateAt(T*−1e-3) == channelSwapStateAt(T*+1e-3)` → invalid.
**БАГ:** ULP float растёт с величиной (0.06 мс на 1000 с, 1.95 мс на 21600 с,
7.8 мс выше 65536 с). С ~10 часов суток `ε=1e-3` становится НИЖЕ ULP: обе точки
округляются в один и тот же float ⇒ `valid=0`, фейд пропадал **вечером и ночью**.

### Ред. 2 — `std::nextafter` без суффикса (double-перегрузка)
`std::nextafter(Tstar, ±inf)`.
**БАГ (доказан хост-зондом `tools/swap_fade_probe/ulp_probe.cpp`):** если вызов
разрешается в **double-вариант**, соседние значения (`T* ± ~7e-12 с` при
`t≈4e4`) при обратном сужении во float округляются В САМ `T*`; `before==after==T*`
⇒ «переворота нет» ⇒ `valid=0` **круглые сутки**. На устройстве:
`SWAPDIAG ... proc valid=0 Tstar=0.000 F=0.0000 P=0.0000 | gain=1.0000` при
корректном конфиге (`en=1 mode=TIMER int=30 fadeEn=1 fadeMs=2000`).

### Ред. 3 — double ε = 1e-6 (РАБОТАЛА на устройстве)
`channelSwapStateAt(double)` + проверка в double ±1e-6.
**Устройство (инструментированный дебаг):** `SWAPDIAG t=43214.074 | ...
proc valid=1 Tstar=43200.000 F=15.0000 P=0.0000 | gain=0.9906` — огибающая
реально применялась (`gain≈0.99` на излёте нарастания при `F=15 c`), кроссфейд
**СЛЫШЕН** пользователем.
**Отвергнута пользователем:** «замени все вхождения double на float» — ось суток
(0..86400 с) обязана быть `float` по всему проекту. Требование зафиксировано как
жёсткое правило.

### Ред. 4 — float + `std::nextafterf` (ЛОМАЕТСЯ на устройстве) ← текущее состояние
`std::nextafterf(Tstar, ±std::numeric_limits<float>::infinity())`.
**Хост:** `valid=1` при любом времени суток; проверено И с `-O2`, И с точными
флагами устройства `-O3 -ffast-math -funroll-loops` (`tstar_probe`, x86 g++) —
работает.
**Устройство (arm64, NDK clang, `-ffast-math`):** безусловный лог `SWAPGAIN`
показывает `valid=0 F=0.000 P=0.000 gain=1.00000` **на протяжении минут**, при
том что смены каналов слышны. Кроссфейд пропал — прямое подтверждение
пользователя («снова пропал после твоих изменений»).
**Механизм (гипотеза, наиболее вероятная):** `-ffast-math` включает
`-ffinite-math-only`; передача `±infinity` в `nextafterf` при предположении
«бесконечностей не бывает» — UB-зона, в которой clang на arm64 волен свернуть
вызов (например, в тождество `x`) — тогда `before==after==T*`. Точный машинный
механизм не устанавливался; **наблюдение надёжно и его достаточно**: ред. 4 на
устройстве даёт `valid=0`, ред. 3 давала `valid=1`, конфиг между ними не менялся
(один и тот же пресет/расписание, смена только в коде проверки).

> **УРОК (жирный):** ЛЮБАЯ проверка «соседних float через nextafter / nextafterf /
> бесконечность» несовместима с `-ffast-math` на этом тулчейне. Нельзя чинить
> подбором соседей — надо **убрать сам класс решения** (см. ред. 5).

## 4. Ложные следы (чтобы не наступать снова)

Эти гипотезы проверялись и ИСКЛЮЧЕНЫ — не тратьте на них время:

- **Stale `.so` / «правка не попала в бинарник».** Исключено: безусловный
  `__android_log_print` из новой функции печатается на устройстве.
- **`-ffast-math` на хосте.** Не воспроизводит (x86 g++ корректен даже с
  `-O3 -ffast-math`); расхождение **тулчейн-специфично** (arm64 clang vs x86 g++).
- **«Дрейф часов +600 с» (SWAPGAIN `wall`/`t`, CLOCKDRIFT).** Это **хвост
  ПРЕДГЕНЕРАЦИИ батча**, а не баг часов. Движок генерирует батч целиком
  (`m_batchDurationMinutes`, ~10 мин) и стримит его; в момент генерации `t`
  прочёсывает `[frontier, frontier+600]`, поэтому хвост батча = `wall+600`. Это
  норма. Проверка «слышимое = сейчас» идёт по НАЧАЛУ батча/фронтиру, не по хвосту.
- **`AUDIO_DEBUG` в debug-APK.** НЕ полагаться: `LOGD` может не компилироваться
  под реальный native-билд (флаг `CMAKE_CXX_FLAGS_DEBUG`/`AUDIO_DEBUG` не
  прокидывается так, как ожидается) — диагностика во время отладки ОБЯЗАНА быть
  безусловной (`__android_log_print`), иначе молчит.
- **Логи Kotlin о конфиге.** Режим/интервал на устройстве в момент `valid=0` НЕ
  были зафиксированы (открытый пункт, см. §7).

## 5. Решение — ред. 5: конструктивная валидность (без зондирования)

Убрать зондирование окрестности `T*` **полностью**. Переворот не надо
«проверять во время выполнения» — он **гарантирован самим построением
расписания**:

- **TIMER:** состояние = чётность `floor(t/I)`. На КАЖДОМ узле `k·I` `floor`
  скачет ровно на 1 (`floor((k·I−ε)/I)=k−1`, `floor((k·I+ε)/I)=k`) ⇒ знак
  переворачивается на каждом узле. Процедура валидна ⇔ интервал задан (`I > 0`).
- **TREND:** `channelSwapStateAt` считает выбранные пересечения с `timeSec < t`;
  на каждом выбранном пересечении счёт инкрементируется ⇒ переворот гарантирован.
  Процедура валидна ⇔ выбранных пересечений **≥ 1** (тогда `T*` из
  `nearestSwapTimeSec` — реальное пересечение).

Эквивалентно семантике всех четырёх редакций, но **доказуемо на бумаге** и не
зависит от nextafter/бесконечности/двойного/ULP.

**Псевдокод `nearestSwapProcedure`:**
```cpp
SwapProcedure p;
if (!cfg.channelSwapEnabled) return p;

bool hasScheduleFlip = false;
float Tstar = 0.0f;
if (cfg.channelSwapMode == ChannelSwapMode::TIMER) {
    hasScheduleFlip = (cfg.channelSwapIntervalSec > 0);
    Tstar = nearestSwapTimeSec(cfg, t);
} else {  // TREND
    // посчитать выбранные пересечения (тот же цикл, что в swapGapSec/
    // nearestSwapTimeSec, с учётом trendCrossingsValid-фолбэка)
    hasScheduleFlip = (selectedCrossingCount(cfg) >= 1);
    Tstar = nearestSwapTimeSec(cfg, t);
}
if (!hasScheduleFlip) return p;   // valid=false, Tstar=0

p.valid = true;
p.tStarSec = Tstar;
if (!cfg.channelSwapFadeEnabled) return p;  // голая ступенька

// F/P + кламп по swapGapSec — БЕЗ изменений
float F = static_cast<float>(cfg.channelSwapFadeDurationMs) / 1000.0f;
float P = static_cast<float>(cfg.channelSwapPauseDurationMs) / 1000.0f;
// ... (как сейчас) ...
```

**Альтернатива (не основная):** зонды на безопасно разнесённых точках
`T* ± gap/4` (gap из `swapGapSec`). Работает, но снова «проверка во время
выполнения» с граничными случаями (wrap полуночи у `T*=0`: `T*−gap/4` уходит в
вчера — сравнение состояний всё ещё корректно через модуль, но конструктивная
проверка проще и неуязвимее). Оставлена как запасной вариант.

**Что менять:**
- `core/audio/src/main/cpp/include/ChannelLayout.h` — `nearestSwapProcedure`:
  проверка переворота → конструктивная (выше); комментарий к функции переписать
  под историю ред. 1–5; `channelSwapStateAt` остаётся `float`.
- Для TREND понадобится подсчёт выбранных пересечений — вынести общий цикл в
  хелпер (он уже есть внутри `swapGapSec`/`nearestSwapTimeSec`, переиспользовать).

**Требование пользователя соблюдено:** код остаётся СТРОГО `float`, без `double`,
без `nextafter`/`nextafterf`/`numeric_limits<float>::infinity()`.

## 7. Открытые вопросы / риски

- **Если после ред. 5 резкая смена ОСТАЁТСЯ при `valid=1` и работающем фейде
  каждые 30 с** — значит, слышимая смена порождается **ДАННЫМИ** (знак `beat`
  кривой пресета проходит через ноль, см. «три источника знака» в §2), а не
  расписанием. Огибающая расписания такие смены **не покрывает**. Тогда
  расширение: точки смены знака `beat`-кривой включить в множество `T*` (та же
  процедура: затухание→тишина→нарастание, рез кусочков по этим моментам). Чтобы
  отличить: добавить в `SWAPGAIN` знак `beat(t)` и конфиг (`mode`/`interval`/
  `fadeEn`/`fadeMs`).
- **Зафиксировать конфиг устройства** в момент диагностики (mode/interval/
  fadeEn/fadeMs) — в логах ред. 4 его не было; это сняло бы часть неопределённости
  выше.
- `values-en/strings.xml` — хвост от прошлой задачи («each sine wave»).
