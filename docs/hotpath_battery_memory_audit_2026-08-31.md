# Аудит горячих путей: батарея и память

Дата: 2026-08-31. Аддитивно к `battery_hotpath_audit_2026-08-30.md`,
`hotpath_full_analysis_part2_2026-08-30.md`, `battery_ui_audit_2026-08-30.md`.

## 1. Выводы (сразу)

**1. Батарея оптимизирована до предела, где further work не имеет смысла.**
Приложение тратит **≈1.2 с CPU в час ≈ 0.96 Дж/ч** против базовой стоимости
непрерывного аудиовывода **540–1080 Дж/ч**, то есть **0.09–0.18 % энергии сессии**.
Даже лучшее из найденных изменений (PCM_16BIT) экономит **≈0.1 Дж/ч = 0.01–0.02 %**.
Это ниже любого порога, который пользователь способен заметить.

**2. Память — единственный рычаг с реальными последствиями.**
Именно память исторически убивала этот процесс (LMK, `memory leaks occurred`,
OOM на `allocateDirect`). Сейчас поток держит **33.5 МБ** пакетного буфера;
при шторме смены пресетов одновременно живёт несколько потоков, и буферы
складываются (оценка пика: 6 потоков × 33.55 МБ ≈ **200 МБ** — это расчёт,
не замер; задокументированный прецедент — куча 223/256 МБ со сторожем Xiaomi,
`BinauralStreamImpl.kt:441`). Это и надо снижать.

**3. Найденный структурный эффект: PCM_FLOAT упирается в потолок кольца трека
и тем самым удваивает число пробуждений писателя.**
`MAX_TRACK_BUFFER_BYTES = 2 МиБ` при 48 кГц float даёт кольцо всего **5.46 с**
(запрошено 10 с), из них 1 с съедает маржа → реальный чанк **4.46 с → 807
пробуждений в час** вместо задокументированных 450. На PCM_16BIT запрошенные
10 с (1.92 МБ) в потолок **не упираются** → чанк 8 с → **450/час (−44 %)**.
Этот эффект в прошлых аудитах не учтён: там 16-бит рассматривали только как
экономию памяти.

**4. Настройка `bufferIntervalMs = 600 с` молча урезается до 87 с.**
`PACKET_MAX_BYTES = 32 МБ` связывает пакет сильнее, чем пользовательская
настройка и чем `maxBufferBytes = 256 МБ`. Реальный пакет — **87.4 с @48 кГц**.
Комментарий в `BinauralStreamManager.kt:83-87`, утверждающий «работает как
задумано, без тихого усечения», — **неверен**.

**5. Три комментария в коде активно вводят в заблуждение** (см. §5). Из-за них
прошлая оценка «230 МБ на поток» и «450 пробуждений в час» выглядит правдоподобно,
но не соответствует действительности. Это стоит исправить даже без правок кода.

**6. Сужать дефолт `bufferIntervalMs` не предлагаю** — вопрос закрыт, настройка
пользовательская и намеренно честная. К тому же сейчас она и так урезана до 87 с,
то есть сужение дефолта ничего не изменило бы.

## 2. Что НЕ является возможностью (проверено, не повторять)

| Кандидат | Почему нет |
|---|---|
| Микрооптимизация DSP (SIMD-gather в wavetable, скалярный путь, обёртка фазы) | Генерация — 1.02 с CPU/час = 0.08–0.19 % сессии. Даже −20 % даёт 0.02–0.04 %. |
| Сужать дефолт `bufferIntervalMs` | Вопрос решён пользователем. Плюс пакет и так урезан до 87 с. |
| Удлинять/коротить пакет ради CPU | Замер прошлого аудита: **1.02 с CPU/час и при пакете 2 с, и при 190 с**. Перекрёстно подтверждается: 3600 с × 48000 кадр/с × 6.4 нс/кадр = 1.1 с/час. Длина пакета влияет **только на память**. |
| Уменьшать `MIN_WRITE_MARGIN_MS` (1000 мс) | Даёт 807 → 726/час (−10 %), ценой запаса до underrun. Несоразмерно. |
| `StreamLogger` как расход батареи | `enabled = BuildConfig.DEBUG`. В release — no-op. Влияет только на достоверность замеров в debug (flush на каждой строке). |
| `MiniGraphCache` | Ограничен 50 записями, FIFO-вытеснение, ключ уже включает `carrierRangeMin/Max`. |
| PKG_SEAM-диагностика как расход энергии | 2–3 lookup на пакет × 41 пакет/час — пренебрежимо. Это чистка кода, не оптимизация. |

## 3. Анатомия горячего пути с реальными числами

```
writerLoop (нить писателя)
  ├─ if (offset >= packetBytes)          ← РАЗ В ПАКЕТ (87.4 с → 41 раз/час)
  │    ├─ maybeGrowPacketBuffer()          дорастить 768 КБ → 33.5 МБ
  │    └─ engine.generateBufferDirect()    JNI → generateAudioBuffer
  │         ├─ config = m_config                O(1) — shared_ptr таблицы (N3)
  │         ├─ planner.planPackage()            ~600 сегментов на 87 с
  │         ├─ PKG_SEAM-диагностика             2–3 getChannelFrequenciesAt (без гарда!)
  │         └─ AudioGenerator::generatePackage{Neon,Sse}
  └─ track.write(buf, chunk, WRITE_BLOCKING)  ← РАЗ В ЧАНК (4.46 с → 807 раз/час)
```

### 3.1 Кольцо трека и чанк записи (48 кГц, PCM_FLOAT)

```
requested    = 48000 × 8 Б × 10 с = 3 840 000 Б = 3.66 МиБ
size         = min(requested, MAX_TRACK_BUFFER_BYTES = 2 МиБ) = 2 097 152 Б
             = 262 144 кадра / 48000  = 5.46 с          ← урезано в 1.8 раза
marginBytes  = 48000 × 8 × 1 с       =   384 000 Б
byMargin     = 2 097 152 − 384 000   = 1 713 152 Б      = 4.46 с
targetChunk  = 48000 × 8 × 8 с       = 3 072 000 Б      = 8 с
maxChunkBytes= min(8 с, 4.46 с)      = 1 713 152 Б      = 4.46 с   ← режет
пробуждений  = 3600 / 4.46           = 807 в час
```

### 3.2 То же на PCM_16BIT

```
requested    = 48000 × 4 Б × 10 с = 1 920 000 Б = 1.83 МиБ  < 2 МиБ → НЕ урезано
кольцо       = 10 с
byMargin     = 10 − 1 = 9 с
maxChunkBytes= min(8 с, 9 с)      = 8 с
пробуждений  = 3600 / 8           = 450 в час        (−44 %)
```

По частотам дискретизации (PCM_FLOAT → PCM_16BIT, пробуждений в час):

| SR | Кольцо float | Чанк float | Частота | Чанк 16bit | Частота | Выигрыш |
|---|---|---|---|---|---|---|
| 48000 (HIGH) | 5.46 с (урезано) | 4.46 с | **807** | 8 с | 450 | **−44 %** |
| 44100 (MEDIUM) | 5.94 с (урезано) | 4.94 с | **728** | 8 с | 450 | **−38 %** |
| 22050 (LOW) | 10 с | 8 с | 450 | 8 с | 450 | 0 |
| ≤22050 | не урезано | 8 с | 450 | 8 с | 450 | 0 |

Штраф платится ровно на двух частотах, которыми все и пользуются.

### 3.3 Пакетный буфер: почему 600 с ≠ 600 с

```kotlin
val targetSamples = minOf(
    requestedSamples,      // 48000 × 600 = 28 800 000  → 230.4 МБ
    maxSamplesByMinutes,   // 48000 × 60 × 60           → 60 мин
    maxSamplesByBytes,     // 256 МБ / 8                → 699 с
    maxSamplesByPacket     // 32 МБ  / 8 = 4 194 304    → 87.4 с  ← СВЯЗЫВАЕТ
)
```

Реальный пакет: **4 194 304 кадра = 87.4 с = 33.55 МБ** на поток.
Генераций в час: **41**, а не 6. Пакет 2 с (стартовый, рост отложен) —
1800 генераций в час по тому же CPU-бюджету.

### 3.4 Бюджет CPU на час (48 кГц, экран выключен)

| Компонент | Частота | CPU/час | Дж/час* |
|---|---|---|---|
| Генерация PCM (wavetable) | 41 пакет | 1.02 с | 0.82 |
| Писатель: пробуждение + `write()` | 807 | ~0.16 с (оценка 200 мкс) | 0.13 |
| Джоб уведомления (с дедупликацией) | 120 | ~0.02 с | 0.02 |
| **Итого приложение** | | **≈1.2 с** | **≈0.96** |
| Базовый аудиовывод (кодек, DMA, микшер) | непрерывно | — | **540–1080** |
| **Доля приложения** | | | **0.09–0.18 %** |

\* при ~0.8 Вт на активном ядре.

## 4. Предложения

### A. Память (приоритет — единственный рычаг с последствиями)

**A1. PCM_16BIT + TPDF-дитер.** Меняет стоимость сэмпла 4→2 байта на всём пути:

| | Сейчас (float) | 16 bit |
|---|---|---|
| Пакетный буфер на поток | 33.55 МБ | **16.8 МБ** |
| Пик шторма смены пресетов (6 потоков, оценка) | ~200 МБ | **~100 МБ** |
| Трафик `write()` | 384 КБ/с | **192 КБ/с** |
| Кольцо трека @48 кГц | 5.46 с (урезано) | **10 с** |
| Пробуждения писателя | 807/час | **450/час** |
| Генерация (меньше байт на запись) | 1.02 с/час | ~0.95–1.0 с/час |

Требует: конверсии float→int16 прямо в генераторе (без отдельного прохода),
правки `frameBytes`, `packetBudgetBytes`, `maxBufferBytes`, JNI-сигнатуры и логов.

Риск по качеству ниже, чем кажется: громкость применяется **после** квантования
(`track.setVolume` + VolumeShaper), поэтому шум квантования ослабляется вместе с
сигналом и SNR сохраняется. Проверить надо другое — минимальную амплитуду,
которую может выдать генератор (режим расслабления, `calculateNormalizedAmplitudes`):
если сигнал уходит ниже −60 dBFS, запас сжимается. **Обязателен слепой A/B.**

**A2. Общий бюджет пакетных буферов вместо эвристики на поток (без изменения звука).**
Сейчас рост гейтится `neededBytes * GROW_HEADROOM_STREAMS(3) > freeBytes` —
эвристика, которая не ограничивает сумму по всем живым потокам. Модульный
счётчик выделенных байт с глобальным потолком (например, 96 МБ) даёт
детерминированный пик вместо «сколько повезло». Нулевой риск для звука.

**A3. (уже сделано, не трогать)** Уходящий поток не доращивает пакет
(`fadeMode == OUT` → return), а NEXT Writer не стартует до промоушена —
значит NEXT живёт на стартовых 768 КБ. Оптимально.

### B. Пробуждения

**B1.** Приходит бесплатно вместе с A1 (807 → 450/час). Отдельно не окупается:
экономия всего ~0.07 с CPU/час ≈ 0.056 Дж/час.

### C. Гигиена (батарея ~0, ценность — поддерживаемость)

**C1. Удалить `BinauralAudioEngine.kt` — но НЕ напрямую.**
Файл мёртв как движок: нет ни одного `import`, ни одного места создания,
только упоминания в комментариях. **Но** в нём объявлен `enum class SampleRate`,
который импортируют 5 модулей (`BinauralViewModel`, `ChannelSettingsCard`,
`BinauralPlaybackService`, `DebugCommandExecutor`, `PlaybackSpec`).
Порядок: перенести `SampleRate` в `core/audio/.../model/`, обновить импорты,
затем удалить 1447 строк. Влияние на рантайм release ≈ 0 (R8 и так вырежет
недостижимое) — это время сборки и долг.

**C2. Мёртвые переменные в `generatePackage*`** — `lastLeftSample`,
`lastRightSample`, `endLeftSample`, `endRightSample`, `currentElapsedMs`
используются только внутри `LOG_SEG`. Убрать или завести под макрос.

**C3. `collectStepBoundaries()`** (`AudioGenerator.cpp:107`) аллоцирует
`std::vector<int>` на каждый SOLID-сегмент. Заменить на переиспользуемый
scratch-буфер в генераторе — убрать аллокацию из горячего пути.

**C4. `calculateNormalizedAmplitudes()` / `fastPow`** вызываются на каждый
кусок ≤100 мс, то есть **20 раз в секунду аудио**, хотя частоты внутри
SOLID-сегмента часто постоянны. Кэшировать результат по паре частот — убрать
`exp/log` из пути.

> **ЗАМЕР (2026-08-31) — ОТРИЦАТЕЛЬНЫЙ РЕЗУЛЬТАТ, кэш НЕ нужен.**
> Верхнюю границу выигрыша измерили так: `NormalizationType::NONE` убирает
> стоимость функции **полностью** (сразу `{1,1}`), любой кэш оставляет и
> проверку ключа, и первый вызов на каждую новую пару частот. Значит
> разница «NONE против CHANNEL/TEMPORAL» — это потолок C4.
> Хост-бенч (`/tmp/bench/norm.cpp`, SSE, 40 млн кадров на точку, 44.1 кГц):
>
> | пакет | NONE | CHANNEL | TEMPORAL |
> |---|---|---|---|
> | 100 мс | 4.030 нс/кадр | +0.33 % | −0.66 % |
> | 1 с | 3.938 | +0.87 % | +0.90 % |
> | 10 с | 3.964 | +0.40 % | +0.19 % |
> | 60 с | 3.953 | +0.62 % | +0.52 % |
>
> Всё это — шум (TEMPORAL на 100 мс даже «быстрее» NONE). **Потолок C4 < 1 %**
> генерации, а генерация — 0.62 с/час ⇒ **выигрыш < 6 мс в час**. Кэш добавил
> бы состояние в горячий путь (ключ, проверка, инвалидация при смене
> конфигурации) ради величины ниже шума измерения. **Не делать.**

**C5.** Обернуть PKG_SEAM-блок (`BinauralEngine.cpp:705-737`) проверкой
«логирование включено»: сейчас два `getChannelFrequenciesAt` выполняются
всегда, а нужны только для диагностической строки.

## 5. Ошибки в документации кода (найдены при анализе)

Три комментария расходятся с кодом и сбивают с толку будущие оптимизации —
из-за них легко прийти к неверным выводу «230 МБ на поток».

| Где | Что написано | Что в действительности |
|---|---|---|
| `BinauralStreamImpl.kt:88-90` | «8000 мс (450/час)» | **807/час**: кольцо урезано до 5.46 с, маржа 1 с вычитается → чанк 4.46 с |
| `BinauralStreamManager.kt:83-87` | «600 с … влезает целиком … без тихого усечения» | Урезается `PACKET_MAX_BYTES = 32 МБ` до **87.4 с** |
| `BinauralStreamManager.kt:268-274` | «Верхний предел 60 с … 60 с @48 кГц = 23 МБ» | `MAX_BUFFER_INTERVAL_MS = 600_000` (600 с) |
| `hotpath_optimization_analysis_2026-08-30.md:284-287` | «600 с @48 кГц = 230 МБ < 256 МБ → дефолт влезает целиком при любом SR» | Упирается в `PACKET_MAX_BYTES = 32 МБ` → 87.4 с |

Примечание: сам код **знает** про штраф маржи — в `BinauralStreamImpl.kt:113-114`
прямо сказано, что при урезанном кольце лишние 1000 мс «удваивают число
пробуждений». Расхождение именно в верхнеуровневом комментарии про 450/час.
