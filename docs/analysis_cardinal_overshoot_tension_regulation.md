# Анализ: заскок канальных кривых за границы при CARDINAL-интерполяции

**Вопрос:** почему при `InterpolationType.CARDINAL` канальные кривые выскакивают
за обозначенные нижнюю и верхнюю границы, и как устранить заскок регуляцией
натяжения **только в тех участках, где он происходит**, чтобы кривая там не
перескакивала границу, а **касалась** её — при этом чтобы левый и правый каналы
**не схлопывались** в точке касания (что обнулило бы частоту биений), а имели
корректное интерполированное значение.

**Область анализа:** математика сплайна и её реализация в
`Interpolation.h` / `Interpolation.kt`. **Не** входят: переключение каналов
(channel swap), режим расслабления как таковой (затрагивается только как
потребитель кривой), VolumeShaper и уровни потока.

**Метод:** точный порт C++-формул в Python + аналитический экстремум кубики
(решается производная, не сэмплирование) + стресс на случайных кривых.

**Воспроизведение:** `python3 tools/cardinal_overshoot_analysis.py` (~50 с).
Три раздела: показательные пресеты, стресс 5000 кривых, верификация
инвариантов на 3.88 млн сэмплов.

---

## 1. Главный результат

**Решение — общий вес натяжения `w[i]` на обоих каналах.** Вместо глобальной
правки `splineTension` (уродует всю кривую) или клампа результата (ломает
производную и меняет биения) вводится поузловой множитель касательной
`w[i] ∈ [0, 1]`, **одинаковый для левого и правого канала**:

```
m_i = w[i] · M_i,     M_i = s·(y[i+1] − y[i−1]),   s = (1 − tension)/2
```

Итог по стрессу 5000 случайных кривых (2–14 узлов, 4 диапазона частот,
tension ∈ {0, 0.25, 0.5}):

| Метрика | Значение |
|---|---|
| кривых, где коррекция потребовалась | 2213 / 5000 |
| сэмплов вне границ + допуск 0.1 Гц после регуляции | **0** |
| макс. число дополнительных проходов (verifying-свип) | **1** |
| кривых с потерей > 50 % модуля биений | **0** |
| худшее отношение \|beat\|\_новое / \|beat\|\_исходное | **0.8411** |

Верификация инвариантов (4000 кривых, 3 883 374 сэмпла):

```
макс. выход за границу (Гц)                : 0.100000   (допуск 0.1)
макс. разрыв C1 (Гц/интервал)              : 0.000000000
макс. |(R − L) − spline(beat)| (Гц)        : 0.000000000
```

Последняя строка — ключевая: **разность каналов остаётся точным сплайном
узлов биений**, поэтому схлопывание в нуль математически невозможно, если
номинальный сплайн биений не проходит через нуль сам.

## 2. Корень проблемы

### 2.1. Где именно теряется граница

`Interpolation::cardinal` (`core/audio/src/main/cpp/include/Interpolation.h:36-51`)
— чистый кубический Эрмит, **без какого-либо клампа**:

```cpp
inline float cardinal(float p0, float p1, float p2, float p3, float t, float tension = 0.0) {
    const float s = (1.0 - tension) / 2.0;
    const float m1 = (p2 - p0) * s;
    const float m2 = (p3 - p1) * s;
    ...
    return h00 * p1 + h10 * m1 + h01 * p2 + h11 * m2;
}
```

Единственный предохранитель во всей системе — в диспетчере
`Interpolation::interpolate` (строка 150):

```cpp
return allowNegative ? result : std::max(0.0f, result);
```

Это **нижняя** граница 0 Гц для физических частот. **Верхней границы нет
вообще**, а `carrierRange` (по умолчанию 100–600 Гц) не участвует нигде.

Показательно, что соседний тип уже умеет то, что нужно:
`Interpolation::monotone` заканчивается `return std::clamp(result, minVal, maxVal);`
(строки 94–97). У `CARDINAL` аналога нет.

### 2.2. Почему границы физически не доходят до нативного кода

`binaural::FrequencyCurve` (`core/audio/src/main/cpp/include/Config.h:133-140`)
содержит `points`, `interpolationType`, `splineTension` и кэш min/max частот —
но **не содержит `carrierRange`**. Вертикальные границы живут только в Kotlin
(`FrequencyCurve.carrierRange`, `BinauralPreset.kt:132+`) и в UI. Нативный
движок принципиально не может клампить по ним: он о них не знает.

### 2.3. Почему заскок максимален именно сейчас

`FrequencyCurve.splineTension` (`BinauralPreset.kt:138`) имеет значение по
умолчанию `0.0f`, а `BinauralViewModel.setSplineTension` (строки 1176–1194)
**не имеет ни одного вызывающего места в UI**. То есть на практике всегда
работает `tension = 0` — чистый Catmull-Rom, худший случай по overshoot.
Готовая ручка регуляции есть, но к ней не прикреплён ни один ползунок.

### 2.4. Масштаб явления

На пресетах раздела 1 инструмента заскок достигает десятков герц:
провал левого канала до **53.67 Гц** при нижней границе 100 Гц (минус 46 Гц),
выброс левого до **639.29 Гц** при верхней 600 Гц (плюс 39 Гц). Кламп в UI —
чисто пиксельный (`FrequencyGraph.kt:1021-1022`), он прячет проблему от глаз,
но в аудио уходит неклампленное значение.

## 3. Почему наивные решения не годятся

### 3.1. Кламп готового результата

```cpp
result = std::clamp(result, lo, hi);          // то, что делает monotone()
```

Не годится по двум причинам.

**Во-первых, кламп убивает гладкость.** На участке «прижатия» кривая становится
горизонтальной прямой: производная разрывна, в спектре появляются
широкополосные щёлки, слышимые как артефакт. Сплайн тем и хорош, что гладок.

**Во-вторых — и это главное — кламп ломает биения.** Каналы клампятся
независимо. Если левый упёрся в пол, а правый ещё нет, разность `R − L`
перестаёт быть сплайном узлов биений: она «сплющивается» сверху, и
интерполированное значение подменяется разностью двух клампов. Именно это
схлопывание и требовалось исключить.

### 3.2. Независимые веса для каждого канала

Очевидная идея: раз у каждого канала своя кривая, то и вес натяжения пусть
будет свой. На preset 2 это даёт:

```
общий вес  : beat [ 3.89, 10.11]   w = [1.0, 0.0707, 0.0707, 1.0]
независимо : beat [-0.21, 13.19]   w_L = [1.0, 0.0707, 0.0707, 1.0]
                                   w_R = [1.0, 0.2129, 0.2129, 1.0]
```

Оба канала честно касаются 99.9 Гц — но в **разных точках** и с разной
«силой» прижатия. Биения при этом проходят через **ноль** и меняют знак:
каналы меняются местами. Заскок не устранён, а перемещён в другую величину,
причём в ту самую, которая и есть смысл приложения.

Причина: при независимых весах разность каналов уже не выражается через узлы
биений (см. доказательство ниже — оно опирается ровно на общность `w`).

### 3.3. Глобальное повышение tension

Да, `tension → 1` убирает overshoot — ценой превращения сплайна в ломаную.
Пользователь выбирал CARDINAL именно ради плавности. Глобальная правка
уничтожает ровно то свойство, ради которого выбран режим.

## 4. Решение: общий вес натяжения

### 4.1. Идея

Сплайн — **линейный оператор** от узлов и касательных. Если умножить
касательную в узле на `w[i]`, сегмент «прижмётся» к хорде; при `w = 0` он
вырождается в саму хорду (отрезок между узлами), которая гарантированно лежит
внутре корректных границ. Значит, для каждого интервала существует допустимый
диапазон весов, и в нём можно взять **наибольший** — минимально искажающий
форму кривой.

Ключевая конструкция: вес **общий для обоих каналов**.

### 4.2. Алгоритм

Обозначения: `n` узлов, циклических (сутки 24 ч); `j = (i+1) mod n`;
`lo, hi` — границы (`max(carrierRange.min, MIN_TONE)` и
`min(carrierRange.max, MAX_TONE)`); `TOL = 0.1` Гц.

**Шаг 0. Номинальные касательные** (по каждому каналу `y ∈ {left, right}`):

```
M_i = s · (y[j] − y[i−1]),     s = (1 − tension)/2
```

**Шаг 1. Требование интервала.** Для интервала `i..j` и канала `y` найти
бисекцией наибольший `k ∈ [0,1]`, при котором кубика с касательными
`(k·M_i, k·M_j)` остаётся в границах (точный min/max кубики — из корней
производной, см. `cubic_range`). Затем взять **min по каналам**:

```
k[i] = min над каналами  max_scale(y[i], y[j], M_i, M_j, lo, hi)
```

**Шаг 2. Вес узла (сохранение C¹).** Сегмент `i..j` использует касательные узлов
`i` и `j`; узел `i` участвует в сегментах `i−1..i` и `i..i+1`. Чтобы обе
касательные в узле изменились согласованно:

```
w[i] = min(k[i−1], k[i])
```

**Шаг 3. Проверяющий свип.** Шаг 2 занижает веса, но шаг 1 считал `k` для
номинальных (невзвешенных) соседей, поэтому отдельные интервалы могут
остаться недопустимыми. Пройти по интервалам, для недопустимого вычислить
`need = max_scale(...)` для уже взвешенных касательных и домножить
`w[i] *= need; w[j] *= need`. Повторять до сходимости.

На 5000 стресс-кривых сходилось **не более чем за 1 дополнительный проход**;
в показательных пресетах сходится с нулём.

**Шаг 4. Применение.** Везде, где строится канальная кривая, касательные
берутся как `w[i]·M_i` — вместо `M_i`.

### 4.3. Ссылочная реализация

```kotlin
// core/audio/.../model/Interpolation.kt — расчет один раз на смену кривой
fun computeTensionWeights(
    left: FloatArray, right: FloatArray,
    tension: Float, lo: Float, hi: Float
): FloatArray {
    val n = left.size
    val s = (1f - tension) / 2f
    val k = FloatArray(n) { 1f }
    for (i in 0 until n) {
        val j = (i + 1) % n
        var kk = 1f
        for (y in arrayOf(left, right)) {
            val m1 = s * (y[j] - y[(i - 1 + n) % n])
            val m2 = s * (y[(j + 1) % n] - y[i])
            kk = minOf(kk, maxScale(y[i], y[j], m1, m2, lo, hi))
        }
        k[i] = kk
    }
    val w = FloatArray(n) { i -> minOf(k[(i - 1 + n) % n], k[i]) }
    repeat(MAX_SWEEPS) {                      // проверяющий свип
        var changed = false
        for (i in 0 until n) {
            val j = (i + 1) % n
            var need = 1f
            for (y in arrayOf(left, right)) {
                val m1 = w[i] * s * (y[j] - y[(i - 1 + n) % n])
                val m2 = w[j] * s * (y[(j + 1) % n] - y[i])
                if (!feasible(y[i], y[j], m1, m2, lo, hi))
                    need = minOf(need, maxScale(y[i], y[j], m1, m2, lo, hi))
            }
            if (need < 1f) { w[i] *= need; w[j] *= need; changed = true }
        }
        if (!changed) break
    }
    return w
}
```

`maxScale` — бисекция (24 итерации дают точность ~6e-8), `feasible` — проверка
точного экстремума кубики против **эффективных** границ (см. §5).

### 4.4. Сложность

`O(n)` на вычисление касательных, `O(n · 2 канала · 24 итерации)` на веса —
итого `O(n)` с малой константой. Веса зависят **только от узлов и границ**, то
есть пересчитываются при смене кривой — ровно там же, где уже работает
`updateCache()` / `cachedHash` (`Interpolation.h:584-624`). **На сэмпл ничего не
добавляется**: горячий путь генерации буфера не меняется вовсе.

## 5. Два тонких места без которых алгоритм не работает

### 5.1. Эффективные границы

Если узел сам лежит вне `[lo, hi]`, никаким конечным уменьшением натяжения
интервал не сделать допустимым: кривая обязана пройти через узел. Первая версия
прототипа именно на этом «залипала»: веса уходили в `0.0`, а нарушения
оставались, потому что монотонность по `k` нарушалась (даже `k = 0`
оказывался недопустим).

Решение — требовать лишь, чтобы **касательные не добавляли** нарушения
сверх того, что задано узлами:

```
lo_eff = min(lo, p1, p2)
hi_eff = max(hi, p1, p2)
```

При этом `k = 0` всегда допустим (отрезок `p1..p2` лежит в `[lo_eff, hi_eff]`),
монотонность восстанавливается, бисекция корректна. В штатном режиме узлы
всегда внутри диапазона — их клампит `FrequencyMath.clampBeat` через
`carrierRange`, — так что `lo_eff == lo`, и ослабление ничего не меняет; оно
нужно как страховка на граничных и переходных состояниях.

### 5.2. Допуск на касание `TOL = 0.1` Гц

Узел, лежащий **ровно** на границе (например, ровно 100.00 Гц), формально
создаёт микроскопическое нарушение (~0.001 Гц) — просто потому, что касательная
в соседнем узле направлена наружу. Устранить его можно только полным обнулением
касательной, то есть ценой уничтожения формы кривой.

Без допуска алгоритм делал именно это: на preset 3 («зигзаг», узел ровно на
границе) веса падали до `w = [0,0,0,0,0,0]` при **полном отсутствии** реального
заскока. С допуском 0.1 Гц тот же пресет даёт `w = [1,1,1,1,1,1]` —
коррекция не требуется, кривая не тронута.

Величина выбрана из практики: 0.1 Гц на слух неразличимо (порог различения
частоты тона — порядка 0.5–1 % , то есть десятые доли герца на низких частотах
и единицы герц на 600 Гц), при этом на графике при масштабе 100–600 Гц это
0.02 % высоты — касание визуально неотличимо от точного.

## 6. Доказательства

### 6.1. Биения сохраняются тождественно

Пусть `L(t)` и `R(t)` — сплайны каналов с касательными `w[i]·M_i^L` и
`w[i]·M_i^R`. Раскроем Эрмит на интервале `i..j`:

```
R(t) − L(t) = h00·(R_i − L_i) + h10·(w_i·M_i^R − w_i·M_i^L)
            + h01·(R_j − L_j) + h11·(w_j·M_j^R − w_j·M_j^L)
```

Первое и третье слагаемые: `R_i − L_i = beat_i` по построению каналов
(`left = carrier − beat/2`, `right = carrier + beat/2`).

Второе и четвёртое — здесь и используется **общность веса**:

```
w_i·(M_i^R − M_i^L) = w_i·s·[(R_j − R_{i−1}) − (L_j − L_{i−1})]
                    = w_i·s·[beat_j − beat_{i−1}]
                    = w_i·M_i^beat
```

Итого:

```
R(t) − L(t) = H(beat_i, beat_j; w_i·M_i^beat, w_j·M_j^beat; t)
```

**Разность каналов — в точности сплайн узлов биений с теми же весами.** Не
приближённо, а тождественно (численно подтверждено: отклонение 0.000000000 Гц
на 3.88 млн сэмплов).

Следствия:
- Схлопывание каналов в нуль возможно тогда и только тогда, когда сплайн самих
  биений проходит через нуль — то есть это свойство **заданной кривой**, а не
  артефакт регуляции.
- Знак биений (раскладка каналов) сохраняется: сплайн непрерывен и не
  пересекает нуль, если не пересекает его номинальный сплайн биений.
- Уменьшение натяжения *сглаживает* кривую биений ровно там же, где сглаживает
  каналы — это согласованное, а не рассогласованное изменение.

### 6.2. Сохраняется C¹

В узле `i` сходятся сегменты `i−1..i` и `i..i+1`. Оба используют касательную
узла `i`, умноженную на **один и тот же** `w[i]`. Производная сегмента в узле
равна его касательной, значит обе односторонние производные равны `w[i]·M_i`:
разрыва нет. Численно: макс. разрыв 0.000000000 Гц/интервал.

Отсюда же следует, почему нельзя брать вес **интервала** (`k[i]`) напрямую:
тогда левый и правый сегменты в узле умножали бы общую касательную на разные
числа и C¹ рассыпалась бы. Шаг 2 (`w[i] = min(k[i−1], k[i])`) — цена гладкости,
небольшое занижение весов, которое и компенсирует шаг 3.

### 6.3. Границы соблюдаются

`maxScale` по построению возвращает наибольший `k`, при котором **точный**
экстремум кубики (корни производной плюс концы интервала, не сэмплирование)
лежит в эффективных границах. Шаг 3 доводит до выполнения все интервалы.
Численно: макс. выход 0.100000 Гц = ровно `TOL`, ни одного сэмпла дальше.

## 8. Точки интеграции

Веса должны применяться **одинаково во всех местах**, где строится канальная
кривая, иначе звук и график разойдутся.

### 8.1. Что добавлено в натив

Границы `[carrierMinFreq; carrierMaxFreq]` в натив **не передаются** — это
оказалось не нужно и даже вредно. Веса считает Kotlin: именно он знает
`carrierRange` (в нативе этих данных нет, см. §2.2), и вторая реализация
алгоритма на C++ означала бы две копии одного численного кода, которые
обязательно разойдутся. В натив уезжает готовый массив весов: он умеет только
применять его, но не вычисляет.

1. **`Config.h:156` — `FrequencyCurve::tensionWeights`:** `std::vector<float>`
   с весами касательных по узлам. Пустой или не того размера — регулировка
   выключена.
2. **`jni.cpp:55` — `readTensionWeights`:** общий приёмник с защитной
   валидацией. Отклоняет `null`, несовпадение размера с числом узлов, `NaN`,
   `Inf` и значения вне `[0; 1]` (мусор заменяется на нейтральный `1.0`).
   Публикует массив только целиком заполненным — частичное применение чужих
   весов к чужим узлам хуже, чем выключенная регулировка.
3. **`jni.cpp:183`:** попутно закламплен `splineTension` в `[0; 1]`. Вне
   диапазона формула `s = (1 − tension)/2` даёт отрицательное `s`, касательные
   разворачиваются и сплайн петляет — это уже поломка, а не «натяжение».

### 8.4. Режим расслабления

`RelaxationModeSettings.generateVirtualPoints` подменяет кривую виртуальными
точками, и `curveWithRelaxation` передаёт её дальше как обычную
`FrequencyCurve`. Веса считаются **по подменённой кривой**, а не по исходной —
иначе отрегулированная кривая движка разойдётся с той, что рисует UI.

Тонкость: `NativeAudioEngine.updateConfig` (`NativeAudioEngine.kt:280`)
передаёт `playbackWeights`, посчитанные **по тем же точкам**, которые реально
уезжают в движок, а не по `config.curve.points`. Это принципиально: взвешивать
нужно ровно тот набор узлов, по которому натив построит таблицу.

### 8.5. Схлопывание дублей по времени

Нативный `buildLookupTableInternal` схлопывает точки с одинаковым временем,
оставляя **последнюю**, и сверяет размер массива весов с числом узлов уже
**после** схлопывания. Поэтому `CardinalTension.forPoints` схлопывает дубли
тем же правилом (`collapseDuplicateTimes`). Без этого кривая с задвоенными
точками молча лишилась бы регулировки ровно в тот момент, когда она нужна, —
защита по размеру просто отбросила бы массив.

## 9. Рекомендации попутно

1. **Подключить `setSplineTension` к UI** (`BinauralViewModel.kt:1176-1194`).
   Метод готов, вызывающих мест нет — пользователь лишён возможности снизить
   overshoot вручную, и это единственный видимый сейчас «рычаг».
2. **Валидация `splineTension` в JNI** (`jni.cpp:144`) — диапазон `[0, 1]`;
   вне его формула `s = (1 − tension)/2` даёт инвертированные касательные.
3. **Тест-регрессия — сделано.** `CardinalTensionTest.kt` (18 тестов) закрывает
   инварианты из §6: границы на 300 случайных кривых, касание вместо перескока,
   точность `R − L == spline(beat)` и `(L + R)/2 == spline(carrier)`, отсутствие
   излома, отсутствие лишних нулей биений. C++-тест `FrequencyTableTest.cpp`
   расширен до 11 тестов: те же веса применяются к таблице, единичные веса
   дают тождественное преобразование, нулевые веса снимают overshoot,
   несовпадение размера отключает регулировку.
4. **Унифицировать вычислители.** Веса подключены во ВСЕХ точках, где строится
   канальная кривая, — расхождения звука и графиков нет. Но формула живёт в трёх
   местах (`Interpolation.h`, `Interpolation.kt`,
   `FrequencyGraph.interpolateFrequency`), и выбор интервала в третьем из них
   написан отдельным линейным поиском. Пока все три согласованы, но любая
   правка правила «какому интервалу принадлежит время» должна вноситься
   синхронно. Это долг поддерживаемости, а не текущий дефект.
5. **`monotone()` уже клампит** по `minVal/maxVal` (строки 94–97). Стоит
   проверить, не страдает ли он тем же рассогласованием каналов, что описано в
   §3.1, — кламп там тоже независимый.

## 10. Вывод

Заскок — не «баг округления», а следствие трёх совпавших факторов: у
`cardinal()` нет клампа (в отличие от `monotone()`), вертикальные границы не
доходят до нативного кода, а `splineTension` зафиксирован в худшем значении `0`.

Предложенное решение — **поузловой общий вес натяжения** — устраняет заскок
локально (веса равны 1 всюду, где коррекция не нужна), превращает перескок в
касание границы с точностью 0.1 Гц, сохраняет C¹-гладкость и — за счёт
общности веса — гарантирует, что разность каналов остаётся **точным сплайном
узлов биений**. Схлопывание каналов в точке касания исключено не эвристикой, а
алгеброй: оно возможно лишь там, где через нуль проходит сам сплайн биений.

Стоимость — `O(n)` один раз на смену кривой, ноль добавлений в горячий путь
генерации аудио.
