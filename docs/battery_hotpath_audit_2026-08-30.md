## 0. Главный вывод

**Горячий путь DSP уже оптимизирован до уровня, где он не виден на фоне стоимости
самого аудиовывода.** Суммарная нагрузка приложения — **≈1.4 с CPU в час**
(0.04 % одного ядра, ≈1.1 Дж/ч ≈ 0.31 мВт·ч) against базовой стоимости
непрерывного воспроизведения 150–300 мВт (540–1080 Дж/ч).
То есть **≈0.1–0.2 % энергии сессии**. Пакетная архитектура работает: она
уже убрала 99.9 % того, что можно было убрать микрооптимизациями.

Следовательно, дальше искать надо **не в DSP**, а в двух других местах:

1. **Структурные рычаги конфигурации** — частота дискретизации, разрядность PCM,
   предел размера буфера. Они меняют *количество* работы, а не её удельная стоимость.
2. **Стоимость, которую нельзя убрать, но можно не сломать** — WakeLock, аудиотрек,
   уведомления. Здесь риск не в экономии, а в регрессиях (щелчки, обрыв).

Отдельно: найдено **3 новых дефекта/узких места**, которых нет в
`docs/battery_hotpaths_analysis.md` — см. §3 (N1, N2, N3).

## 3. Новые находки

### 🔴 N1. `MAX_BUFFER_BYTES` молча урезает пакет в 3 раза, сводя на нет настройку интервала

`BinauralStreamImpl.kt:222-228`:

```kotlin
val maxSamplesByMinutes = rate.toLong() * 60 * MAX_BUFFER_MINUTES   // 60 мин
val maxSamplesByBytes   = MAX_BUFFER_BYTES / 8L                     // 8388608
samplesPerChannel = minOf(
    rate.toLong() * bufferIntervalMs / 1000L,   // 44100 * 600 = 26 460 000
    maxSamplesByMinutes,
    maxSamplesByBytes                            // ← 8 388 608 всегда меньше
).toInt()
```

`maxSamplesByBytes = 8 388 608` **меньше** запрошенных 26 460 000 при любом
интервале ≥ 190 с. Итог:

| Частота | Запрошено (`bufferIntervalMs = 600 с`) | Реально | Пакетов/час | Потеря |
|---|---|---|---|---|
| 22050 Гц | 600 с | **380.4 с** | 9.5 | ×1.58 |
| 44100 Гц | 600 с | **190.2 с** | 18.9 | ×3.15 |
| 48000 Гц | 600 с | **174.8 с** | 20.6 | ×3.43 |

Настройка «интервал генерации» **не работает ни в одном режиме**, а пользователь
и логи видят 600 000 мс. Прямой ущерб — лишние пробуждения CPU: 18.9 вместо 6 в час.

**Решение:** перейти на `ENCODING_PCM_16BIT` (см. N2) — тогда при 22050 Гц
600 с = 52.9 МБ и предел перестаёт быть узким местом (6 пакетов/час, **×3.15 меньше**).

### 🟠 N2. `ENCODING_PCM_FLOAT` — вдвое больше памяти и трафика без акустической выгоды

`BinauralStreamImpl.kt:270,281` — трек создаётся с `ENCODING_PCM_FLOAT`
(4 байта/сэмпл, `directBuffer = allocateDirect(samplesPerChannel * 2 * 4)`).

Для бинауральных ритмов — двух чистых синусоид — динамический диапазон 16 бит
(96 дБ) более чем достаточен: собственный шум квантования лежит далеко ниже
порога слышимости на фоне обычной комнатной обстановки.

Переход на `PCM_16BIT` даёт одновременно:

| | Было | Стало |
|---|---|---|
| Размер direct-буфера за те же 600 с @22050 | 105.8 МБ | **52.9 МБ** ✅ влезает в 64 МБ |
| Пакетов/час @22050 | 9.5 | **6.0** (×1.58 меньше) |
| Трафик записи в трек @22050 | 352 КБ/с | 176 КБ/с |
| Запас до underrun в 64 МБ @44100 | 190 с | 380 с |

Побочный выигрыш: при 44100 Гц тот же 64 МБ покроет 380 с вместо 190 с.

Обратная сторона: нужен дитеринг/округление при конверсии float→int16, иначе на
очень низкой громкости появится легкая окраска. Для генератора синусов это
один `_mm_cvtps_epi32` + сдвиг на пакет, стоимость пренебрежима.

### 🟠 N3. Копирование всех 6.59 МБ таблиц частот на каждый пакет ради 0.2 % данных

`BinauralEngine::generateBatch()`:

```cpp
BinauralConfig config;
{ std::shared_lock<std::shared_mutex> lock(m_configMutex); config = m_config; }
```

Копируются оба `std::vector<float>` по 864 000 записей. Но **пакет длится
190–380 с**, то есть из таблицы читается ≈1900–3800 записей — **0.2–0.4 %**.
Остальные 99.6 % копируются зря. Цена — 0.651 мс + 2 alloc/free по 3.3 МБ
на пакет (≈37.8 крупных аллокаций в час — это уже фактор для GC/heap).

**Решение (минимальное, без смены архитектуры):** держать таблицы за
`std::shared_ptr<const std::vector<float>>` и копировать только скалярные поля
+ инкремент счётчика ссылок. Пересборка при `setConfig()` создаёт новый
`shared_ptr`, движок подхватывает его под тем же `shared_lock`.
Стоимость копии конфига: **0.651 мс → ~0 мкс**.

### 🟡 N4. Таблица частот: разрешение 100 мс избыточно на порядки

`FREQUENCY_TABLE_INTERVAL_MS = 100` → 864 000 записей × 2 канала = **6.6 МБ**.
При этом таблица **линейно интерполируется при чтении**
(`BinauralEngine.cpp:540-543`, `Interpolation.h:660-673`), то есть разрешение
ограничивается только кривизной кривой, а не шагом таблицы.

Кривая пресета растянута на сутки; даже быстрый пресет меняет несущую
на ~1–2 Гц/с. Ошибка линейной интерполяции на шаге Δt:
`(1/8)·f''·Δt²` — при Δt = 1 с она на много порядков ниже 0.01 Гц.

Снижение до **1 с (86 400 записей, 346 КБ)** даёт ×10:

| | 100 мс | 1 с |
|---|---|---|
| Память таблиц | 6.6 МБ | **0.69 МБ** |
| `updateCache()` (MONOTONE) | 37.7 мс | **~3.8 мс** |
| Копия конфига (если не делать N3) | 0.651 мс | **0.065 мс** |
| Поиск min/max (3 прохода) | 2.6 М чтений | 259 К чтений |

Плюс таблица целиком влезет в L2/L3 — исчезнут промахи кэша при чтении.
Рекомендуется начинать с 1 с и проверять A/B на слух; при желании можно
оставить 0.5 с как компромисс.

### 🟡 N5. `updateCache()` (19–39 мс) на каждое изменение настроек

`setConfig()` → `updateCache()`. `BinauralViewModel.updateAudioConfig()`
вызывается из `onServiceConnected`, из коллектора пресета и после каждого
`restartWithFadeIfNeeded()` (8 точек вызова). То есть **каждое движение
слайдера** = полная пересборка 1.7 млн записей + 2 аллокации по 3.3 МБ.

Смягчается тем, что `restartWithFadeIfNeeded()` делает `delay(300)` перед
`applyChanges()`, что работает как дебаунс. Но для MONOTONE-интерполяции
39 мс — это **2.3 кадра 60 Гц**, при перетаскивании слайдера это заметно.

`N4` решает это автоматически: 39 мс → ~4 мс.

### 🟡 N6. `startUiFrequencyUpdateJob()` без защиты по экрану и без привязки к состоянию

`BinauralPlaybackService.kt:267` — джоб запускается **безусловно в `onCreate()`**,
внутри цикла нет ни `isScreenInteractive()`, ни проверки воспроизведения на
входе (проверка `_isPlaying` есть только *внутри*, уже после `delay(1000)` и
после вызова `updateCurrentFrequencies()`).

Остановка — только из `onAppBackground()` (стр. 1165), который зовётся из
`MainActivity.onPause()`. **Сценарий отказа:** сервис — sticky; если система
пересоздаст его, пока приложение в фоне, `onAppBackground()` уже не придёт,
и цикл 1 Гц (`updateCurrentFrequencies()` через JNI + сборка объектов
`NotificationContent`/`MetadataContent` для дедупликации) будет крутиться
**при выключенном экране до перезапуска процесса** — 3600 итераций/час.

Стоимость одной итерации невелика, и дедупликация (P0-1) отсекает binder-IPC,
но **сама сборка объектов для сравнения остаётся** — это 3600 аллокаций и
форматирований строк в час.

**Решение (3 строки):** перенести `if (!isScreenInteractive()) continue` из
`startNotificationUpdateJob` в `startUiFrequencyUpdateJob`, и запускать джоб
в `onCreate` только если `isScreenInteractive()`.

### ⚪ N7. Полиномиальный синус вместо wavetable — ×1.29, но **не про батарею**

Замер §2.3: **×1.29** быстрее, точность **лучше** (2.075e-07 против 1.326e-06).
Wavetable-путь платит SIMD-gather: `s_sineTable[idx[i]]` и `s_sineTable[idx[i]+1]`
— 8 скалярных загрузок на 4 сэмпла, это и есть основной стоимость в NEON/SSE.

Экономия: 1.03 → 0.79 с CPU/час, то есть **0.24 с CPU/час = 0.2 Дж/ч**.
На фоне 540–1080 Дж/ч базовой стоимости воспроизведения — **0.02–0.04 %**.

**Рекомендация: не делать ради энергии.** Единственный резон — снизить
латентность генерации при старте/смене пресета (54 мс → 42 мс на пакет,
незаметно) или разгрузить CPU на слабых устройствах. Если делать — то
обязательно с корректной редукцией фазы (полная свёртка в [-π, π] + одна
складка), что и было воспроизведено в бенчмарке; «короткая» редукция
только через `π − |x|` даёт ошибку 2.0 на фазах вне [-π/2, π/2].

## 4. Бюджет энергии на час воспроизведения (44100 Гц, экран выключен)

| Компонент | Частота | CPU/час | Дж/час* |
|---|---|---|---|
| Генерация PCM (wavetable) | 18.9 пакетов | 1.03 с | 0.82 |
| Копия `BinauralConfig` (N3) | 18.9 | 0.012 с | 0.01 |
| Писатель: пробуждение + `write()` 2 с | 1800 | ~0.36 с (оценка 200 мкс/пробуждение) | 0.29 |
| Джоб уведомления (с дедупликацией) | 120 | ~0.02 с | 0.02 |
| Продление WakeLock | 12 | ~0 с | 0.00 |
| **Итого приложение** | | **≈1.4 с** | **≈1.1 Дж** |
| Базовый аудиовывод (кодек, DMA, микшер) | непрерывно | — | **540–1080** |
| **Доля приложения** | | | **0.1–0.2 %** |

\* при ~0.8 Вт на активном ядре.

**Писатель (0.5 Гц) — самый частый источник пробуждений в приложении**,
в 95 раз чаще генерации. Это следствие того, что пакетная генерация экономит
CPU генерации, но **не** меняет частоту подпитки трека.

Можно поднять `TRACK_BUFFER_MS 3000 → 12000` и `WRITE_CHUNK_MS 2000 → 8000`
(→ 450 пробуждений/час, ×4 меньше), и это **одновременно увеличит** запас до
underrun с 1 с до 4 с (сейчас он равен `TRACK_BUFFER_MS − WRITE_CHUNK_MS`).
Цена — +3.2 МБ на буфер трека. Риск: `pause()` останавливает трек немедленно,
не дожидаясь опустошения буфера, так что отзывчивость паузы не страдает;
но реакции на `setVolume` и программные фейды станут «дальше по времени».
Требует теста на устройстве.

## 7. Что внедрено (результат)

Правки внесены 2026-08-30. Ниже — измеренный эффект (тот же бенч, те же флаги).

### 7.1 N3 — таблицы через `shared_ptr`: копия конфига стала O(1)

`FrequencyCurve::lowerFreqTable/upperFreqTable` теперь
`shared_ptr<const std::vector<float>>`. `config = m_config;` на каждом пакете
копирует только скаляры + два счётчика ссылок.

| | До | После |
|---|---|---|
| Копия `BinauralConfig` на пакет | 0.651 мс | **0.0001 мс** (×6500) |
| memcpy на пакет | 6.59 МБ | 0 |
| Крупных аллокаций на пакет | 2 × 3.3 МБ | 0 |

Безопасность: `buildLookupTableInternal()` выделяет **новые** векторы и
публикует их одной парой присваиваний в конце. Писатель, держащий копию
конфига на время генерации, не может увидеть наполовину построенную таблицу —
это проверяется тестом `FrequencyTableSharing.RebuildPublishesNewTables_OldCopyStaysValid`.

### 7.2 N4 — адаптивный шаг таблицы (НЕ фиксированный 1 с!)

Первоначальный план «взять фиксированный шаг 1 с» **отвергнут по результатам
замера**: он безопасен только для кривых с редкими точками. Замер
(`/tmp/table_resolution_test.cpp`, эталон — точный сплайн):

| Кривая | 100 мс | 1 с |
|---|---|---|
| Пресет по умолчанию (точки через 3 ч) | 0.0002 Гц | 0.0002 Гц |
| Пила, точки через 10 мин | 0.0020 Гц | 0.0042 Гц |
| **Пила, точки через 60 с** | 0.0135 Гц | **0.3925 Гц** |
| **Пила, точки через 10 с** | 0.1420 Гц | **12.9 Гц** |

Пользователь вправе ставить точки сколь угодно часто, поэтому фиксированный
крупный шаг дал бы ошибку до десятков Гц. Вместо этого шаг стал **адаптивным**:

```
step = clamp(minGapBetweenPoints * 1000 / 1000,   // 1000 ячеек на минимальный зазор
             100 мс,                              // ПОЛ = историческое разрешение
             1000 мс)                             // потолок
```

**Пол шага = 100 мс** — принципially: это разрешение, с которым таблица жила
всегда. Поэтому адаптивный шаг **никогда не даёт ошибки больше прежней** —
кривая с частыми точками упирается в пол и ведёт себя в точности по-старому.

Измеренный эффект (production-код, эталон — точный сплайн):

| Кривая | Шаг | Записей | МБ/канал | Ошибка |
|---|---|---|---|---|
| Пресет по умолчанию (8 т., 3 ч) | 1000 мс | 86 400 | **0.33** | 0.000092 Гц |
| 8 точек через 1 ч | 1000 мс | 86 400 | 0.33 | 0.000122 Гц |
| 8 точек через 10 мин | 600 мс | 144 000 | 0.55 | 0.000122 Гц |
| Пила через 10 мин | 600 мс | 144 000 | 0.55 | 0.002563 Гц |
| Пила через 60 с | 100 мс | 864 000 | 3.30 | 0.006592 Гц (= как раньше) |
| Пила через 10 с | 100 мс | 864 000 | 3.30 | 0.136871 Гц (= как раньше) |

| | До | После |
|---|---|---|
| Таблица, записей/канал | 864 000 (всегда) | 86 400 … 864 000 |
| Память таблиц (типичный пресет) | 6.6 МБ | **0.66 МБ** (×10) |
| `updateCache()` LINEAR | 19.4 мс | **2.56 мс** (×7.6) |
| `updateCache()` CARDINAL | 30.0 мс | **3.54 мс** (×8.5) |
| `updateCache()` MONOTONE | 37.7 мс | **4.44 мс** (×8.5) |

`updateCache()` вызывается на **каждое** изменение настроек (движение слайдера),
так что это прямой выигрыш в отзывчивости UI: 37.7 мс ≈ 2.3 кадра 60 Гц → 4.4 мс.
Попутно решается N5.

Гарантия памяти закреплена тестом: число записей ∈ [86 400; 864 000],
то есть **никогда не превышает исторический максимум**.

### 7.3 N6 — guard экрана в UI-джобе

`startUiFrequencyUpdateJob()` (`BinauralPlaybackService.kt`) больше не
запускается при выключенном экране и проверяет экран внутри цикла.
Сервис sticky: при пересоздании в фоне `onAppBackground()` не приходит, и
раньше цикл крутился 1 Гц при выключенном экране до конца жизни процесса
(3600 итераций/час: JNI-опрос частот + сборка контента для дедупликации).

### 7.4 N1 — урезание буфера сделано видимым, потолок НЕ поднят

`MAX_BUFFER_BYTES = 64 МБ` урезает запрошенные 600 с до 190 с @44.1 кГц
(18.9 пакетов/час вместо 6). Теперь это пишется в лог потока
(`prepare spec#N: buffer interval clamped ...`), а не происходит молча.

**Потолок НЕ поднят** — осознанно. Выигрыш от честных 600 с:
9.5 → 6 пакетов/час при 22.05 кГц = ~0.2 с CPU/час = **~0.02 % энергии
сессии**. Против этого — документированная история `OutOfMemoryError` в
`prepare()` именно на буферах ~212 МБ при уничтоженной активити. При 600 с и
22.05 кГц буфер = 105.8 МБ (×2 в кроссфейде = 212 МБ) — ровно та зона, где
это уже падало. 0.02 % не оправдывает возврат к риску.

### 7.5 Что НЕ сделано и почему

| Находка | Почему нет |
|---|---|
| **N2** `ENCODING_PCM_FLOAT` → `PCM_16BIT` | Даёт ×2 к длительности в том же объёме и половинный трафик записи, но требует перевода выхода генератора на int16 во всех трёх путях (scalar/NEON/SSE) и всех типах сегментов, плюс дитеринг. Выигрыш ≈ 0.05 % энергии сессии; риск — тихая порча звука, которую я не могу проверить на слух. Требует A/B-прослушивания. |
| **N7** полиномиальный синус вместо wavetable | ×1.30 и точность лучше (2.075e-07 против 1.326e-06), но это 0.24 с CPU/час = 0.02–0.04 % сессии. Правит ядро DSP. Не стоит риска. |
| Писатель 2 с → 8 с (трек 3 с → 12 с) | −4× к пробуждениям (1800 → 450/час) и запас до underrun 1 с → 4 с. Но меняет тайминги фейдов; этот проект уже ловил щелчки и обрывы именно на стыках. Требует теста на устройстве. |

### 7.6 Итог по приложению

| Компонент | Было, CPU/час | Стало |
|---|---|---|
| Генерация PCM | 1.03 с | 1.02 с (не менялась — таблица на неё не влияет) |
| Копия `BinauralConfig` | 0.012 с | **~0** |
| `updateCache()` на изменение настроек | 19–38 мс | **2.5–4.4 мс** |
| Память таблиц частот | 6.6 МБ | **0.66 МБ** (типичный пресет) |
| 1 Гц джоб при выключенном экране | до 3600 итер./час | **0** |

Энергия сессии: приложение было ~1.4 с CPU/час ≈ 0.1–0.2 %; внедрённое
убирает малую часть и этого. **Главный практический выигрыш — не батарея,
а память (−6 МБ) и отзывчивость UI на движениях слайдеров (×8.5).** Это
честный результат: DSP-путь был уже оптимизирован, и замер это подтвердил.
